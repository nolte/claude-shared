# Portfolio-In-Flight-Management

Status: draft

## Kontext

Das `nolte/*`-Portfolio hat bereits Specs für die statische Seite organisatorischer Gesundheit: `portfolio-management` deklariert, *welche Capability wo lebt*, `continuous-improvement` deklariert, *wie aus einem Audit-Finding ein spezialistengetriebener Fix wird*, und `workflow-health` deklariert, *wie eine rote CI in einem einzelnen Repository zurück auf grün triagiert wird*. Keine dieser Specs beantwortet die operative Frage, **welche Arbeit aktuell portfolio-weit in Bewegung ist und wo sie ins Stocken geraten ist**. Offene Issues sammeln sich ohne Triage an, Pull Requests stehen an roten Checks oder ungelösten Review-Kommentaren, Feature-Branches driften von `develop` weg, ohne je einen PR zu öffnen, GitHub-Discussions stellen Nutzerfragen, die niemand routet — und das einzige bestehende Erkennungssignal ist „ein Maintainer hat es zufällig bemerkt". Diese Spec füllt die Lücke mit einer periodischen, on-demand Cross-Repository-Inspektion, die einen priorisierten Spezialisten-Dispatch-Report produziert.

Die *In-Flight*-Perspektive ist bewusst komplementär zu `portfolio-management`. Letztere fragt „hat diese Capability einen Owner?"; diese Spec fragt „bewegt sich die Arbeit, die bereits begonnen wurde, tatsächlich?". Eine Capability mit eindeutigem Owner kann immer noch einen festgefahrenen PR haben; ein Repository mit gesunder Workflow-Oberfläche kann immer noch Issues haben, die seit Monaten niemand triagiert hat. Beide Audits laufen unabhängig und speisen denselben `continuous-improvement`-Spezialisten-Dispatch-Loop.

In-Flight-Findings werden bewusst nicht auto-remediiert. Der Audit produziert einen priorisierten Report, der pro Finding benennt, welcher bestehende Skill oder Agent im `nolte-shared`-Plugin ihn übernehmen soll — der Operator bestätigt und dispatcht. Der Audit ist gegenüber jedem Portfolio-Mitglied-Repository strikt read-only; er öffnet kein Issue, merged keinen PR, löscht keinen Branch, löst keinen Kommentar auf. Die Grenze spiegelt die read-only-Haltung, die `portfolio-management` §Nicht-Ziele etabliert: der Audit identifiziert nur, die Konsolidierungs-PR ist menschengetriebene Folgearbeit.

Leser: (1) Maintainer von `nolte/*`-Repositories — die entscheiden, welcher dispatchte Spezialist gegen welches Finding läuft; (2) der Claude-Code-Skill, der den periodischen In-Flight-Audit ausführt — der diese Spec als Autoring-Vertrag konsumiert; (3) Downstream-Leser des gerenderten Findings-Reports — einschließlich des Operators beim nächsten Audit-Lauf und jedes Lesers, der einen Spezialisten-Dispatch zurück zu seinem Trigger verfolgt.

## Ziele

- Jedes offene Issue, jeder Pull Request, jeder Branch-ohne-aktiven-PR, jeder ungelöste Review-Kommentar und jede GitHub-Discussion über das `nolte/*`-Portfolio-Mitglied-Set ist in einem einzigen periodischen Audit beobachtbar, sodass festgefahrene Arbeit nicht innerhalb einer Per-Repository-Sicht verschwinden kann.
- Jedes Finding trägt einen empfohlenen Spezialisten (Skill oder Agent aus dem `nolte-shared`-Plugin) und eine empfohlene Ein-Satz-Aktion, sodass der Audit-Report dispatch-fertig statt analytisch ist.
- Priorisierung ist explizit und nachvollziehbar: Jedes Finding hat einen Schweregrad, abgeleitet aus einer dokumentierten Matrix (Sicherheitsrelevanz × Release-Blockade × Alters-Multiplikator × Cross-Repository-Blockade), nicht aus dem Bauchgefühl des Operators zum Lese-Zeitpunkt.
- Der Audit ist strikt read-only: Er öffnet keinen PR, schließt kein Issue, löscht keinen Branch, löst keinen Review-Kommentar, schließt keine Discussion. Der Operator (oder ein nachgelagerter Remediation-Skill) handelt auf Basis des Reports.
- Der Audit integriert sich in `continuous-improvement` als anerkannte Finding-Quelle, sodass In-Flight-Triage denselben Spezialisten-Dispatch-Loop speist wie Drift-, Workflow-Health- und Vocabulary-Findings.
- Der Audit verwendet den Mechanismus zur Portfolio-Mitglied-Set-Auflösung aus `portfolio-management` wieder, statt ihn neu abzuleiten, sodass das Hinzufügen oder Entfernen eines Repositorys aus dem Portfolio die In-Flight-Inspektion automatisch erweitert oder verkleinert.
- Lücken im Spezialisten-Roster (eine wiederkehrende Finding-Klasse ohne passenden Skill oder Agent) werden aus demselben Audit sichtbar und spiegeln, wie `continuous-improvement` Spezialisten-Lücken aus bestehenden Audit-Quellen aufdeckt.

## Nicht-Ziele

- Zu definieren, wie einzelne Issues, PRs, Branches, Review-Kommentare oder Discussions *bearbeitet* werden — `pull-request-workflow`, `branching-model`, `feature-decompose`, `pull-request-merge` und die diversen Per-Repository-Specs bleiben für die Remediation-Seite autoritativ.
- Automatische Remediation. Der Audit meldet; der Operator dispatcht. Diese Spec bleibt bewusst einen Schritt vor Fire-and-Forget-Automatisierung stehen und entspricht damit der read-only-Grenze, die `portfolio-management` §Nicht-Ziele für den parallelen Capability-Audit etabliert.
- Per-Repository-CI-Failure-Triage — `workflow-health` bleibt autoritativ für rote Workflow-Läufe in einem einzelnen Repository. Der In-Flight-Audit beobachtet, dass die Required-Checks eines PR rot sind, und empfiehlt `workflow-health-triage`; er dupliziert die Per-Repo-Triage-Mechanik nicht.
- Routing bereits klassifizierter Findings in Spezialisten-Arbeit — `continuous-improvement` bleibt autoritativ, sobald ein Finding existiert. Diese Spec ist eine weitere vorgelagerte Finding-Quelle, die in diesen Loop einspeist, kein konkurrierender Router.
- Capability-Allokation, Duplikat-Erkennung über Repositories hinweg oder irgendeine Frage darüber, *welcher Code wo lebt* — `portfolio-management` ist autoritativ für die statische Portfolio-Oberfläche.
- Issue-Template-Authoring, PR-Template-Authoring oder irgendeine Meinung über den *Inhalt* eines Issues / PRs / einer Discussion — `github-issue-templates`, `pull-request-workflow` und eine eventuelle zukünftige Discussion-Template-Spec sind autoritativ für die Inhaltsform.
- Synchrones, Echtzeit-Monitoring — diese Spec beschreibt einen periodischen Audit (quartalsweise per Default, on-demand immer), keinen Notification-Stream und kein Dashboard.
- Governance darüber, wer welchen Spezialisten dispatchen darf — Operator-Autorität wird vorausgesetzt; diese Spec produziert die Empfehlung, die bestehenden `pull-request-workflow`- und `branching-model`-Specs gatekeepen die resultierende Arbeit.

## Anforderungen

### Portfolio-Scope

- **MUST** den In-Flight-Portfolio-Scope als exakt das Set von Portfolio-Mitglied-Repositories behandeln, das durch `spec/portfolio/portfolio-management/` §Portfolio-Scope zum Zeitpunkt des Audit-Laufs definiert ist. Diese Spec redefiniert Portfolio-Mitgliedschaft nicht.
- **MUST** denselben Opt-Out-Marker (`portfolio: excluded` am Anfang von `CLAUDE.md`) ehren, den `portfolio-management` ehrt; opt-out-markierte Repositories erscheinen nicht im In-Flight-Audit.
- **MAY** zusätzlich einen Per-Datenquelle-Opt-Out über einen Inline-Marker `inflight: skip-<source>` in der `CLAUDE.md` des Repositorys unterstützen (zum Beispiel `inflight: skip-discussions`), wenn ein Repository eine Datenquelle legitim nicht nutzt. Der Marker wird als `Info`-stufige Notiz im Report festgehalten, sodass die Auslassung inspizierbar bleibt.
- **MUST NOT** Repositories außerhalb des aufgelösten Portfolio-Mitglied-Sets scannen, auch nicht, wenn der Operator beim Aufruf explizit ein `nolte/<other>`-Repository benennt. Scope-Erweiterung passiert durch Adoption von `portfolio-management`, niemals durch ad-hoc-Inklusion.

### Datenquellen

- **MUST** bei jedem Audit-Lauf die vier Primärdatenquellen aus jedem in-scope Portfolio-Mitglied-Repository erheben:
  - **Offene Issues** — jedes Issue mit `state: open`, das kein ausschließendes Label (`triage-done`, `wontfix`, `parking-lot`) trägt.
  - **Offene Pull Requests** — jeder PR mit `state: open`, einschließlich Drafts.
  - **Branches ohne aktiven PR** — jeder Branch auf dem Remote, der keinen offenen PR in Richtung `develop` hat und nicht der Default-Branch ist.
  - **Ungelöste Review-Kommentare und GitHub-Discussions** — Review-Threads auf offenen PRs mit `resolved: false`, plus offene Discussions ohne Maintainer-Antwort innerhalb des letzten Triage-Fensters.
- **MUST** über read-only-`gh api`-Aufrufe erheben (oder die Äquivalente `gh issue list`, `gh pr list`, `gh api repos/.../branches`, `gh api graphql` für Discussions). Der Audit ruft niemals eine mutierende GitHub-API-Operation auf.
- **SHOULD** die Per-Repository-Erhebung parallelisieren, soweit möglich, um innerhalb der GitHub-API-Rate-Limits zu bleiben; ein Fan-out über einen read-only Agent (analog zu `portfolio-manifest-collector`) ist die empfohlene Implementierungsform.
- **MUST** einen Per-Finding-Identifier der Form `<repo>/<source>/<id>` persistieren (zum Beispiel `claude-shared/issue/142`, `vale-style/branch/feat-decompound-fix`), sodass dasselbe Finding über Re-Runs adressierbar bleibt und vorherige Findings gegen den vorigen Report korreliert werden können.
- **MUST NOT** private Repositories, archivierte Repositories oder Forks von Upstream-Projekten in die Erhebung aufnehmen. Die Portfolio-Mitglied-Set-Auflösung aus `portfolio-management` filtert diese bereits aus; der In-Flight-Audit erbt denselben Filter. HINWEIS: Ein echt verwaister offener PR in einem archivierten Repo wird einmal über den Historical-Capabilities-Pfad von `portfolio-management` ausgewiesen, nicht durch erneute Aufnahme des Repos in den In-Flight-Scan.
- **MUST NOT** die Ungelöster-Review-Kommentar-Quelle auf Threads geschlossener PRs ausdehnen; die Quelle ist auf Review-Threads *offener* PRs beschränkt, da die Threads eines geschlossenen PR keinen Merge mehr blockieren können. Legitime Folgearbeiten, die auf einem geschlossenen PR zurückbleiben, werden als frisches Issue über `feature-decompose` erfasst, nicht durch eine Erweiterung dieser Datenquelle.

### Stagnations-Schwellen

- **MUST** die folgenden Default-Schwellen anwenden, wenn entschieden wird, ob ein Item *festgefahren* ist und im Report auftaucht:
  - **Issue**: länger als 30 Tage offen ohne Prioritäts-Label, ohne Assignee und ohne Maintainer-Kommentar in den letzten 30 Tagen.
  - **Pull Request**: länger als 7 Tage offen mit roten Required-Checks, ODER länger als 14 Tage als Draft, ODER länger als 14 Tage ohne Reviewer-Aktivität, ODER Konflikte gegen `develop` tragend.
  - **Branch ohne aktiven PR**: letzter Push älter als 30 Tage UND kein offener PR in Richtung `develop` UND nicht der Default-Branch.
  - **Ungelöster Review-Kommentar**: Thread älter als 7 Tage ohne Maintainer-Antwort.
  - **Discussion**: länger als 30 Tage offen ohne Maintainer-Antwort.
- **MAY** die Default-Schwellen pro Repository über eine `project/inflight.yml`-Konfigurationsdatei im Repository-Root überschreiben; Overrides **MUST** im gerenderten Report inspizierbar sein (der Report hält sowohl den Default als auch den Per-Repo-Override fest), sodass der Operator Abweichungen vom Portfolio-Baseline sieht.
- **MUST NOT** ein Item, das die Schwelle nicht überschritten hat, als Finding klassifizieren. Vor-Schwell-Items werden vom Report ausgeschlossen, um das Signal-zu-Rausch-Verhältnis hoch zu halten; einen Audit kurz nach einer Maintainer-Antwort auf ein Issue auszuführen, sollte dieses Issue nicht ausweisen.
- **MUST** einen PR, der Konflikte gegen `develop` trägt, unabhängig vom Alter als `Warning`-Finding klassifizieren — für den Konflikt-Treiber greift keine Stagnations-Schwelle, weil ein ungelöster Konflikt den Merge bereits ohne weiteres Verstreichen von Zeit blockiert. Andere Dimensionen desselben PR (Alter, Reviewer-Aktivität, rote Checks) dürfen weitere Findings mit ihren eigenen Schwellen produzieren.
- **SHOULD** die Schwelle als Untergrenze, nicht als absolute Grenze behandeln: Ein `Critical`-Finding darf ein Item ausweisen, das die Stagnations-Schwelle noch nicht überschritten hat, wenn eine andere Matrix-Achse (Sicherheitsrelevanz, Release-Blockade) es verlangt.

### Klassifikation und Priorisierung

- **MUST** jedes Finding in einen der vier kanonischen Schweregrade aus `spec/claude/review-plan/` §Severity-Skala klassifizieren, abgeleitet aus einer Matrix mit vier Achsen, die im gerenderten Report wortgleich genannt werden: `security_relevance`, `release_blocking`, `age_multiplier`, `cross_repo_blocking`.
  - `Critical` — sicherheitsrelevant (CVE in Abhängigkeiten, Supply-Chain-Advisory, Leaked-Credential-Indikator) ODER release-blockierend (gemäß der `release_blocking`-Detection-MUST weiter unten: PR trägt ein Label `release-blocker` ODER der PR-Head-SHA taucht in einem offenen `release-drafter`-Draft auf) ODER cross-portfolio-blockierend (gemäß der `cross_repo_blocking`-Detection-MUST weiter unten: das `project/roadmap.md` oder eine `project/sprints/*.md`-Datei eines anderen Portfolio-Mitglieds referenziert das Finding).
  - `Warning` — über das 2-fache der Schwelle festgefahren, ODER ein Nicht-Release-Sprint-Feature blockierend, ODER ein PR mit Konflikten gegen `develop`.
  - `Suggestion` — über das 1-fache, aber noch nicht das 2-fache der Schwelle festgefahren und nicht blockierend, ODER ein Branch-ohne-PR älter als 30 Tage, ODER ein ungelöster Review-Kommentar-Thread älter als 7 Tage auf einem nicht-blockierenden PR.
  - `Info` — eine Beobachtung, die festzuhalten lohnt, aber nicht handlungsfordernd ist (Per-Quelle-Opt-Out-Marker, ein kürzlich festgefahrenes Item noch innerhalb des Rausch-Fensters, ein seit dem vorigen Audit geschlossenes Item).
- **MUST** die Matrix-Achsen-Eingabewerte, die zur Klassifikation geführt haben (z. B. `security_relevance: false, release_blocking: true, age_multiplier: 3×, cross_repo_blocking: false`), in jeder Finding-Zeile festhalten, sodass der Operator die Klassifikation ohne erneuten Audit-Lauf nachvollziehen kann.
- **MUST** `release_blocking: true` für ein PR-Finding erkennen, wenn eines dieser Signale vorliegt: (a) der PR trägt ein Label `release-blocker` (case-insensitive), ODER (b) der PR-Head-SHA taucht in einem offenen `release-drafter`-Draft desselben Repositorys auf (erkennbar via `gh api repos/<repo>/releases?per_page=…` gefiltert auf `draft: true`). Repositories ohne konfiguriertes `release-drafter` stützen sich allein auf das Label-Signal; weitere Signale (Milestone-Match, Branch-Namens-Pattern) **MAY** vom implementierenden Skill ergänzt werden, aber die Label- und `release-drafter`-Draft-Membership-Prüfungen sind die kanonische Baseline.
- **MUST** `cross_repo_blocking: true` für ein Finding erkennen, wenn das `project/roadmap.md` oder ein beliebiges `project/sprints/*.md` eines anderen Portfolio-Mitglied-Repositorys den GitHub-Identifier des Findings entweder als Kurz-Cross-Reference (`nolte/<repo>#<number>`) oder als vollständige GitHub-Issue-/PR-URL (`https://github.com/nolte/<repo>/(issues|pull)/<number>`) referenziert. Die Erkennung ist ein read-only Text-Scan gegen den Source-Tree des referenzierenden Repositorys zum Audit-Snapshot; keine Inferenz, kein Fuzzy-Matching.
- **SHOULD** den höheren Schweregrad bevorzugen, wenn ein Item mehrere Zeilen erfüllt; das entspricht der kanonischen Severity-Ordnung von `spec/claude/review-plan/`.
- **MUST NOT** Schweregrade jenseits der kanonischen vier erfinden. `BLOCKER`, `HIGH`, `MEDIUM` oder ALL-CAPS-Varianten sind per `spec/claude/review-plan/` §Severity-Skala verboten und stellen selbst eine `review-plan`-Verletzung dar, wenn sie im Findings-Report auftauchen.

### Spezialisten-Empfehlung

- **MUST** an jedes Finding einen empfohlenen Spezialisten (Skill- oder Agent-Identifier aus dem `nolte-shared`-Plugin) anhängen, wann immer ein passender Spezialist existiert. Spezialisten-Matching folgt dem bestehenden Muster aus `spec/project/continuous-improvement/` §Spezialisten-Dispatch.
- **MUST** den passenden Skill oder Agent wortgleich über seinen Slug benennen (zum Beispiel `dependency-audit`, `workflow-health-triage`, `feature-decompose`, `pull-request-merge`, `vocab-drift-audit`), sodass der Operator dispatchen kann, ohne das Match aus der Beschreibung neu abzuleiten.
- **MUST**, wenn der einzige Treiber eines PR-Findings ein roter Required-Check ist, `workflow-health-triage` als empfohlenen Spezialisten benennen, und **MUST NOT** denselben Roter-Check-Treiber an einen anderen Spezialisten routen. Andere Dimensionen desselben PR (Stale-Draft, ungelöste Review-Kommentare, Konflikte) **MAY** zusätzliche Findings mit eigenen empfohlenen Spezialisten produzieren; die Roter-Check-Exklusivität gilt pro Treiber, nicht pro PR.
- **MUST**, wenn die Aktion des empfohlenen Spezialisten einen konkreten offenen PR, Branch oder ein Issue adressiert (zum Beispiel `pull-request-merge`, `pull-request-create`, `workflow-health-triage`), den Slash-Befehl wortgleich plus den Target-Identifier in die empfohlene-Aktion-Zeile des Findings aufnehmen (zum Beispiel `/nolte-shared:pull-request-merge gegen PR #142`), sodass der Operator per Copy-Paste dispatchen kann, ohne die Aufruf-Oberfläche aus der Skill-Beschreibung neu abzuleiten.
- **MUST** ein `Suggestion`-stufiges Finding festhalten, dass das Spezialisten-Roster eine Lücke hat, wenn kein passender Spezialist für ein Finding existiert. Wiederkehrende Lücken (dieselbe Finding-Klasse drei- oder mehrmals portfolio-weit gemäß `spec/project/continuous-improvement/` §Portfolio-Lücken-Schluss) eskalieren die Empfehlung zu „neuen Spezialisten autorieren". Wiederkehr wird gezählt, indem das jüngste vorherige `.audits/portfolio-inflight/<YYYY-MM-DD>.md`-Artefakt (sofern vorhanden) gelesen und Gap-Findings über ihren `<data-source>/<finding-class-token>`-Tag gematcht werden, wobei `<finding-class-token>` der nicht-gematchte Spezialisten-Slug ist oder, wenn kein Slug greift, ein stabiles snake-case-Label, das der Audit zum Zeitpunkt der Gap-Erkennung vergibt; in Abwesenheit eines vorherigen Artefakts wird Wiederkehr nur innerhalb des aktuellen Laufs gezählt.
- **MAY** einen Generalisten-Fallback nennen, wenn kein Spezialist existiert und die Lücke die 3-Wiederholungs-Schwelle noch nicht erreicht hat. Der Generalisten-Fallback wird explizit markiert, sodass die Audit-Historie unterversorgte Finding-Klassen sichtbar macht.
- **MUST NOT** den Spezialisten selbst dispatchen. Der Audit gibt die Empfehlung ab; der Operator bestätigt und dispatcht über die normale Skill-Aufruf-Oberfläche.

### Audit-Operation

- **MUST** als dedizierter Skill `portfolio-inflight-triage` im `nolte-shared`-Plugin implementiert sein (analog zu `portfolio-audit`, `dependency-audit`, `workflow-health-triage`), autoriert gemäß `spec/claude/skill-management/` und reviewt gemäß `spec/claude/skill-review/`.
- **MUST** vom Operator on-demand aufrufbar sein und **SHOULD** mindestens quartalsweise laufen. On-demand- und Cadence-Trigger produzieren dieselbe Artefakt-Form.
- **MUST** einen read-only Spezialisten-Agent `portfolio-inflight-collector` für die Per-Repository-Datenquellen-Erhebung dispatchen, gemäß derselben Kontextfenster-Schutz-Begründung, die `portfolio-audit` für die Manifest-Erhebung anwendet. Der Collector liefert eine vor-reduzierte strukturierte Zusammenfassung; rohe Issue-/PR-/Branch-/Discussion-Bodies gelangen nie in die orchestrierende Konversation.
- **MUST** den Mechanismus zur Portfolio-Mitglied-Set-Auflösung aus `portfolio-management` (den bestehenden `portfolio-manifest-collector`-Agent oder seinen verallgemeinerten Nachfolger) wiederverwenden, statt Portfolio-Scoping neu zu implementieren.
- **MUST NOT** als Claude-Agent implementiert sein. Der Audit ist eine mehrstufige Orchestrierung mit mittendrin liegender User-Bestätigung über Stagnations-Schwellen-Overrides und Spezialisten-Roster-Lücken-Eskalationen; das ist die Skill-Seite der `spec/claude/skill-vs-agent/`-Entscheidungsregel.
- **SHOULD**, wenn on-demand innerhalb eines Nicht-`claude-shared`-Repositorys aufgerufen, stoppen und den Nutzer für den Audit nach `claude-shared` routen — der Findings-Report-Schreibpfad lebt dort, analog zur Erkennungsregel von `portfolio-audit`.

### Findings-Report-Form

- **MUST** das Audit-Artefakt nach `.audits/portfolio-inflight/<YYYY-MM-DD>.md` im `claude-shared`-Repository schreiben — das Repository, das auch `.audits/portfolio/` gemäß `portfolio-management` §Portfolio-Audit beherbergt.
- **MUST** der `spec/claude/review-plan/`-Artefakt-Form entsprechen, einschließlich der vier Pflicht-Abschnitte (`## Scope`, `## Summary`, `## Findings`, `## Processing log`) und des kanonischen vierstufigen Schweregrad-Vokabulars (`Critical` / `Warning` / `Suggestion` / `Info`) gemäß `review-plan` §Severity-Skala.
- **MUST** ein Finding, dessen zugrundeliegendes Item seit dem vorigen Audit geschlossen wurde, als `Info`-stufigen „seit vorigem Audit geschlossen"-Eintrag unter `## Findings` (kein neuer Abschnitt) ausweisen und dabei seinen ursprünglichen `<repo>/<source>/<id>`-Identifier erhalten. Ein separater `## Resolved since previous audit`-Abschnitt ist verboten, weil er einen fünften Top-Level-Abschnitt hinzufügen und damit die oben geforderte Vier-Pflicht-Abschnitt-Konformität zu `review-plan` brechen würde.
- **MUST** den `## Findings`-Abschnitt zuerst nach Schweregrad (Critical → Warning → Suggestion → Info) und innerhalb jedes Schweregrades nach Portfolio-Mitglied-Repository-Name (alphabetisch) gliedern. Innerhalb eines Per-Repository-Blocks nach Datenquelle ordnen (Issues → PRs → Branches → Review-Kommentare → Discussions) und innerhalb einer Datenquelle nach aufsteigendem Finding-Identifier.
- **MUST** pro Finding mindestens enthalten: den Finding-Identifier (`<repo>/<source>/<id>`), das Datenquellen-Label, das Stagnations-Maß (Tage offen, Tage seit letzter Aktivität), den empfohlenen Spezialisten (oder „kein Spezialist passt" mit Roster-Lücken-Hinweis), die empfohlene Aktion als einzelnen Satz und die Schweregrad-Klassifikation mit den Matrix-Achsen-Eingabewerten, die zu ihr geführt haben. Jede Finding-Zeile trägt ein in eckigen Klammern stehendes Präfix mit Zitat der originatenden Spec-Regel und folgt damit der `portfolio-audit`-Konvention (z. B. `[portfolio-inflight-management §Klassifikation und Priorisierung]`).
- **SHOULD** eine eröffnende `## Summary`-Tabelle mit Per-Schweregrad-Counts und Per-Repository-Counts enthalten, sodass der Operator die Form des Portfolios auf einen Blick erhält, bevor er einzelne Findings liest.
- **MAY** einen „Trend vs. vorigem Audit"-Anhang enthalten, der Finding-Counts gegen den vorigen `.audits/portfolio-inflight/<YYYY-MM-DD>.md`-Eintrag vergleicht; der Trend-Anhang ist rein informativ und beeinflusst die Schweregrad-Klassifikation nicht.
- **MUST NOT** rohe Issue-/PR-/Branch-/Discussion-Bodies im Findings-Report enthalten. Der Audit reduziert jedes Finding auf eine strukturierte Zusammenfassung plus den empfohlenen Spezialisten und die Aktion; wortgetreue Source-Bodies bleiben auf GitHub und sind über den Finding-Identifier erreichbar.
- **MUST NOT** einen Per-Repository-Subreport schreiben; der Audit schreibt genau ein aggregiertes Artefakt. Per-Repository-Sichten sind, falls je nötig, ein Docs-Rendering-Belang (analog zu `portfolio-management` §Documentation rendering), keine zusätzlichen Audit-Dateien — der `## Findings`-Abschnitt ist bereits innerhalb jedes Schweregrades nach Repository gegliedert, sodass ein Maintainer seinen Repo-Ausschnitt innerhalb des einzelnen Artefakts findet.

### Integration mit continuous-improvement

- **MUST** in zukünftigen Revisionen von `spec/project/continuous-improvement/` §„Finding sources in scope" als anerkannte Audit-Quelle gelistet sein. In-Flight-Findings fließen durch denselben Triage-und-Spezialisten-Dispatch-Loop wie `spec-drift-audit`-, `workflow-health`- und `vocab-drift-audit`-Findings.
- **MUST** jedes Finding mit dem Zitat der originatenden Spec (z. B. `[portfolio-inflight-management §Klassifikation und Priorisierung]`) im in eckigen Klammern stehenden Präfix der Report-Zeile identifizieren, analog zu den `portfolio-audit`- und `review-plan`-Konventionen.
- **SHOULD** ein Tracking-Issue im betroffenen Portfolio-Mitglied-Repository für jedes `Critical`-Finding öffnen, gegen das der Operator dispatcht. Der Body des Tracking-Issues zitiert den Audit-Finding-Identifier, sodass der Loop von beiden Seiten schließbar ist, analog zu `portfolio-management` §Gap-Analyse.
- **MAY** in einem folgenden Audit-Lauf ein `Critical`-Finding aus dem vorigen Audit, das offen bleibt, als `Critical`-Persisted-Eintrag mit erhaltenem Original-Identifier ausweisen, sodass die Persistenz festgefahrener Arbeit über Audits hinweg sichtbar wird, ohne die Audit-Historie diff-walking zu müssen.

### Operator-Autorität

- **MUST NOT** irgendein GitHub-Issue schließen, irgendeinen PR mergen, irgendeinen Branch löschen, irgendeinen Review-Kommentar als gelöst markieren oder irgendeine Discussion schließen. Der Audit ist strikt beobachtend.
- **MUST NOT** irgendeine Datei in irgendeinem Portfolio-Mitglied-Repository außer `claude-shared` modifizieren (wo der Report selbst lebt). Der Audit schreibt genau einen Artefakt-Pfad: `.audits/portfolio-inflight/<YYYY-MM-DD>.md`.
- **MUST NOT** `gh api` mit `-X POST`, `-X PATCH` oder `-X DELETE` gegen ein Portfolio-Mitglied-Repository aufrufen. Der Audit-und-Collector-Pfad nutzt ausschließlich read-only API-Calls, analog zur Hard-Rule von `portfolio-manifest-collector`.
- **MUST**, wenn der Operator versucht, einen Spezialisten direkt aus der Audit-Konversation zu dispatchen, den Dispatch durch die bestehende Skill-Aufruf-Oberfläche routen (der Operator tippt den Slash-Befehl), nicht durch eine In-Skill-Auto-Invokation. Das bewahrt die Grenze, dass jede Cross-Repository-Aktion in der Consumer-seitigen Konversation landet, nicht mitten im Audit.

## Akzeptanzkriterien

- [ ] Eine kanonische Spec `spec/portfolio/portfolio-inflight-management/en.md` und ihre Übersetzung `de.md` existieren und sind strukturell synchronisiert (gleiche Headings, gleiche Anforderungsanzahl, gleiche Akzeptanzkriterien-Checkboxen).
- [ ] Der Skill `portfolio-inflight-triage` existiert unter `skills/portfolio-inflight-triage/SKILL.md` im `nolte-shared`-Plugin, entspricht `spec/claude/skill-management/` und wurde mindestens einmal gegen `spec/claude/skill-review/` reviewt mit dem resultierenden Plan geschlossen.
- [ ] Der Agent `portfolio-inflight-collector` existiert unter `agents/portfolio-inflight-collector.md`, deklariert ausschließlich read-only Tools (`Read`, `Bash`, `Glob`, `Grep`) und wurde mindestens einmal gegen `spec/claude/agent-review/` reviewt mit dem resultierenden Plan geschlossen.
- [ ] Mindestens ein Audit-Findings-Report existiert unter `.audits/portfolio-inflight/<YYYY-MM-DD>.md` im `claude-shared`-Repository und entspricht der `review-plan`-Vier-Abschnitts-Struktur und dem kanonischen Schweregrad-Vokabular.
- [ ] Jedes Finding im Report trägt: Identifier `<repo>/<source>/<id>`, Datenquellen-Label, Stagnations-Maß, empfohlenen Spezialisten (oder Roster-Lücken-Hinweis), Ein-Satz-Empfehlung der Aktion und Schweregrad-Klassifikation mit den vier Matrix-Achsen-Eingabewerten.
- [ ] Der Audit wertet `security_relevance` gegen mindestens eines der folgenden Signale aus: einen `dependency-audit`-CVE-Indikator, ein vom Lockfile des Repositorys referenziertes Supply-Chain-Advisory oder einen Secret-Scanning-Leaked-Credential-Alert; ein synthetischer Sicherheits-Trigger, der in den Audit eingespeist wird, produziert ein Finding mit `security_relevance: true`.
- [ ] Der Audit wertet `cross_repo_blocking` aus, indem er die `project/roadmap.md`- und `project/sprints/*.md`-Dateien jedes Portfolio-Mitglieds nach `nolte/<repo>#<number>`- oder vollständigen GitHub-URL-Referenzen auf den Identifier des Findings scannt; eine synthetische Cross-Reference produziert ein Finding mit `cross_repo_blocking: true`.
- [ ] `continuous-improvement` listet `portfolio-inflight-management` (oder den implementierenden Skill `portfolio-inflight-triage`) als anerkannte Audit-Quelle in seiner „Finding sources in scope"-Sektion.
- [ ] Der Audit gegen eine leere In-Flight-Oberfläche (null festgefahrene Items portfolio-weit) produziert einen gültigen Findings-Report mit null Findings unter jedem Schweregrad, statt gar keinen Report.
- [ ] Der Audit dispatcht den `portfolio-inflight-collector`-Agent für die Per-Repository-Datenerhebung; die Konversation des orchestrierenden Skills erhält niemals rohe Issue-/PR-/Branch-/Discussion-Bodies.
- [ ] Der Audit ruft niemals einen mutierenden `gh api`-Call auf; ein Static-Analysis-Sweep des Skill- und Agent-Quelltexts bestätigt, dass nur read-only Kommandos enthalten sind.
- [ ] Stagnations-Schwellen-Overrides, die in einer `project/inflight.yml`-Datei eines Portfolio-Mitglied-Repositorys deklariert sind, werden vom Audit aufgenommen und im gerenderten Report explizit vermerkt (sowohl Default als auch Override werden gezeigt).
- [ ] Jede Finding-Zeile trägt ein Zitat in eckigen Klammern auf die Spec (z. B. `[portfolio-inflight-management §...]`), sodass ein nachgelagerter Leser sie auf die originatende Anforderung zurückverfolgen kann.

## Offene Fragen

- Riskiert der Audit für Repositories mit sehr hohem Open-Issue-Count (zum Beispiel weil ein Maintainer Issues als persönliche Todo-Liste nutzt) unverwaltbare Findings-Reports? Eine Per-Repository-Finding-Obergrenze mit einem `Info`-stufigen „siehe verbleibende N ähnliche Findings"-Footer könnte nötig sein, um den Report navigierbar zu halten.
- Sollte die GitHub-Discussions-Datenquelle auch Discussions außerhalb der Per-Repository-Oberfläche einschließen — zum Beispiel portfolio-weite Ankündigungs- oder Feedback-Kanäle? Der aktuelle Scope ist ausschließlich per-Repository; eine Ausweitung würde eine neue Source-of-Truth für „portfolio-weite Discussion-Orte" erfordern.
