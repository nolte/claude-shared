# Image Boot Verification

Status: draft
Portfolio-Scope: local

## Context

An image definition can pass every static check in `spec/project/linux-image-best-practices/` and still not boot: a missing driver in the initial RAM disk, a partition the boot loader can't find, a health unit that never starts, or a rollback path that's wired but never fires. The only proof that an image boots is to boot it. This spec governs that proof: starting a built image in a virtual machine with real firmware (UEFI or U-Boot), waiting for the image's own health report, asserting what it reports, and, for an image updated in the field, exercising the update-and-rollback path.

Boot verification is a **realisation of the end-to-end tier** of `spec/project/test-pyramid-foundation/`, not a seventh tier. The foundation's functional-tier taxonomy is closed, and booting a whole operating system and asserting its observable state is exactly what that tier describes. The foundation defines it as the tier that "drives the real user-facing surface of a running system and asserts on observable behaviour" and for an appliance that surface is the booted system. The requirement record `project/requirements/nolte-linux-plugin.md` holds this placement decision (its item R4). The spec fills the foundation's per-tier invariant shape in §A (purpose and scope boundary), §B (isolation and doubles), §C (speed and determinism), §D (execution placement), §E (traceability), §K (anti-patterns), and §L (reference profile). §F–§J add what's specific to images: the readiness and state contract, the protocol, host tooling and verdicts, the update scenarios, and timeouts.

The content comes from a research pass on 2026-11-14 across the systemd documentation (the VM interface, Automatic Boot Assessment, `systemd-vmspawn`), the EDK II OVMF documentation, libvirt's Secure Boot notes, and the boot smoke tests that Debian and OpenEmbedded run against their own images. A second pass on 2026-11-15 settled the switch transport for U-Boot across the QEMU, Linux kernel, U-Boot, and systemd sources.

**Boundaries:** `spec/project/linux-image-best-practices/` owns what an image must contain and declare, including the image declaration and the health report line this spec reads. This spec only boots the image and checks what it reports at runtime. Against the neighbouring tiers: the static-analysis tier of an image is the `linux-image-audit` skill against that spec, which never boots anything; a single component's integration with one real collaborator has no image-specific tier and stays with the component's own tests. `spec/project/e2e-test-automation/` owns E2E tests of an application's user interface. Its browser-specific rules (page objects, screenshots, the Selenium profile, the opt-in test protocol) don't apply here, while its determinism and traceability rules apply through the foundation, which owns them. When an appliance serves a web UI, its UI tests run against the booted VM under that spec, not this one. `spec/project/test-pyramid-foundation/` owns the tier model, the test-double vocabulary, arrangement fidelity, and the CI gating model this spec applies.

**Readers:** the authors of the `image-boot-verify` skill; maintainers of image-building repositories who wire a boot check into their pipeline; reviewers judging whether a boot verdict is trustworthy.

## Goals

- A built image is proven to boot to a healthy state the image itself reports, not merely to start a kernel
- A run that couldn't verify anything reports exactly that, and is never mistaken for a pass
- An image updated in the field is proven to roll back on its own when an update comes up unhealthy
- An image updated in the field is proven at runtime to refuse a version that isn't newer and a payload signed with a key it doesn't trust
- Every run leaves a protocol that names exactly which image, firmware, and host it ran on, so a verdict can be reproduced and audited
- Boot checks stay deterministic: condition-based waits with bounded timeouts, never fixed delays

## Non-Goals

- Static review of the image definition, owned by `spec/project/linux-image-best-practices/` and the `linux-image-audit` skill
- Tests of an application's user interface running on the appliance, owned by `spec/project/e2e-test-automation/`
- Booting on physical hardware, hardware-in-the-loop rigs, and board-specific bring-up. A verdict from a virtual machine, under UEFI or U-Boot, doesn't establish that the image boots on physical hardware, such as a Raspberry Pi that runs its own firmware chain before any boot loader of the image
- Images whose firmware is neither UEFI nor U-Boot, such as BIOS (§A)
- Performance benchmarking of boot time; a run records durations, but this spec sets no boot-time target
- Fleet-level update rollout and the update server side

## Requirements

### A. Purpose and scope boundary

- A boot verification **MUST** assert that the image reaches its healthy state as its own health definition reports it: the image's health report line (`spec/project/linux-image-best-practices/` §A) says `status=healthy`, and the reported system state is acceptable under §F
- A boot verification **MUST NOT** assert application business behaviour. A service's own functional behaviour belongs to that service's test tiers; this spec asserts only what the image's health definition reports
- A boot verification resolves the properties of the built image that a static audit can't decide (`spec/project/linux-image-best-practices/` §J) through the scenarios of §I: the rollback scenario for the update behaviour; the downgrade, signature-rejection, commit-boundary, and interrupted-update scenarios for the update-security properties of `spec/project/linux-image-best-practices/` §F; and the identity scenario for a machine ID baked into the image
- Boot verification covers images whose firmware is UEFI or U-Boot, each booted under a hypervisor's virtual machine. The declaration's `image.firmware` (schema version 1.1 and later, `schemas/image-declaration-v1.2.schema.yaml` being the newest) names the firmware type, and a declaration of schema version 1.0, which has no such field, counts as `uefi`. An image that declares `bios` or `other` is out of scope: every scenario is `not-run` with the reason that its firmware is out of scope, and `spec/project/linux-image-best-practices/` §J reports the results those scenarios would resolve as `spec-gap: boot verification out of scope for <firmware>` instead of blocking
- A run boots the guest architecture the declaration's `image.architectures` names; when it names several, the operator's input or the artifact selects one of them. For a declaration of schema version 1.0, the architecture comes from the artifact or an explicit input. When none of these yields it, every scenario is `not-run`
- A verdict is evidence for the image under the virtual machine's firmware and machine type only. It **MUST NOT** be presented as proof that the image boots on physical hardware, whose firmware chain the run doesn't exercise

### B. Isolation, test doubles, and arrangement fidelity

- The image under test, the boot loader, and the kernel **MUST** be the real build artifacts, booted unmodified. A run **MUST NOT** rebuild, patch, or re-sign the image to make it boot
- A run **MUST** boot from a disposable copy or a copy-on-write overlay of the image, so the artifact under test is never modified by its own boot
- A scenario **MUST NOT** modify the real artifact under test (N), the next-version artifact (N+1), or the previous-version artifact of §H: every scenario boots or serves them as given. The signature-rejection scenario serves test payloads produced separately from them (§I), never ones made by writing to the N+1 artifact
- A run **MUST** refuse an artifact that refers to another file, such as a qcow2 image with a backing file or an external data file, and record the affected scenarios `not-run`, because the reference would let the hypervisor read a host file or fetch a URL outside this isolation
- Each arrangement is classified in the vocabulary of `spec/project/test-pyramid-foundation/` §"Test-double taxonomy" and held to its §"Arrangement fidelity":
  - **Firmware**: real firmware of the declared type, not a double: UEFI firmware, or a U-Boot build for the hypervisor's machine type. When the declaration's `boot_chain.secure_boot` is `implemented`, the firmware **MUST** run with Secure Boot enabled and only the image's own public keys enrolled; enrolling a broader key set or disabling Secure Boot is a divergence the run **MUST NOT** make
  - **TPM**: a software TPM emulator **MAY** stand in for the hardware TPM; it's a fake. The protocol records that the TPM was emulated
  - **Update server**: a local source that serves an image version is a fake of the update server. It **MUST** serve real release artifacts, signed as they would be in production: the next version (N+1) in the rollback, positive, and interrupted-update scenarios, and the previous-version artifact in the downgrade scenario. The one exception is the signature-rejection scenario, whose source serves the test payloads of §I, one signed with a key the image doesn't trust and one unsigned, neither ever published
  - **Acceleration**: emulation instead of hardware virtualisation is a declared divergence in speed only; §H governs it
- A run **MUST** give the VM no route to an external network or to a host service other than the declared local-source endpoint. A scenario with an update source (rollback, positive, downgrade, signature-rejection, interrupted-update) reaches exactly one forwarded endpoint, the local source that serves that scenario's payload; a scenario without one (smoke, identity, commit-boundary) runs with no network device at all. Any other reachable endpoint is a collaborator the arrangement doesn't declare, so a verdict couldn't account for it
- Before each boot, the run **MUST** assert the network configuration it passes to the hypervisor: for a scenario with an update source, user-mode networking in restricted mode (`restrict=on` in the reference profile of §L) with exactly one forwarded endpoint, the declared one; for a scenario without one, no network device. A configuration that fails the assertion, such as one without the restriction or with a second forward, is rejected before boot, and the scenario is `not-run` (§H)

### C. Speed and determinism budget

- A single boot check is expected to take on the order of minutes. Every wait **MUST** be bounded by an explicit timeout from §J, and the run **MUST** record every timeout it used
- A run **MUST NOT** synchronise with fixed delays (`sleep`). It waits for a condition: the health report line, or the end of a bounded timeout [R3]
- A run **MUST NOT** retry a scenario silently. A retry is a new attempt, and the protocol records the attempt number. A scenario that fails and then passes on a retry **MUST** carry the `flaky` flag on its verdict, per `spec/project/test-pyramid-foundation/` §"Determinism and flakiness"

### D. Execution placement

- Boot verification **SHOULD** run in a dedicated stage or on a schedule (nightly, or before a release), not on every pull request, consistent with the slow-tier placement that `spec/project/test-pyramid-foundation/` §"CI gating model" sets. A repository **MAY** gate pull requests on it when its risk profile justifies the runtime
- Boot verification **MUST** be runnable locally by the same entry point the pipeline uses, so a red pipeline run can be reproduced on a developer machine

### E. Traceability

- Each boot scenario **MUST** name the requirement or TC-ID it verifies, as `spec/project/test-pyramid-foundation/` §"Traceability" requires. At minimum, the smoke scenario names the image's health definition, the rollback scenario the image's rollback requirement, and the identity scenario the image's identity requirement (`spec/project/linux-image-best-practices/` §D). The update-security scenarios name the §F requirement they verify: the downgrade scenario the refusal of a version that isn't newer, the signature-rejection scenario the payload signature, the commit-boundary scenario the failure switch's effect on a committed version, and the interrupted-update scenario the atomic update
- The protocol (§G) **MUST** carry those identifiers, so a report maps back to requirements without external bookkeeping

### F. Readiness and state assertions

- A run **MUST** capture the serial console of the VM to a file from power-on to shutdown, in every scenario [R2]
- A run **MUST** treat the image's health report line (`spec/project/linux-image-best-practices/` §A) on the serial console as the readiness condition and the single source for the assertions below. Before matching, the run strips a trailing carriage return, other control characters, and terminal escape sequences from each captured line. A report is a normalised line that begins with `IMAGE-HEALTH-REPORT` followed by a space; a report broken up by interleaved console output doesn't count, so the image writes it as one write; a mention of that string anywhere else in a line, such as an echoed kernel command line, isn't a report. Per boot, the run waits for the first report until the readiness timeout of §J expires
- When the line reports `status=healthy`, the run **MUST** check two things. Every unit in `failed_units` is listed in the declaration's `health.tolerated_units`. And `system_state` is `starting` (the health definition still gates `boot-complete.target`), `running`, or `degraded`; the value `-` is accepted only when the declaration's `health.definition.kind` is `framework-hook`. `failed_units=-` means no unit failed. Anything else fails
- When the line reports `status=unhealthy`, or no report appears before the readiness timeout, the smoke scenario fails. A missing report is the image's defect, since `spec/project/linux-image-best-practices/` §A requires the line on a serial console
- A run **MUST** record the reported `image_id` and `image_version` and **MUST** check them against the declaration's `image.name` and the expected version the caller passed for the artifact (§H), so the protocol proves which image actually booted
- A run **MAY** use an out-of-band readiness channel offered by the hypervisor and the image (§L) for progress diagnostics. Such a channel **MUST NOT** replace the health report line as the basis of a verdict

### G. Protocol

- Every run **MUST** write a machine-readable protocol (`protocol.json`) and the captured serial log into one run directory. The default location is outside the tracked tree (git-ignored), like the E2E test protocol
- The protocol **MUST** contain: the version of the protocol format; the run timestamp; the overall verdict and the exit status that exposes it (§H); the host (operating system, kernel, architecture); each image artifact (the one under test, the next version for the scenarios that serve it, and the previous-version artifact for the downgrade scenario) with its digest and expected version; the signature-rejection scenario's two test payloads, each with its digest, the version it offers, and how it was produced, plus the identifier of the key the untrusted-key payload is signed with; the commit of the image definition; the image declaration it read; the firmware type, the firmware build, and whether Secure Boot was enabled; the guest architecture and where it came from (§A), the machine type, and whether the guest architecture differs from the host's; whether the TPM was emulated; the hypervisor and its version; the acceleration mode and, under emulation, the warning and the timeout factor; every timeout used; per scenario whether it's required, its verdict, `flaky` flag, attempt number, network isolation (no network, or the one forwarded endpoint, with the configuration asserted before boot), duration of each phase, and the health report lines observed; the image versions observed after each boot of the rollback scenario; for the downgrade, commit-boundary, and interrupted-update scenarios, the image version each of their reports named; for the downgrade and interrupted-update scenarios, the number of guest requests the local source recorded; for each payload variant of the signature-rejection scenario, its verdict, the image versions its reports named, the guest requests its local source recorded, and for a `not-run` or `not-producible` variant the reason; for the interrupted-update scenario, when the run reset the VM; the machine UUID and the `machine_id_app` value of each of the two boots of the identity scenario; for `not-run`, the missing tools or the failed precondition and an install hint; the requirement or TC-IDs covered; and the path of the serial log
- The protocol **MUST** be written for every verdict, including `not-run`. A field the run couldn't collect is written as `unavailable` with a reason, never omitted or guessed
- `schemas/image-boot-protocol-v1.2.schema.yaml` is normative for the protocol format. It extends version 1.1 by the downgrade, signature-rejection, commit-boundary, and interrupted-update scenarios (§I), their fields, and the timeouts §J adds for them. A run for an image updated in the field always plans the downgrade and signature-rejection scenarios, since a deselected one is recorded `not-run` and counts toward the overall verdict (§H), so such a run **MUST** write its protocol in version 1.2, as **MUST** any run that plans one of the four scenarios. Only a run for an image not updated in the field **MAY** write version 1.1; the shipped runner writes version 1.2 for every run. A run **MUST** write `schema_version` and **MUST** validate its protocol against the schema that version names before it hands the protocol on; a consumer **MUST** validate a protocol the same way before it uses it and **MUST** ignore one that fails. A consumer **MUST** still accept a protocol that names version `1.0` or `1.1` and validates against `schemas/image-boot-protocol-v1.0.schema.yaml` or `schemas/image-boot-protocol-v1.1.schema.yaml`. Such a protocol can't name the scenarios version 1.2 adds, so a consumer **MUST** treat each of them as absent, as it does a scenario that a version 1.2 protocol doesn't list: an absent scenario resolves nothing, and a requirement it would resolve stays `not-decidable` with cause `resolvable: <scenario>` (`spec/project/linux-image-best-practices/` §J), so an absence never reads as `pass`. The schema expresses the `unavailable` convention (an uncollected field holds `status: unavailable` and a non-empty `reason`, never `null`) and admits only consistent pairs of overall verdict and exit status. It also admits each scenario at most once, rejects a `pass` or `fail` scenario whose network isolation is `unavailable`, rejects a `pass` scenario that carries no report line, and requires the smoke, identity, and commit-boundary scenarios to run without a network device. For the four scenarios version 1.2 adds, it fixes the required flag that §H sets, admits their per-scenario fields only on them, rejects a `pass` of the downgrade or interrupted-update scenario, or a passing signature-rejection variant, whose local source recorded no request, derives a signature-rejection verdict from its variants as §I does, and enforces the positive controls of §I: a downgrade or signature-rejection `pass` needs a `pass` of the rollback or positive scenario in the same protocol, and a commit-boundary `pass` or `fail` needs a positive `pass`. A `fail` scenario may carry no report line: that's the missing report of §F, for example a readiness timeout. Rules that span several fields stay with the consumer, which **MUST** ignore a protocol that breaks one: the overall verdict is the worst verdict of the required scenarios the protocol lists, as §H defines it; a scenario with a forwarded endpoint names exactly the endpoint the run served that scenario's payload from, for the signature-rejection scenario both variants' payloads (§B); an identity `pass` records two different `machine_id_app` values; a `pass` or `fail` scenario records the commit of the image definition and the artifact it booted, not `unavailable`; an image whose firmware is out of scope, or the identity scenario under U-Boot, carries only `not-run` (§A, §I); a downgrade `pass`, or a passing signature-rejection variant, observed only N's expected version, and a downgrade `pass` or `fail`, or a signature-rejection variant that booted, records the payload it served, not `unavailable`; an interrupted-update `pass` ends on N's or N+1's expected version; and a commit-boundary `pass` observed only N+1's expected version

### H. Host tooling and verdicts

- A run takes as input the path of the image declaration, the artifact under test with its expected version and the commit of the image definition it was built from, and, for the rollback, positive, and interrupted-update scenarios, the next-version artifact with its expected version. For the downgrade scenario it takes the previous-version artifact: an artifact of the same image whose version is strictly older than N, such as the previous version N−1, with its expected version. A previous-version artifact whose version equals N's, or the artifact under test itself, makes the downgrade scenario `not-run` with the reason `previous-version artifact isn't older than N`, without booting, since an installation of the same version can't be told from a refusal. Versions compare as dotted numbers padded with zeros (`1.4` equals `1.4.0`); a version that isn't dotted-numeric equals N's only when it's identical, and whether it's older rests on the operator. For the signature-rejection scenario it takes the two test payloads of §I, each with the version it offers and how it was produced: the untrusted-key payload with the identifier of the key it's signed with, and the unsigned payload, or instead the reason the update framework's payload format admits no unsigned payload. The run records that commit in the protocol as given and never substitutes the working copy's current commit. A missing input is a failed precondition; a missing previous-version artifact or test payload makes only the scenario or variant that needs it `not-run`
- Before booting, a run **MUST** check every precondition: a firmware type in scope (§A) and the guest architecture (§A); the hypervisor for that architecture and the firmware of the declared type it selects: for `uefi`, UEFI firmware for the architecture and, when the declaration says `secure_boot: implemented`, firmware variables with the image's keys enrolled; for `u-boot`, a U-Boot build for the hypervisor's machine type and the architecture that the image's boot chain accepts unchanged, which for an image that implements Secure Boot trusts only the image's own keys; the TPM emulator, when the declaration says `measured_boot: implemented`; a valid image declaration; a readable image artifact; for the rollback and interrupted-update scenarios, the next-version artifact and a local source the guest can reach; for the downgrade scenario, the previous-version artifact, and for the signature-rejection scenario, its test payloads, each with a local source the guest can reach; for the commit-boundary scenario, a `pass` of the positive scenario in the same run and its kept disk state (§I); for the identity scenario, a hypervisor that can assign a machine UUID the guest reads, which isn't established for `u-boot`, so a U-Boot image's identity scenario is `not-run` until a real run confirms one; and, for every scenario, the network isolation of §B, asserted from the configuration. When isolation can't be established, the affected scenario is `not-run`; a run **MUST NOT** boot it with open networking instead
- For `u-boot`, the rollback and positive scenarios, and every later scenario that sets a host switch (each of the downgrade, signature-rejection, commit-boundary, and interrupted-update scenarios sets one), have further preconditions, the **switch transport**. They exist because a missing transport raises no error of its own: the guest never sees the switches, so N doesn't install N+1, or N+1 ignores the failure switch and reports itself healthy, and the scenario would end in `fail` although nothing about the rollback path was verified. The run checks them in this order, records each result in the protocol, and makes those scenarios `not-run` with the reason of the first check that fails:
  1. The switch type has a transport for the declared firmware. Under `u-boot`, `systemd-credential` and `qemu-fw-cfg` travel over the QEMU `fw_cfg` (§I, §L), and `smbios-type11` has none, since SMBIOS from QEMU doesn't reach a U-Boot guest (§L): reason `switch transport unavailable: smbios-type11 doesn't reach a u-boot guest`
  2. A `systemd-credential` name is at most 28 characters, since its `fw_cfg` item name carries a 27-character prefix and QEMU rejects item names over 55 characters (§L): reason `switch transport unavailable: credential name exceeds 28 characters under u-boot`
  3. The device tree the guest kernel boots with (the booted DTB) is determined from the artifact's own boot configuration, read without modifying the artifact: the file an `extlinux` entry names with `fdt` or finds under `fdtdir` [R10]; the device tree a boot script loads, `${fdtfile}` or another file; for a FIT, the configuration the boot command selects with `#<conf>`, else the default configuration of the FIT, extracted for example with `dumpimage` and read with `fdtget` [R10]; for a UKI that U-Boot starts through its EFI support, the matching `.dtbauto` section, else the `.dtb` section, either of which replaces the device tree U-Boot passes on [R10]. Only when none of these sources applies is the booted DTB the device tree QEMU generates for the `virt` machine type [R7]. When the sources don't yield exactly one device tree (several apply, a boot script computes the file at boot time, or a `.dtbauto` match depends on the device tree the firmware provides): reason `booted DTB not determinable`
  4. The booted DTB contains a node with `compatible = "qemu,fw-cfg-mmio"`, through which the kernel finds the QEMU `fw_cfg` device [R7]: reason `switch transport unavailable: booted DTB has no qemu,fw-cfg-mmio node`. When the artifact ships its kernel configuration, that configuration also enables the `fw_cfg` interface of the kernel in `sysfs` (`CONFIG_FW_CFG_SYSFS`) [R7]: reason `switch transport unavailable: shipped kernel configuration lacks CONFIG_FW_CFG_SYSFS`; without a shipped configuration, the device-tree check decides alone
  5. A real run has confirmed the transport, and §I records that confirmation. Until it does, the scenarios are `not-run` with the reason `switch transport unverified until a real run confirms it (#728)` even when checks 1–4 hold; the run still performs and records checks 1–4, so the prepared path stays ready
- Under `uefi`, a `qemu-fw-cfg` switch travels over the same QEMU `fw_cfg` (§L), whose end-to-end delivery is just as unconfirmed: until a real run confirms it, a scenario that sets one is `not-run` with the reason `switch transport unverified until a real run confirms it (#728)`
- Each scenario **MUST** end in exactly one verdict, defined by exclusion:
  - `not-run`: a precondition failed, the run's own infrastructure failed before the firmware handed over to the image (the hypervisor couldn't start, the overlay couldn't be created, the protocol directory isn't writable), or §I names the case as `not-run` (a missing switch, a report without `machine_id_app`, a local source that delivered nothing to the guest, a committed state the run couldn't keep). In each case the run verified nothing that the scenario exists to check
  - `fail`: every precondition held, the image was started, and an assertion of §F or §I failed or the readiness timeout expired
  - `pass`: every precondition held and every assertion held
  - For the downgrade and signature-rejection scenarios, `pass` additionally requires the positive control of §I, which isn't a precondition: both scenarios boot whether it holds or not. When every assertion held but neither the rollback nor the positive scenario passed in the same run, the verdict is `not-run` with the reason `no positive control: neither rollback nor positive passed`; a failed assertion is `fail` regardless of the control, and also when the local source never delivered the payload (§I)
- A scenario **MUST NEVER** return `pass` when any precondition is missing. A `not-run` verdict **MUST NOT** be counted as a green check by any gate
- The run's overall verdict is the worst verdict of its required scenarios (the smoke scenario, and for an image updated in the field the rollback, downgrade, and signature-rejection scenarios), in the order `fail`, `not-run`, `pass`. A recommended scenario (the positive, identity, commit-boundary, and interrupted-update scenarios) raises the overall verdict to `fail` when it fails, but its `not-run` is reported without raising the overall verdict. A run that writes protocol version 1.0 or 1.1 can't record the downgrade and signature-rejection scenarios (§G), so its overall verdict covers only the required scenarios that version names and isn't a verdict on the requirements those two resolve. The run **MUST** expose it both in the protocol and as its process exit status: `0` for `pass` (with or without the `flaky` flag), `1` for `fail`, `2` for `not-run`
- A guest architecture that differs from the host's always runs under emulation, and the protocol records the boot as cross-architecture
- IF hardware virtualisation is unavailable, THEN the run **MAY** fall back to emulation. Such a run states an explicit warning in its output and protocol and scales every timeout by the emulation factor of §J. A scenario that holds under emulation **MAY** return `pass`; the protocol's acceleration field keeps the weaker evidence visible. Emulated boots on shared CI runners are known to exceed timeouts sized for accelerated boots [R3]

### I. Update and rollback scenario

- For an image whose declaration says `update_model: field-updated`, boot verification **MUST** include a rollback scenario, driven entirely through the switches the declaration names (`spec/project/linux-image-best-practices/` §F):
  1. Boot version N from a fresh copy, with `update.source_switch` set to the local source that serves version N+1 and `health.failure_switch` set to N+1's expected version. The run sets both values once, at launch; they persist across the reboots the guest triggers, and the run doesn't restart the hypervisor during the scenario. N reports `status=healthy`, since the failure switch names another version
  2. The image's update mechanism installs N+1 and reboots into it without further input (`spec/project/linux-image-best-practices/` §F); wait for the first report of N+1
  3. N+1 reports `status=unhealthy` because of the failure switch and reboots on its own; keep reading reports
  4. Assert that the first `status=healthy` report after at most `update.max_boot_attempts` unhealthy reports of N+1 comes from version N. Then power the VM off from the host; the scenario ends there. The power-off is best-effort: N may already have started to install N+1 again, which doesn't affect the verdict, since the copy is discarded
- A run **MUST NOT** make N+1 unhealthy by corrupting or altering the artifact, since a corrupted artifact tests the update framework's signature check, not the rollback path
- A run **SHOULD** also include the positive scenario, as a separate boot from a fresh copy: the same steps without the failure switch, asserting that N+1 reports `status=healthy` and is still the reported version after one further boot, which the run triggers as a reset of the VM through the hypervisor, without restarting the hypervisor process. When the run plans the commit-boundary scenario, it keeps the positive scenario's disk state after the power-off instead of discarding it
- When the declaration lacks the `update` block or `health.failure_switch` despite `update_model: field-updated`, the rollback scenario is `not-run` with that reason; it's never skipped silently. The same holds for the update-security scenarios below: a missing `update` block makes the downgrade, signature-rejection, and interrupted-update scenarios `not-run`, and a missing `health.failure_switch` the commit-boundary scenario
- For an image whose firmware is `u-boot`, the prepared switch transport is the QEMU `fw_cfg` interface, which alters no signed boot component: a `systemd-credential` switch as the item `opt/io.systemd.credentials/<name>`, and a `qemu-fw-cfg` switch as the item its name gives, each passed with `-fw_cfg` (§L). That this chain delivers the switches end to end is **[unverified]** until a real run confirms it (#728). Until then, the rollback and positive scenarios, and every later scenario that sets a host switch, are `not-run`, with the reason of the first switch-transport precondition of §H that fails, and otherwise with `switch transport unverified until a real run confirms it (#728)`, so no verdict rests on the unconfirmed transport. The first real run that confirms the chain, observing and recording that N receives the source switch and installs N+1 and that N+1 honours the failure switch, lifts that `not-run`, and this spec then records the confirmation here. The identity scenario of such an image stays `not-run`, with the reason that no machine-UUID transport is established for U-Boot (§H)
- A run **SHOULD** include the identity scenario for every image: boot the artifact twice, each time from a fresh copy, with a distinct machine UUID assigned by the hypervisor and with no failure or source switch set, and compare the `machine_id_app` values of the two reports. Each boot is held to the smoke assertions of §F, so an unhealthy or missing report fails the scenario. Equal values fail it, because the image ships a fixed machine identity (`spec/project/linux-image-best-practices/` §D). When either report carries `machine_id_app=-`, the scenario is `not-run`
- For an image whose declaration says `update_model: field-updated`, boot verification **MUST** also include the downgrade and the signature-rejection scenarios, and **SHOULD** include the commit-boundary and the interrupted-update scenarios. Each boots from a fresh copy unless its steps say otherwise, is driven only through the switches the declaration names and through host actions on the VM (a reset through the hypervisor, a power-off), sets every switch once at launch, and asserts only on health report lines (§F) and on the requests the local source records. Each sets a host switch, so the switch-transport preconditions of §H and the rule above for `u-boot` firmware apply to it
- **Positive control.** The downgrade and signature-rejection scenarios pass only by observing that nothing changed, which a source arrangement that installs nothing at all would also produce. They boot whether the control holds or not, and only a `pass` of the rollback or positive scenario in the same run, which shows that this arrangement installs a validly signed newer version, lets them return `pass` (§H). When every assertion held but no such `pass` exists, each is `not-run` with the reason `no positive control: neither rollback nor positive passed`; a failed assertion is `fail` regardless, since an installed payload is evidence on its own. The control decides the scenario verdict only: a signature-rejection variant records `pass` when its own assertions held and its payload was delivered, and the scenario turns that into `not-run` when the control is missing. The commit-boundary scenario has its own control, the positive `pass` it continues from
- **Downgrade scenario.** It verifies that the update mechanism refuses a version that isn't newer (`spec/project/linux-image-best-practices/` §F):
  1. Boot N with `update.source_switch` set to the local source, which serves the previous-version artifact of §H as it would serve a release, and with no failure switch. N reports `status=healthy`
  2. Keep reading reports until the update window of §J, counted from N's first report, has passed. Then reset the VM through the hypervisor, without restarting the hypervisor process, and wait for the next report
  3. Assert that every report of the scenario, the one after the reset included, names N's expected version and holds under the §F assertions. A report that names another version, an unhealthy report, or a missing report fails the scenario. Then power the VM off
  4. When the local source didn't deliver the served artifact in full to the guest within the update window, the scenario is `not-run` with the reason `update source not contacted within the update window`, since nothing about the refusal was verified; a request for another path or an aborted transfer doesn't count as delivery. A report that failed step 3 makes the scenario `fail` even then, since a wrong version or an unhealthy report is evidence on its own
- **Signature-rejection scenario.** It verifies at runtime that the update mechanism rejects a payload whose signature is invalid or missing (`spec/project/linux-image-best-practices/` §F; the static side is the payload-signature knob of its §I). It has two payload variants, each booted from its own fresh copy through the steps of the downgrade scenario, with the local source serving that variant's test payload instead of the previous-version artifact. Both variants use the same single forwarded endpoint and the same network configuration, so the scenario records one network entry for both. In each variant the assertion that every report names N's expected version holds although the payload offers a newer version, and the rule on a source that delivered nothing applies unchanged:
  - **The untrusted-key variant**: the payload is signed with a throwaway key generated for the test whose public part no trust anchor of the image contains
  - **The unsigned variant**: the payload carries no signature at all, which catches a mechanism that verifies a payload only when it's signed. When the update framework's payload format admits no unsigned payload, so its tooling can't produce one, the variant is `not-producible` and isn't booted. Its reason **MUST** name why the payload format of the declared `update.mechanism` can't carry an unsigned payload; a consumer that resolves a requirement from a `pass` resting on it reports that reason for human review (`spec/project/linux-image-best-practices/` §J)
  - Each test payload is a complete image of a version newer than N that boots, built through the image definition's own build entry point and differing from the release build only in its signature: signed with the throwaway key, or not signed. The update framework's bundling tool **MAY** only package it, with the framework's normal compatibility metadata, so that a mechanism that accepts it would install it, boot it, and report its version; a payload that a mechanism could refuse for its format or compatibility metadata alone would let a refusal for that other reason read as a signature check. Producing it never writes to the N+1 artifact (§B)
  - The scenario `fail`s when either variant fails. It passes when the untrusted-key variant passes and the unsigned variant passes or is `not-producible`, and only under the positive control above; otherwise it's `not-run`. A `not-producible` unsigned variant never makes the scenario pass on its own
  - The test payloads and the throwaway key **MUST NOT** be published, uploaded to a release location, or stored next to the release artifacts. The throwaway private key **MUST NOT** be committed to the image repository or to any tracked tree, signs nothing else, and is discarded after the run; only its identifier or fingerprint goes into the protocol. The run records each payload's digest, the version it offers, and how it was produced (§G)
- **Commit-boundary scenario.** It verifies that the failure switch has no effect on a committed version (`spec/project/linux-image-best-practices/` §F). A version counts as committed when, in the positive scenario, it reported `status=healthy` and was still the reported version after a VM reset through the hypervisor. That observation is the whole definition, whatever mechanism records the commit inside the image, and the image contract (`spec/project/linux-image-best-practices/` §A) gains no field for it. The scenario continues from that state:
  1. It runs only after a `pass` of the positive scenario in the same run, else it's `not-run` with the reason `no committed version: positive scenario didn't pass`
  2. Boot the disk state the positive scenario left, in a new hypervisor process, with `health.failure_switch` set to N+1's expected version, no source switch, and no network device. The disk state is the copy-on-write overlay and, when the positive scenario used them, the firmware-variables copy and the TPM emulator state
  3. Assert that the first report names N+1's expected version and reports `status=healthy` under the §F assertions; then reset the VM through the hypervisor and assert the same for the next report, so no rollback happened. An unhealthy report, a report that names another version, or a missing report fails the scenario. Then power the VM off and discard the state
  4. When setting the switch needs a new hypervisor process and that restart loses the committed state, for example because the overlay lives only inside the hypervisor process, or when the mechanism can't be driven this way, the scenario is `not-run` with that reason
- **Interrupted-update scenario.** It verifies at runtime that an interrupted installation leaves a complete version active (`spec/project/linux-image-best-practices/` §F atomic update):
  1. Boot N with `update.source_switch` set to the local source, which serves the next-version artifact, and with no failure switch. N reports `status=healthy`
  2. Once the local source has finished sending the next-version artifact to the guest, and before any report of N+1, reset the VM through the hypervisor, without restarting the hypervisor process, and record that moment (§G). When N+1 reports before the run could reset, or the source hasn't finished sending within the update-installation timeout of §J, the scenario is `not-run` with that reason
  3. Assert that within the recovery timeout of §J, counted from the reset, a report with `status=healthy` arrives that names N's or N+1's expected version and holds under the §F assertions. Unhealthy reports before it are allowed, since a rollback path may need them. No healthy report within the recovery timeout, which is a failed boot loop, or a report that names any other version fails the scenario. Then power the VM off; the source still serves N+1, so N may start the update again, which doesn't affect the verdict

### J. Timeouts

- A run **MUST** use these timeouts unless the caller overrides one, in which case the protocol records the override. The defaults are engineering values for an accelerated boot, not calibrated measurements:

  | Timeout | Default | Bounds |
  |---|---|---|
  | Readiness | 300 s | From power-on to the first health report line of one boot |
  | Update installation | 600 s | From the first healthy report of N to the first report of N+1 |
  | Rollback | (`max_boot_attempts` + 1) × readiness | From N+1's first unhealthy report to N's healthy report, covering every boot of N+1 and the boot of N |
  | Update window | 600 s | From N's first report to the VM reset that ends the observation in the downgrade scenario and in each signature-rejection variant |
  | Recovery | (`max_boot_attempts` + 1) × readiness | From the VM reset of the interrupted-update scenario to the first healthy report, covering every boot in between |
  | Total | Sum of the scenario's phases plus 120 s | One scenario, including shutdown |

- Under emulation (§H), every timeout **MUST** be multiplied by an emulation factor of at least 5, and the protocol records the factor used

### K. Canonical anti-patterns

- Declaring success when the kernel prints its banner or the login prompt appears, without the image's health report
- Waiting with a fixed `sleep` before reading the console
- Reporting `pass` when the hypervisor, the firmware, or another precondition was missing
- Booting with Secure Boot disabled, or with a broader key set enrolled, to verify an image that declares Secure Boot
- Booting the build artifact in place, so a first-boot write changes the artifact that's later published
- Testing rollback by corrupting the update payload
- Testing signature rejection with a payload signed by a key the image trusts, publishing a test payload, or committing the throwaway key
- Reading a scenario that a protocol doesn't list, or can't name in its version, as a `pass`
- Treating an out-of-band readiness notification as proof that the image is healthy

### L. Reference profile (optional)

This profile is a worked default. `spec/project/test-pyramid-foundation/` §"Per-tier invariant shape (the meta-contract)" demotes such a profile to a reference, so the profile sets no requirement.

- Hypervisor: QEMU (`qemu-system-<target>`) with KVM acceleration where `/dev/kvm` is available, and TCG emulation otherwise; the image attached with `-snapshot` or through a copy-on-write overlay. The target is the guest architecture (`x86_64`, `aarch64`, `riscv64`, `s390x`), `arm` for `armv7l`, and `ppc64` for `ppc64le`; a guest architecture other than the host's runs under TCG
- Firmware: EDK II OVMF. For Secure Boot, a firmware variables file with only the image's keys enrolled, prepared with `virt-fw-vars`; a distribution's pre-enrolled template carries a broader key set and doesn't satisfy §B. The variables file has to match the firmware build [R2], [R4]
- U-Boot: the QEMU `virt` machine type of the guest architecture, with a U-Boot build for that board passed as `-bios`, for example `qemu-system-aarch64 -machine virt -cpu cortex-a57 -m 2G -display none -bios u-boot.bin -snapshot -drive if=none,id=hd0,format=raw,file=<image> -device virtio-blk-device,drive=hd0 -serial file:<path>`, plus the network arguments below and the switches of the next entries; `qemu-system-arm` and `qemu-system-riscv64` take the same `-machine virt -bios u-boot.bin` **[unverified]**. Whether `-display none` with `-serial file:` captures the console without `-nographic`, which conflicts with `-serial file:`, awaits the first real run (#728)
- TPM: `swtpm` attached as an emulated TPM 2.0 device [R4]
- Console: `-serial file:<path>` captures the serial console [R2]
- Network isolation: a scenario without an update source runs with `-nic none`, which configures no network device [R6]. A scenario with one uses restricted user-mode networking with exactly one guest forward to the host-side local source, for example `-netdev user,id=n0,restrict=on,guestfwd=tcp:10.0.2.100:8080-tcp:127.0.0.1:<port>`, and the source switch names `http://10.0.2.100:8080/`. `restrict=on` isolates the guest from the host and the outside network, and `guestfwd` forwards one guest address to a host endpoint [R6] **[unverified]**: that `guestfwd` keeps working under `restrict=on`, and that an outbound connection to any other address fails, awaits the first real run on the pinned QEMU version (#728)
- Switches: SMBIOS Type 11 strings passed with `-smbios type=11,value=<key>=<value>`; a systemd credential uses the key `io.systemd.credential:<name>` [R1] **[unverified]**
- Switches over `fw_cfg` (the prepared transport under U-Boot, and for a `qemu-fw-cfg` switch under UEFI): QEMU `fw_cfg` items, set once at launch [R7]. QEMU keeps them across guest resets, since its reset handler only resets the item selector and leaves the items in place [R7]. A `systemd-credential` switch is passed as `-fw_cfg name=opt/io.systemd.credentials/<name>,string=<value>`, which systemd 251 and later imports as a system credential [R8] **[unverified]**. QEMU rejects an item name longer than 55 characters [R7], and the item name carries the 27-character prefix, so the credential name is at most 28 characters. A `qemu-fw-cfg` switch, for an image without systemd, is passed as `-fw_cfg name=<name>,string=<value>`, where the name is the full item name `opt/<reverse-domain>/<name>` of at most 55 characters, and the image reads the value from `/sys/firmware/qemu_fw_cfg/by_name/<name>/raw` [R7]. The guest kernel finds the device through the `qemu,fw-cfg-mmio` node of the device tree on the `virt` machine type, or through the ACPI ID `QEMU0002` that QEMU gives it on x86 [R7] **[unverified]**: no source shows the chain from the firmware through the kernel to the guest end to end, so it awaits the first real run (#728), and §H and §I keep the scenarios that depend on it `not-run` until then
- Machine UUID: `-uuid <uuid>`, a fresh value per boot of the identity scenario
- Committed state for the commit-boundary scenario: `-snapshot` keeps its writes in a temporary file that QEMU discards when the process exits [R6], so it can't carry the positive scenario's state into a new process. An overlay file the run creates on top of the artifact, together with copies of the firmware-variables file and the TPM emulator state, can; that the image's committed state survives the new process this way is **[unverified]** until the first real run (#728)
- Under U-Boot on aarch64, SMBIOS from QEMU doesn't reach the guest: the U-Boot configuration `qemu_arm64_defconfig` enables `SYSINFO_SMBIOS`, which builds U-Boot's own SMBIOS tables, and `QFW_SMBIOS`, which would pass the QEMU tables through, depends on its absence [R9]; on a boot without EFI, the arm64 kernel reads no SMBIOS at all, since its `DMI` support depends on `EFI` [R9]. For the other architectures under U-Boot, that SMBIOS from QEMU doesn't reach the guest is **[unverified]**. So SMBIOS Type 11 switches aren't available under U-Boot, and §H makes a scenario with an `smbios-type11` switch there `not-run`. The `-uuid` value likely isn't available either, since without SMBIOS it reaches the guest only as a legacy `fw_cfg` item that the kernel doesn't expose **[unverified]**; §H keeps the identity scenario `not-run`
- Switch transports rejected for U-Boot: SMBIOS, which doesn't reach the guest (above) [R9]; `-device loader`, which writes at most eight bytes into guest memory and gives the guest no defined place to read them from [R7]; a U-Boot environment on a separate flash device, which reaches user space only through the kernel command line, is ignored by a hardened build, and shares state with the update framework's boot counter **[unverified]**, since no source of this pass states it; and the kernel command line, which a signed UKI or FIT, a built-in boot command, or a configuration file on the image fixes, so appending to it alters a signed component or the artifact §B protects, while the QEMU option `-append` applies only together with `-kernel` [R6], [R9]
- Out-of-band readiness (diagnostics only): the `vmm.notify_socket` system credential, through which a systemd guest reports `READY=1` over `AF_VSOCK` [R1]
- Launchers: `mkosi vm` or `systemd-vmspawn` **MAY** replace a raw QEMU command line, provided the run still meets §B–§J [R5]

## Acceptance Criteria

These criteria roll up the requirements above; every requirement stays normative on its own.

- [ ] `spec/project/image-boot-verification/` exists with `en.md` (canonical) and `de.md` (translation) and is listed in `spec/README.md`, and `spec/project/test-pyramid-foundation/` names it as the image realisation of the E2E tier
- [ ] Every field of the foundation's per-tier invariant shape is filled: purpose and scope boundary (§A), isolation and doubles (§B), speed and determinism (§C), execution placement (§D), traceability (§E), anti-patterns (§K), and an optional reference profile (§L), with the boundary against neighbouring tiers stated
- [ ] §B forbids rebuilding, patching, re-signing, or booting the artifact in place, and classifies firmware, TPM, update server, and acceleration with their fidelity rules
- [ ] §C forbids fixed delays and silent retries and requires the `flaky` flag
- [ ] §F makes the line-anchored health report on the serial console the readiness condition and the single source of the state assertions, accepts `starting`, `running`, and tolerated `degraded`, and requires the reported identity to match the declaration and the expected version
- [ ] §G lists every protocol field, requires a protocol for every verdict, and writes uncollected fields as `unavailable` with a reason
- [ ] §G names `schemas/image-boot-protocol-v1.2.schema.yaml` as normative for the protocol format; every protocol a run writes validates against the schema its version names, including a `fail` without a report line, a run that plans an update-security scenario writes version 1.2, a consumer ignores a protocol that doesn't validate against the schema its version names, valid version `1.0` and `1.1` protocols stay accepted, and a scenario a protocol doesn't list or can't name leaves its requirement `not-decidable` with cause `resolvable: <scenario>`
- [ ] §B forbids every network route except the declared local-source endpoint, runs a scenario without an update source with no network device, and has the run assert the network configuration before boot and reject one without the restriction
- [ ] In a scenario with an update source, a connection from the guest to any address other than the forwarded endpoint, an external address or a host service, fails, while the forwarded endpoint serves the next version
- [ ] §A limits boot verification to UEFI and U-Boot images under a virtual machine, counts a declaration of schema version 1.0 as `uefi`, puts `bios` and `other` out of scope with a `spec-gap` result in the audit, and states that a verdict from a virtual machine doesn't establish boot on physical hardware
- [ ] A run boots the hypervisor of the declared guest architecture and is `not-run` when neither the declaration, nor the artifact, nor an input yields the architecture; a U-Boot image's identity scenario is `not-run` until a machine-UUID transport is established
- [ ] §H checks and records a U-Boot image's switch-transport preconditions in order before every scenario that sets a host switch (the rollback and positive scenarios and the four update-security scenarios): a switch type with a transport for the declared firmware, a `systemd-credential` name of at most 28 characters, a booted DTB derived from the artifact's boot configuration (an `extlinux` `fdt` or `fdtdir` entry, a boot script's device tree, the selected or default FIT configuration, a `.dtbauto` or `.dtb` section of a UKI, and the device tree QEMU generates only when none of these applies) that carries a `qemu,fw-cfg-mmio` node, and a shipped kernel configuration that enables `CONFIG_FW_CFG_SYSFS`
- [ ] Run against a U-Boot image updated in the field, every scenario that sets a host switch (the rollback and positive scenarios and the four update-security scenarios) is `not-run`, never `pass` or `fail`, until a real run confirms the transport and this spec records it: with the reason of the first failing switch-transport precondition (for example `switch transport unavailable: smbios-type11 doesn't reach a u-boot guest`, `booted DTB not determinable`, or `switch transport unavailable: booted DTB has no qemu,fw-cfg-mmio node`), and otherwise with `switch transport unverified until a real run confirms it (#728)`; a scenario with a `qemu-fw-cfg` switch under `uefi` is `not-run` with the latter reason
- [ ] §I and §L specify the U-Boot switch transport as a prepared path through the QEMU `fw_cfg`, a `systemd-credential` switch as `-fw_cfg name=opt/io.systemd.credentials/<name>` and a `qemu-fw-cfg` switch as its full item name of at most 55 characters, mark the chain **[unverified]** until a real run, and name the rejected transports (SMBIOS, `-device loader`, a U-Boot environment, the kernel command line) with their reasons
- [ ] §H names the run's inputs, defines `pass`, `fail`, and `not-run` by exclusion, lists every precondition, defines the overall verdict as the worst verdict of the required scenarios, with a recommended scenario's `not-run` not raising it, with exit statuses `0`, `1`, and `2`, and allows `pass` under emulation only with the warning and scaled timeouts
- [ ] §I specifies, for an image updated in the field, the downgrade and signature-rejection scenarios as required and the commit-boundary and interrupted-update scenarios as recommended, each with steps driven only through the declared switches and host actions on the VM, assertions on health report lines, and `not-run` conditions; the commit-boundary scenario defines a committed version as one that reported healthy and was still reported after a VM reset in the positive scenario
- [ ] No scenario modifies the artifact under test, the next-version artifact, or the previous-version artifact; the signature-rejection scenario's test payloads are complete images of a newer version that boot, built through the image definition's own build entry point, differing from the release only in being signed with a throwaway key no trust anchor of the image contains or not signed at all, recorded with how they were produced, and never published, and the throwaway private key is never committed and is discarded after the run
- [ ] §H lists the previous-version artifact and the untrusted-key and unsigned test payloads as inputs, and a missing one makes only the scenario or variant that needs it `not-run`; §G and the protocol schema carry each update-security scenario's observed versions, the requests its local source recorded, each signature-rejection variant's verdict, and the interrupted-update scenario's reset moment
- [ ] A downgrade or signature-rejection `pass` counts only with a `pass` of the rollback or positive scenario in the same run, a commit-boundary result only after a positive `pass`, and the schema rejects a protocol that breaks either; a run for an image updated in the field writes protocol version 1.2; the control decides the scenario verdict, while a signature-rejection variant's record shows its own observation
- [ ] Run against an image whose update mechanism installs a version that isn't newer, the downgrade scenario fails; against one that installs a payload signed with an untrusted key, or an unsigned one, the signature-rejection scenario fails; and without the previous-version artifact, the downgrade scenario is `not-run` while the other scenarios run; with a previous-version artifact that isn't older than N it's `not-run` without booting; and a failed assertion is `fail` even when the local source delivered nothing
- [ ] §I drives the rollback scenario only through the declared switches set once at launch, relies on the image to install, reboot, and roll back on its own, bounds it by `max_boot_attempts`, ends it at N's healthy report, forbids corrupting the artifact, turns a missing switch into `not-run`, and adds the identity scenario
- [ ] Run on a host without the hypervisor, the skill exits with status `2` and writes a protocol whose verdict is `not-run`, whose uncollected fields read `unavailable`, and which validates against the protocol schema
- [ ] For a declaration with `max_boot_attempts: 3`, the rollback scenario ends after at most four boots counted from the first boot of N+1 (three of N+1, one of N), within the §J rollback timeout
- [ ] §J states default timeouts, a rollback timeout that covers the final boot of N, an update window for the downgrade and signature-rejection scenarios, a recovery timeout for the interrupted-update scenario, and the minimum emulation factor
- [ ] Tool names appear only in the reference profile (§L) and as cited examples, never as binding requirements

## Open Questions

- **Runner status** (load-bearing). The non-interactive runner `boot_verify.py` of the `image-boot-verify` skill (#746) ships the exit statuses `0`, `1`, and `2` of §H and is the entry point the pipeline and a developer machine share (§D); its tests cover the acceptance criterion on a host without the hypervisor (exit status `2` and a valid `not-run` protocol). It has booted no real image yet: its tests run a fake hypervisor, so the §L command line, the network isolation, and the §J timeouts stay **[unverified]** until the first real run, tracked in #728. It runs the downgrade, signature-rejection, commit-boundary, and interrupted-update scenarios and writes protocol version 1.2 (#754), equally verified only against the fake hypervisor; the kept disk state the commit-boundary scenario continues from (§L) stays **[unverified]** with the rest. Until a real run has passed, this spec stays `draft`, and a runner verdict is evidence of the runner's control flow, not of a booted image.

- **Cross-architecture evidence** (parking-lot). §A and §H settle the architecture scope: the declaration names its architectures, the run boots the hypervisor for the one under test, and a boot on a foreign host architecture runs under emulation and is recorded as cross-architecture. Whether such emulated evidence suffices for a release gate stays a decision for the first consumer that builds for a foreign architecture; the protocol keeps it visible.
- **U-Boot switch transport** (load-bearing for U-Boot images updated in the field until the first real run). The research pass of 2026-11-15 settled the transport as far as sources reach: the QEMU `fw_cfg` interface passes the switches without altering a signed boot component (§H, §I, §L), and SMBIOS, `-device loader`, a U-Boot environment, and the kernel command line are rejected (§L). What stays open is the confirmation by a real run, tracked in #728. Until then the transport is **[unverified]**, a U-Boot image's rollback and positive scenarios and its four update-security scenarios are `not-run` (§H, §I), and `linux-image-audit` can't resolve the rollback results of such an image, which stays `INCOMPLETE`. The identity scenario under U-Boot stays `not-run` beyond that, since the guest can't read a machine UUID the hypervisor assigns without SMBIOS, so its identity result stays unresolved too.
- **Interruption point** (parking-lot). The interrupted-update scenario resets the VM at one point, once the payload is delivered. A mechanism that installs while it downloads has finished most of its installation by then, while one that installs after the download has only begun. Whether further points, such as a reset during the transfer or a delay after it, add evidence worth their runtime is for the first real runs to show.
- **Calibrating the timeouts** (parking-lot). The §J defaults are engineering values. The first real runs against consumer images (a follow-up per the requirement record's item R10) should measure boot durations and adjust them.
