# Dokumentations-Zielgruppen-Spuren

Status: draft

## Kontext
<!-- Warum existiert diese Spec? Welches Problem, welches Nutzer-Bedürfnis oder welche Einschränkung treibt sie? -->

Die MkDocs-Site eines Portfolio-Repositorys wird von zwei materiell unterschiedlichen Zielgruppen in zwei materiell unterschiedlichen Modi konsumiert: Leuten, die **das Produkt verstehen und nutzen** wollen (Endnutzer / Konsumenten — lesen auf einer veröffentlichten Site, klonen das Repo nie, sprechen die Domänensprache des Produkts), und Leuten, die **das Projekt selbst bauen, erweitern oder betreiben** wollen (Contributor, Maintainer, Release-Manager, Integratoren — klonen das Repo, betreiben die Toolchain, lesen Interna). `spec/project/mkdocs-structure/` definiert die sieben Standard-Top-Level-Sektionen und den `audience`-Frontmatter-Schlüssel, und `spec/project/audience-identification/` definiert, wie ein Repository seine Zielgruppen überhaupt aufzählt — aber keine der Specs sagt, wie diese Zielgruppen auf die *Spur* abbilden, auf der ein Leser unterwegs ist. Das Ergebnis: Jedes Repository entscheidet ad hoc, welche Seite an wen adressiert, die Grenze ist implizit, und ein Leser, der auf einer Seite landet, muss „ist das für mich?" aus Prosa und Kontext ableiten statt aus einem strukturellen Signal.

Diese Spec schließt diese Lücke. Sie deklariert zwei kanonische Dokumentations-Spuren — `user-docs` und `developer-docs` — und verlangt von jeder MkDocs-Seite, dass sie über einen neuen `track`-Frontmatter-Schlüssel genau eine davon deklariert. Die Spec forkt das Sieben-Sektionen-Skelett aus `mkdocs-structure` bewusst **nicht**; Spuren sind eine orthogonale Klassifikation quer durch die Sektionen, getrieben von Per-Page-Frontmatter und verankert im Audience-Artefakt des Projekts. Repositories, die wirklich nur eine Spur bedienen (eine veröffentlichte Library ohne Endnutzer-Oberfläche, ein Endnutzer-Produkt, dessen Interna Closed-Source sind), **DÜRFEN [MAY]** die andere Spur weglassen, aber die Auslassung wird im Audience-Artefakt neben den bestehenden portfolio-Basis-Auslassungs-Notizen festgehalten, damit ein Reviewer eine bewusste Scope-Entscheidung von einem Versehen unterscheiden kann.

## Ziele
<!-- Was diese Spec erreichen will. Stichpunkte, outcome-orientiert. -->
- „Für wen ist diese Seite?" auf jeder MkDocs-Seite aus einem einzigen strukturellen Signal beantwortbar machen, statt aus Prosa-Ableitung
- Zwei kanonische Spuren (`user-docs`, `developer-docs`) mit schriftlicher, testbarer semantischer Abgrenzung definieren
- Die Spuren an den bestehenden `audience`-Frontmatter und an das Audience-Artefakt des Projekts zurückbinden, damit die Spuren keine parallele Klassifikation sind, die von der Audience-Liste wegdriftet
- Das Sieben-Sektionen-Skelett aus `mkdocs-structure` unangetastet lassen — eine Spur ist ein Frontmatter-Signal, keine neue Sektion
- Die Auslassung einer Spur explizit im Audience-Artefakt sichtbar machen, damit ein Single-Track-Repository eine sichtbare, begründete Entscheidung ist und kein Versehen

## Nicht-Ziele
<!-- Explizit außerhalb des Scopes. Verhindert Scope-Creep. -->
- Die sieben Top-Level-Nav-Sektionen aus `spec/project/mkdocs-structure/` neu definieren — Sektionen bleiben das strukturelle Skelett, Spuren sind eine orthogonale Frontmatter-Klassifikation
- Das Audience-Artefakt aus `spec/project/audience-identification/` ersetzen oder duplizieren — diese Spec konsumiert das Artefakt, sie wiederholt es nicht
- Eine dritte Spur einführen (`operator-docs`, `release-docs`, `security-docs`) — diese Spec ist bewusst auf zwei Spuren begrenzt; eine dritte Spur verlangt eine Folge-Spec oder ein projekt-typ-spezifisches Opt-in
- Theme, Palette oder per-Spur-Visualisierung vorschreiben (spur-spezifische Tags, Badges oder Farbakzente sind erlaubt, aber nicht vorgeschrieben)
- Artefakte außerhalb von `docs/<lang>/` regeln (Root-`README.md`, `CONTRIBUTING.md`, `AGENTS.md`, ADR-Quellen unter `docs/<lang>/adrs/` sind im Scope; ADR-Provenienz-Dateien außerhalb des MkDocs-Trees sind es nicht)
- Die Form auto-generierter Katalog-Seiten definieren (die Spurzuweisung des Katalog-Generators ist an die projekt-typ-spezifische Spec delegiert, der der Katalog gehört — zum Beispiel `spec/claude/skill-agent-catalog/`)

## Anforderungen
<!-- RFC-2119-Schlüsselwörter verwenden: MUSS, SOLLTE, KANN. Eine atomare Anforderung pro Stichpunkt. -->

### Spur-Definitionen

- **MUSS [MUST]** portfolio-weit genau zwei kanonische Spuren definieren:
  - `user-docs` — die fachliche Sicht: was das Produkt *für Endnutzer / Konsumenten ist* und wie sie es nutzen. In der Domänensprache des Produkts geschrieben, frei von repository-lokalen Toolchain-Annahmen (kein „klone dieses Repo", kein „führe `task lint` aus"). Ein Leser auf einer veröffentlichten MkDocs-Site ist die kanonische Zielgruppe.
  - `developer-docs` — die technische Sicht: wie Contributor, Maintainer, Operator und Release-Manager das Projekt selbst bauen, erweitern, konfigurieren und betreiben. In der Engineering-Sprache des Projekts geschrieben; referenziert die lokale Toolchain, interne Module, Erweiterungs-Hooks, ADRs sowie Release-/Betriebs-Prozeduren.
- **DARF NICHT [MUST NOT]** zusätzliche `track`-Werte ohne projekt-typ-spezifisches Spec-Opt-in einführen; die geschlossene Enumeration `{user-docs, developer-docs}` ist Portfolio-Default. Eine projekt-typ-spezifische Spec **KANN [MAY]** die Enumeration erweitern (zum Beispiel eine künftige `release-docs`-Spur), aber die Erweiterung **MUSS [MUST]** den neuen Wert, seine semantische Abgrenzung zu den zwei kanonischen Spuren und seine Platzierung in der Nav benennen.

### Inhaltskontrakt der user-docs

Ein Repository, dessen Audience-Artefakt mindestens eine Audience auf `user-docs` abbildet (also nicht aus der Spur austritt), **MUSS [MUST]** die folgenden Inhaltsblöcke auf seiner `user-docs`-Oberfläche auffindbar machen. Die Blöcke **DÜRFEN [MAY]** über die Standard-Nav-Sektionen (Home, Getting Started, Guides) verteilt oder auf einer einzigen User-Docs-Landingpage gebündelt sein; entscheidend ist, dass jeder Block von der Home-Seite aus in höchstens einem Navigationsschritt erreichbar ist und als stabile, identifizierbare Einheit rendert (eine dedizierte Seite, ein `## H2`-Abschnitt oder ein Snippet-Include mit benanntem Marker).

- **MUSS [MUST]** einen **Installations-/Inbetriebnahme-Block** ausliefern — wie ein Endnutzer das Deliverable installiert, einbindet oder anderweitig in Betrieb nimmt. Die Form passt sich an den Projekttyp an: ein Plugin / eine Library erklärt Konsumenten, wie sie es in ihren Stack aufnehmen, ein CLI erklärt Nutzern, wie sie das Binary installieren, ein Service / eine App erklärt Operatoren-als-Endnutzer, wie sie es laufen lassen. Der Block **MUSS [MUST]** ohne die Annahme verfasst sein, dass dieses Repository geklont oder die lokale Toolchain verfügbar ist (kein `task lint`, kein `pnpm install --workspace-root` gegen dieses Repo); er deckt ab, was der Endnutzer in *seiner* Umgebung tut.
- **MUSS [MUST]** einen **Wertversprechen-Block** ausliefern — ein bis drei Absätze, die den fachlichen Nutzen des Projekts benennen, in der Domänensprache des Produkts und frei von Engineering-Jargon. „Welches Problem löst das für mich, und warum sollte ich es übernehmen?" muss allein aus diesem Block beantwortbar sein.
- **MUSS [MUST]** einen **Zielgruppen-Block** ausliefern — für wen das Projekt *ist*, in Endnutzer-Begriffen formuliert. Der Block **MUSS [MUST]** die relevanten Audience-IDs aus dem Audience-Artefakt des Projekts (gemäß `spec/project/audience-identification/`) zitieren, damit Prosa und Artefakt nicht auseinanderlaufen; ein Projekt mit mehreren Endnutzer-Audiences benennt jede einzeln und was sie konkret aus dem Projekt zieht.
- **MUSS [MUST]** einen **Use-Case-/Anwendungsfall-Block** ausliefern — die konkreten fachlichen Szenarien, für die das Projekt gedacht ist, in Endnutzer-Begriffen formuliert (nicht in Toolchain-Begriffen). Der Block listet mindestens die im Scope befindlichen Use Cases; er **SOLLTE [SHOULD]** zusätzlich eine kleine Menge explizit außerhalb des Scopes liegender Use Cases benennen, damit ein Leser sich selbst-screenen kann, bevor er Zeit in den Installations-Block investiert.
- **SOLLTE [SHOULD]** einen **Quickstart-Block** ausliefern — der kürzeste Pfad von einem frischen Leser zum ersten beobachtbaren Erfolg, idealerweise mit einem greifbaren Ergebnis in unter fünf Minuten. Der Quickstart ist **kein** Tutorial (keine ausführliche Lehre) und **kein** Installations-Block (kein erschöpfendes Setup); er wählt einen Happy Path, hard-coded jede Variable mit einem sinnvollen Default und endet bei einem verifizierbaren Resultat (gemäß The Good Docs Project Quickstart Template: „primary feature, start using as quickly as possible"; GitLab „Get started"-Page-Type). Der Block trägt `content_mode: tutorial` und delegiert Tiefe explizit an die Installations-, Use-Case- und How-to-Oberflächen.
- **SOLLTE [SHOULD]** einen **Troubleshooting-Block** ausliefern — verbreitete, für Endnutzer sichtbare Fehlermodi gepaart mit Workarounds und Resolutions. Jeder Eintrag folgt der `symptom`-/`cause`-/`workaround`-/`resolution`-Vokabel, die `spec/project/mkdocs-structure/` §Inhalts-Modi (Diátaxis-Ausrichtung) ratifiziert (Quelle: GitLab Troubleshooting Topic Type und The Good Docs Project Troubleshooting Guide). Der Block trägt `content_mode: troubleshooting`; ein Projekt mit weniger als drei bekannten Fehlermodi **KANN [MAY]** den Block unter `## Troubleshooting` in eine bestehende Seite einbetten, statt eine eigenständige Troubleshooting-Seite auszuliefern.
- **SOLLTE [SHOULD]** Wertversprechen-, Zielgruppen- und Use-Case-Block früh in der Nav-Reihenfolge platzieren (typischerweise auf der Home-Seite oder der User-Docs-Landingpage), damit ein Leser sich selbst-screenen kann, bevor er die Installation erreicht; der Installations-Block eröffnet typischerweise die **Getting Started**-Sektion gemäß `spec/project/mkdocs-structure/` §Top-Level-Navigation
- **KANN [MAY]** dieselben vier Blöcke zusätzlich im Root-`README.md` per `mkdocs-include-markdown-plugin`-Snippet-Einbindung (gemäß `spec/project/mkdocs-structure/` §Snippet-Einbindung (DRY)) spiegeln — das `README.md` ist die Visitenkarte des Repositorys und überschneidet sich naturgemäß mit der `user-docs`-Oberfläche
- **DARF NICHT [MUST NOT]** diese Blöcke auf einem Repository verlangen, dessen Audience-Artefakt explizit aus `user-docs` austritt; die Opt-out-Notiz im Artefakt ist die kanonische Ausnahme und wird zum Audit-Zeitpunkt verifiziert

### Inhaltskontrakt der developer-docs

Ein Repository, dessen Audience-Artefakt mindestens eine Audience auf `developer-docs` abbildet (also nicht aus der Spur austritt), **MUSS [MUST]** die folgenden Inhaltsblöcke auf seiner `developer-docs`-Oberfläche auffindbar machen. Die Blöcke **DÜRFEN [MAY]** über die Standard-Nav-Sektionen (Getting Started, Guides, References, ADRs, Project) verteilt oder auf einer einzigen Developer-Docs-Landingpage gebündelt sein; entscheidend ist, dass jeder Block von der Home-Seite aus in höchstens einem Navigationsschritt erreichbar ist und als stabile, identifizierbare Einheit rendert.

- **MUSS [MUST]** einen **Setup-/Voraussetzungs-Block** ausliefern — was ein Entwickler benötigt, um am Projekt weiterzuarbeiten: die lokale Toolchain (Sprachlaufzeiten, Paketmanager, Task-Runner), die gepinnten Versionen oder Versionsbereiche, die voraussetzenden Systemtools und externen Accounts und die Erstbootstrap-Sequenz (`task install`, `pre-commit install`, `pnpm install`, äquivalent). Der Block **MUSS [MUST]** spezifisch genug sein, dass ein Newcomer in einem Lesen entscheiden kann, ob er beitragen kann und exakt welche Befehle er ausführen muss, bevor das Repository arbeitsfähig ist.
- **MUSS [MUST]** einen **Tech-Stack-Block** ausliefern — die Sprachen, Frameworks, Laufzeiten, Bibliotheken, Plugin-Engines und externen Services, auf denen das Projekt aufsetzt, mit Pin-Absicht. Wo die portfolio-weite Tech-Stack-Erfassung lebt (`spec/portfolio/tech-stack/`, `spec/portfolio/tech-stack-discovery/`), **MUSS [MUST]** der Developer-Docs-Block die kanonische Portfolio-Quelle referenzieren oder einbinden statt sie zu wiederholen, damit die zwei nicht auseinanderlaufen; projekt-lokale Ergänzungen über der Portfolio-Basis werden inline neben dem Include gelistet.
- **MUSS [MUST]** einen **Schnittstellen-/Vertrags-Block** ausliefern — jede Schnittstelle, die das Projekt exponiert und die eine andere Komponente, ein Service, ein Plugin oder ein menschlicher Caller bedienen kann. Beispiele, die als Schnittstelle zählen: öffentliche APIs (REST, gRPC, Library-API), CLI-Befehle und ihre Flags, Plugin- oder Skill-Erweiterungs-Hooks, Konfigurationsdatei-Schemata, Event-/Message-Verträge, MkDocs-Frontmatter- oder Template-Verträge, generierte Artefakt-Formen. Generierte Referenz-Oberflächen (Katalog-Generatoren gemäß `spec/claude/skill-agent-catalog/`, künftige API-Referenz-Generatoren) **SOLLTEN [SHOULD]** den Großteil dieses Blocks tragen; für handgeschriebene Projekte werden jede Schnittstelle und ihr Vertrag direkt aufgelistet.
- **SOLLTE [SHOULD]** einen **Erweiterungs-/Contribution-Flow-Block** ausliefern — wie ein Entwickler eine Änderung landet: Branching-Modell, Pull-Request-Workflow, Quality-Gates, Release-Flow, wo die relevanten Specs liegen. Der Block **KANN [MAY]** `spec/project/branching-model/`, `spec/project/pull-request-workflow/`, `spec/project/quality-gate/` und `spec/project/spec-driven-development/` referenzieren, statt deren Inhalte zu wiederholen.
- **SOLLTE [SHOULD]** einen **Architektur-Überblicks-Block** ausliefern — eine ein-Bildschirm-große Sicht auf die Bausteine des Systems, die Grenze zu externen Systemen und die tragenden Entscheidungen, geschrieben für einen Newcomer, der die Codebase navigieren muss. Der Block trägt `content_mode: explanation` und folgt der arc42-Rahmung („relevant requirements and driving forces … business goals, functional requirements, quality goals, stakeholder expectations"; arc42 §1 + §3 + §5 + §9): mindestens benennt er den **Kontext** (was drin, was draußen ist), die **Bausteine** (Top-Level-Module / Services / Plugins) und die **Entscheidungen**, die nicht-triviale Trade-offs festgezurrt haben (verlinkt auf ADRs, statt sie zu wiederholen). Ein Repository mit weniger als drei Top-Level-Bausteinen **KANN [MAY]** den Architektur-Überblick in die Developer-Docs-Landingpage einbetten; größere Systeme liefern ihn als eigenständige Seite aus.
- **SOLLTE [SHOULD]** einen **Glossar-Block** ausliefern — Terminologie spezifisch für die Domäne, Organisation oder Toolchain des Projekts, einzeilige Definitionen, alphabetisch sortiert. Der Block trägt `content_mode: glossary` (gemäß `spec/project/mkdocs-structure/` §Inhalts-Modi). Glossare sind Best Practice, um Begriffe spezifisch für eine bestimmte Industrie, Organisation oder ein Team zu hinterlegen (The Good Docs Project Glossary Template), und arc42 §12 ratifiziert das Glossar als tragendes Architektur-Doku-Artefakt. Das Glossar **DARF NICHT [MUST NOT]** Begriffe wiederholen, die bereits vom Upstream-Vale-Vokabular (`nolte/vale-style` gemäß `spec/project/prose-style/`) abgedeckt sind; es erfasst den *projektspezifischen* Delta, mit einem Link zum Upstream-Vokabular für die allgemeine Basis.
- **SOLLTE [SHOULD]** einen **Developer-Troubleshooting-Block** ausliefern — verbreitete Fehlermodi, in die ein Contributor oder Operator läuft (Toolchain-Setup schiefgegangen, kaputter lokaler Build, fehlschlagendes CI, Deployment-Überraschung), gepaart mit Workarounds und Resolutions nach derselben `symptom`-/`cause`-/`workaround`-/`resolution`-Vokabel wie der User-Docs-Troubleshooting-Block. Der Block trägt `content_mode: troubleshooting`.
- **DARF NICHT [MUST NOT]** diese Blöcke auf einem Repository verlangen, dessen Audience-Artefakt explizit aus `developer-docs` austritt; die Opt-out-Notiz im Artefakt ist die kanonische Ausnahme und wird zum Audit-Zeitpunkt verifiziert

### Per-Page-Kontrakt

- **MUSS [MUST]** auf jeder Seite unter `docs/<lang>/` einen `track`-Frontmatter-Schlüssel deklarieren, dessen Wert genau eine der kanonischen Spuren (oder eine explizit per Opt-in zugelassene Erweiterungs-Spur) ist. Der `track`-Schlüssel ist ein additiver MUSS oben auf dem Vier-Schlüssel-Per-Page-MUSS-Set (`title`, `audience`, `content_mode`, `last_updated`), das `spec/project/mkdocs-structure/` §Per-Page-Struktur definiert, und erhöht damit den Per-Page-MUSS-Count auf fünf.
- **DARF NICHT [MUST NOT]** einen `track`-Schlüssel auf Snippet-Fragmenten verlangen — Dateien in einem mit `_` präfixierten Ordner unter `docs/<lang>/` (zum Beispiel `docs/<lang>/_snippets/`) sind Fragmente, keine Seiten, und bleiben gemäß `spec/project/mkdocs-structure/` §Snippet-Einbindung (DRY) frei vom Per-Page-Pflicht-Frontmatter
- **MUSS [MUST]** einen unbekannten `track`-Wert, einen fehlenden `track`-Wert (auf einer Nicht-Snippet-Seite) oder einen `track`-Wert aus einer projekt-typ-spezifischen Spec, in die das Repository nicht eingewilligt hat, als `docs-freshness`-Befund gemäß `spec/project/docs-freshness/` behandeln
- **SOLLTE [SHOULD]** der Home-Seite (`docs/<lang>/index.md`) und Per-Sektion-Index-Seiten erlauben, `track: user-docs` *oder* `track: developer-docs` basierend auf der primären Audience der Sektion zu deklarieren; eine einzelne Seite **DARF NICHT [MAY NOT]** beide Spuren deklarieren
- **SOLLTE [SHOULD]** wirklich meta-Seiten — die Home-Seite, wenn sie beide Spuren vorstellt, Per-Sektion-Index-Seiten, generator-emittierte Nav-Stubs (literate-nav-`SUMMARY.md`), Tag-Indexe und ADRs, die den Spur-Split selbst motivieren — als Portfolio-Default auf `track: developer-docs` setzen. Die geschlossene Enumeration `{user-docs, developer-docs}` wird **nicht** durch einen `meta`-`track`-Wert erweitert; meta-Seiten sind von der Audience-zu-Spur-Nicht-Widerspruchs-Regel aus §Audience-zu-Spur-Mapping gemäß §Inhalts-Modus-Mapping ausgenommen, da `content_mode: meta` bereits signalisiert, dass die Seite Leser quer durch Spuren routet, statt eine zu bedienen
- **KANN [MAY]** einen spur-spezifischen Frontmatter-Akzent deklarieren (zum Beispiel ein `summary`, das in spur-passender Sprache umformuliert ist, oder einen `tags`-Eintrag, der die Spur spiegelt) — rein additiv, niemals den `track`-Schlüssel ersetzend

### Audience-zu-Spur-Mapping

- **MUSS [MUST]** jede im Audience-Artefakt des Projekts (gemäß `spec/project/audience-identification/`) gelistete Audience auf genau eine der zwei kanonischen Spuren abbilden. Das Mapping wird im Audience-Artefakt neben jedem Audience-Eintrag festgehalten (zum Beispiel ein Feld `track: user-docs` neben der bestehenden Beziehungskategorie und dem Bestätigungs-Tag).
- **MUSS [MUST]** eine explizite Notiz „keine Audience bildet auf diese Spur ab" im Audience-Artefakt festhalten, wenn das Repository wirklich eine der zwei Spuren nicht bedient (eine Library ohne Endnutzer-Oberfläche lässt `user-docs` weg; ein rein internes Produkt ohne Contributor-Oberfläche lässt `developer-docs` weg). Die Notiz folgt derselben Form wie die portfolio-Basis-Auslassungs-Notiz, die `spec/project/mkdocs-structure/` §Audience-Targeting verlangt.
- **SOLLTE [SHOULD]** die portfolio-Basis-Audiences (`user`, `contributor`, `operator`, `release-manager`) standardmäßig wie folgt abbilden, pro Projekt mit einzeiliger Begründung im Audience-Artefakt übersteuerbar:
  - `user` → `user-docs`
  - `contributor` → `developer-docs`
  - `operator` → `developer-docs`
  - `release-manager` → `developer-docs`
- **MUSS [MUST]** eine Seite, deren `audience`-Frontmatter-Wert auf eine andere Spur abbildet als der `track`-Frontmatter-Wert der Seite, als `docs-freshness`-Befund (Warnung, kein Fehler) behandeln, damit ein Reviewer den Widerspruch bewusst auflösen kann

### Home-Page-Kontrakt

- **SOLLTE [SHOULD]** beide Spuren auf der Home-Seite (`docs/<lang>/index.md`) benennen, wenn das Repository beide bedient — ein Absatz, der Endnutzer auf den User-Docs-Einstieg und Contributor auf den Developer-Docs-Einstieg zeigt — damit ein Leser bei frischem Seitenaufruf in einem Schritt selbst-routen kann
- **KANN [MAY]** den Spur-Routing-Absatz auf der Home-Seite weglassen, wenn das Repository nur eine Spur bedient (die Auslassung der anderen Spur ist bereits im Audience-Artefakt festgehalten und damit zum Audit-Zeitpunkt sichtbar)

### Inhalts-Modus-Mapping

Die `track`-Achse (diese Spec) und die `content_mode`-Achse (`spec/project/mkdocs-structure/` §Inhalts-Modi (Diátaxis-Ausrichtung)) sind **orthogonal**: jede Seite deklariert beides, und die Audit-Oberfläche prüft jede unabhängig. Die zwei Achsen beantworten unterschiedliche Fragen — „für wen ist diese Seite?" (track) und „was liefert diese Seite?" (mode). Eine `user-docs`-Spur-Seite kann ein `tutorial`, ein `how-to`, eine `reference`, eine `explanation`, ein `troubleshooting` oder ein `glossary` sein; dasselbe gilt für `developer-docs`. Das Diátaxis-Framework nimmt zu Audience explizit keine Position ein, und GitLabs CTRT nimmt zur Inhalts-Modus-Taxonomie explizit keine Position ein; die Kombination entlang orthogonaler Achsen ist die einfachste Versöhnung.

- **MUSS [MUST]** auf jeder Seite `track` und `content_mode` unabhängig voneinander deklarieren; eine Seite **DARF NICHT [MUST NOT]** das eine aus dem anderen ableiten
- **SOLLTE [SHOULD]** ein Basis-Mapping im Kopf behalten, wenn die Inhalte einer Sektion geplant werden (Operatoren brauchen selten ausgedehntes `tutorial`-Material; Endnutzer brauchen selten eine `explanation`-Seite, die tief genug ist, einen ADR zu ersetzen), **DARF NICHT [MUST NOT]** aber irgendeine Spur-zu-Modus-Regel über die in `mkdocs-structure` bereits bestehende Nicht-Mischen-Disziplin hinaus verhärten
- **KANN [MAY]** dasselbe konzeptionelle Thema in zwei Seiten unterschiedlicher `track`- und / oder `content_mode`-Werte ausliefern (eine `user-docs`-/`how-to`-Seite „Feature X aktivieren" und eine `developer-docs`-/`reference`-Seite „Konfigurations-Schlüssel X") — das ist beabsichtigte, audience-gebundene Wiederholung und ist vom Write-the-Docs-ARID-Prinzip abgedeckt, das in `spec/project/mkdocs-structure/` §Snippet-Einbindung (DRY) ratifiziert ist

### Erweiterungs-Hook

- **KANN [MAY]** eine projekt-typ-spezifische Spur über eine Folge-Spec unter `spec/` einführen, konform zu `spec/project/mkdocs-structure/` §Erweiterungs-Hooks. Die Erweiterungs-Spec **MUSS [MUST]** den neuen `track`-Wert, seine semantische Abgrenzung zu `user-docs` und `developer-docs`, die abgedeckte(n) Audience(s) und den Per-Page-Frontmatter-Kontrakt (sofern vorhanden) benennen, den sie über die Basis hinaus hinzufügt.
- **DARF NICHT [MUST NOT]** die Enumeration auf anderem Weg stillschweigend erweitern — weder durch Freitext-Werte in `track`, noch durch mehrere Spuren auf einer Seite, noch durch Umbenennung einer kanonischen Spur

## Akzeptanzkriterien

- [ ] Jede Seite unter `docs/<lang>/` in jedem Portfolio-Repository (außer Dateien in einem `_`-präfixierten Snippet-Ordner) deklariert einen `track`-Frontmatter-Schlüssel, dessen Wert `user-docs`, `developer-docs` oder eine explizit per Opt-in zugelassene Erweiterungs-Spur ist. ## Offene Fragen
<!-- Ungeklärte Entscheidungen, bekannte Unbekannte, Punkte, die eine Stakeholder-Antwort brauchen. -->
- Soll die `track`-Enumeration in `spec/project/mkdocs-structure/` ratifiziert werden, sobald diese Spec stabilisiert ist (die geschlossene Menge wandert in die Per-Page-MUSS-Liste), oder bleibt sie hier in `docs-audience-tracks` autoritativ, damit eine künftige Enumerations-Erweiterung nur eine Spec-Datei berührt? Default vorerst: hier autoritativ, von `mkdocs-structure` referenziert.
- Gehört `release-manager` dauerhaft zu `developer-docs`, oder ist eine künftige `release-docs`-Spur sinnvoll, sobald `spec/project/release-skill-layer/` genug Material produziert, um eine eigene Nav-Oberfläche zu füllen? Verschoben, bis ein Portfolio-Repository dieses Volumen wirklich anhäuft.
- Wie entdeckt eine dritte Partei, die nur die veröffentlichte MkDocs-Site liest, die Spur einer gegebenen Seite, wenn sie den Frontmatter nicht sieht? Ist ein kleines Per-Page-Header-Badge („für Endnutzer" / „für Entwickler") vorschreibungswürdig, oder reicht die Nav-Gruppierung? Verschoben, bis eine echte Leser-seitige Beschwerde existiert.
- Wie tief muss der User-Docs-Installations-/Onboarding-Block gehen — reicht ein einzelnes Befehl-Snippet, oder **MUSS [MUST]** jedes Projekt einen ausführbaren End-to-End-Quickstart (der Installation + ersten Erfolg verifiziert) ausliefern, bevor der Block als vollständig zählt? Verschoben, bis ein Portfolio-Repository einen Quickstart ausliefert, den wir als Referenzform kodifizieren können.
- Wie granular muss der Developer-Docs-Schnittstellen-/Vertrags-Block sein — verlangt jede CLI-Flag, jeder Plugin-Frontmatter-Schlüssel und jedes Config-Schema-Feld einen eigenen Eintrag, oder reicht eine sektion-weite Zusammenfassung mit Zeiger auf Quelle/generierte Referenz? Wahrscheinlich projekt-typ-spezifisch; eine Folge-Erweiterungs-Spec (`library-api-docs`, künftige `cli-reference-docs`) kann pro Projekttyp Granularität kodifizieren.
- Ist der Architektur-Überblicks-Block als einzelne Seite ausreichend, oder soll das Portfolio ein vollständiges arc42-Sektionen-Set (Kontext, Bausteine, Runtime-View, Deployment, Crosscutting Concepts, ADRs, Quality, Risiken, Glossar) für Repositories über einer Größenschwelle übernehmen? Verschoben, bis ein Portfolio-Repository diese Schwelle erreicht; die Ein-Seiten-Übersicht ist die Untergrenze, vollständiges arc42 ist eine Opt-in-Erweiterung via `spec/project/mkdocs-structure/` §Erweiterungs-Hooks.
- Soll der Quickstart-Block von `SOLLTE [SHOULD]` zu `MUSS [MUST]` verhärtet werden für Repositories, deren Audience-Artefakt eine `user`-Audience mit „erster beobachtbarer Erfolg" als entscheidendem Evaluationskriterium aufführt? Verschoben, bis das Audience-Identification-Artefakt ein strukturiertes „Entscheidungskriterium"-Feld trägt, das der Audit lesen kann.
