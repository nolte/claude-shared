# Documentation Audience Tracks

Status: draft

## Context
<!-- Why does this spec exist? What problem, user need, or constraint drives it? -->

A portfolio repository's MkDocs site is consumed by two materially different audiences in two materially different modes: people who want to **understand and use the product** (end users / consumers—read on a published site, never clone the repo, speak the product's domain language) and people who want to **build, extend, or operate the project itself** (contributors, maintainers, release managers, integrators—clone the repo, run the toolchain, read internals). `spec/project/mkdocs-structure/` defines the seven standard top-level sections and the `audience` frontmatter key, and `spec/project/audience-identification/` defines how a repository enumerates its audiences in the first place—but neither spec says how those audiences map to the *track* a reader is on. As a result, every repository decides ad hoc which page targets which reader, the boundary is implicit, and a reader who lands on a page has to infer "is this for me?" from prose and context rather than from a structural signal.

This spec closes that gap. It declares two canonical documentation tracks (`user-docs` and `developer-docs`) and makes every MkDocs page declare exactly one of them via a new `track` frontmatter key. The spec deliberately doesn't fork the seven-section skeleton in `mkdocs-structure`; tracks are an orthogonal classification that runs across sections, driven by per-page frontmatter and anchored in the project's audience artefact. Repositories that genuinely serve only one track (a published library without an end-user surface, an end-user product whose internals are closed-source) may omit the other track, but the omission is recorded in the audience artefact alongside the existing portfolio-baseline omission notes so a reviewer can tell a deliberate scope decision from an oversight.

## Goals
<!-- What this spec aims to achieve. Bullet points, outcome-oriented. -->
- Make the "who is this page for?" question answerable from a single structural signal on every MkDocs page, not from prose inference
- Define two canonical tracks (`user-docs`, `developer-docs`) with a written, testable semantic distinction
- Tie the tracks back to the existing `audience` frontmatter and to the project's audience artefact, so the tracks aren't a parallel classification that drifts from the audience list
- Preserve the seven-section skeleton in `mkdocs-structure` untouched—a track is a frontmatter signal, not a new section
- Surface the omission of a track explicitly in the audience artefact, so a single-track repository is a visible, justified choice rather than an oversight

## Non-Goals
<!-- Explicitly out of scope. Prevents creep. -->
- Redefining the seven top-level nav sections from `spec/project/mkdocs-structure/`: sections remain the structural skeleton, tracks are an orthogonal frontmatter classification
- Replacing or duplicating the audience artefact from `spec/project/audience-identification/`: this spec consumes the artefact, it doesn't restate it
- Introducing a third track (`operator-docs`, `release-docs`, `security-docs`)—this spec is deliberately limited to two tracks; a third track requires a follow-up spec or a project-type-specific opt-in
- Prescribing theme, palette, or per-track visual treatment (track-specific tags, badges, or colour accents are allowed but not required)
- Governing artefacts outside `docs/<lang>/` (root `README.md`, `CONTRIBUTING.md`, `AGENTS.md`, ADR source under `docs/<lang>/adrs/` is governed; ADR provenance files outside the MkDocs tree aren't)
- Defining the shape of automatically generated catalog pages (the catalog generator's track assignment is delegated to the project-type-specific spec that owns the catalog—for example `spec/claude/skill-agent-catalog/`)

## Requirements
<!-- Use RFC 2119 keywords: MUST, SHOULD, MAY. One atomic requirement per bullet. -->

### Track definitions

- **MUST** define exactly two canonical tracks portfolio-wide:
  - `user-docs`: the functional view: what the product *is* for end users / consumers and how they use it. Written in the product's domain language, free of repository-local toolchain assumptions (no "clone this repo," no "run `task lint`"). A reader on a published MkDocs site is the canonical audience.
  - `developer-docs`: the technical view: how contributors, maintainers, operators, and release managers build, extend, configure, and operate the project itself. Written in the project's engineering language; references the local toolchain, internal modules, extension hooks, ADRs, and release / operations procedures.
- **MUST NOT** introduce additional `track` values without a project-type-specific spec opt-in; the closed enumeration `{user-docs, developer-docs}` is portfolio-default. A project-type-specific spec **MAY** widen the enumeration (for example a future `release-docs` track), but the widening **MUST** name the new value, its semantic distinction from the two canonical tracks, and its placement in the nav.
- The closed enumeration is authoritative in this spec; `spec/project/mkdocs-structure/` references it rather than restating it, so a future enumeration widening only touches one spec file.

### User-docs content contract

A repository whose audience artefact maps at least one audience to `user-docs` (that's doesn't opt out of the track) **MUST** make the four content blocks below discoverable on its `user-docs` surface. The blocks **MAY** be distributed across the standard nav sections (Home, Getting Started, Guides) or bundled on a single user-docs landing page; what matters is that each block is reachable from the Home page within at most one navigation step and renders as a stable, identifiable unit (a dedicated page, an `## H2` section, or a snippet include with a named marker).

- **MUST** ship an **installation / onboarding block**: how an end user installs, embeds, or otherwise stands up the deliverable. The shape adapts to the project type: a plugin / library tells consumers how to add it to their stack, a CLI tells users how to install the binary, a service / app tells operators-as-end-users how to run it. The block **MUST** be written without assuming a clone of this repository or local toolchain access (no `task lint`, no `pnpm install --workspace-root` against this repo); it covers what the end user does in *their* environment.
- **MUST** ship a **value-proposition block**: one to three paragraphs naming the functional benefit the project delivers, written in the product's domain language and free of engineering jargon. "What problem does this solve for me, and why would I adopt it?" must be answerable from this block alone.
- **MUST** ship an **audience block**: who the project is *for*, phrased in end-user terms. The block **MUST** cite the relevant audience IDs from the project's audience artefact (per `spec/project/audience-identification/`) so the prose and the artefact don't drift; a project with multiple end-user audiences names each one and what specifically they get out of the project.
- **MUST** ship a **use-case / scenario block**: the concrete functional scenarios the project is designed for, phrased in end-user terms (not in toolchain terms). At minimum the block lists the in-scope use cases; it **SHOULD** also call out a small set of explicitly out-of-scope use cases so a reader can self-screen before investing in the installation block.
- **SHOULD** ship a **quickstart block**: the shortest path from a fresh reader to first observable success, ideally producing a tangible outcome in under five minutes. The quickstart isn't a tutorial (no extended teaching) and isn't an installation block (no exhaustive setup); it picks one happy path, hard-codes every variable that has a sensible default, and ends at a verifiable result (per The Good Docs Project Quickstart template: "primary feature, start using as quickly as possible"; GitLab "Get started" page type). The block carries `content_mode: tutorial` and explicitly defers depth to the installation, use-case, and how-to surfaces.
- **SHOULD** ship a **troubleshooting block**: common end-user-visible failure modes paired with workarounds and resolutions. Each entry follows the `symptom` / `cause` / `workaround` / `resolution` vocabulary ratified by `spec/project/mkdocs-structure/` §Content modes (Diátaxis alignment) (sourced from GitLab Troubleshooting topic type and The Good Docs Project Troubleshooting Guide). The block is `content_mode: troubleshooting`; a project with fewer than three known failure modes **MAY** embed the block under `## Troubleshooting` inside an existing page rather than ship a standalone troubleshooting page.
- **SHOULD** place the value-proposition, audience, and use-case blocks early in the nav order (typically on the Home page or the user-docs landing page) so a reader can self-screen before reaching installation; the installation block typically opens the **Getting Started** section per `spec/project/mkdocs-structure/` §Top-level navigation
- **MAY** mirror the same four blocks in the root `README.md` via `mkdocs-include-markdown-plugin` snippet inclusion (per `spec/project/mkdocs-structure/` §Snippet inclusion (DRY))—the README is the repository's calling card and naturally overlaps the `user-docs` surface
- **MUST NOT** require these blocks on a repository whose audience artefact explicitly opts out of `user-docs`; the opt-out note in the artefact is the canonical exemption and is verified at audit time

### Developer-docs content contract

A repository whose audience artefact maps at least one audience to `developer-docs` (that's doesn't opt out of the track) **MUST** make the four content blocks below discoverable on its `developer-docs` surface. The blocks **MAY** be distributed across the standard nav sections (Getting Started, Guides, References, ADRs, Project) or bundled on a single developer-docs landing page; what matters is that each block is reachable from the Home page within at most one navigation step and renders as a stable, identifiable unit.

- **MUST** ship a **setup / prerequisites block**: what a developer needs to start contributing to the project: the local toolchain (language runtimes, package managers, task runners), the pinned versions or version ranges, the prerequisite system tools and external accounts, and the first-time bootstrap sequence (`task install`, `pre-commit install`, `pnpm install`, equivalent). The block **MUST** be specific enough that a newcomer can decide in one read whether they can contribute and exactly which commands they need to run before the repository is workable.
- **MUST** ship a **tech-stack block**: the languages, frameworks, runtimes, libraries, plugin engines, and external services the project depends on, with pinning intent. Where the portfolio-wide tech-stack capture lives (`spec/portfolio/tech-stack/`, `spec/portfolio/tech-stack-discovery/`), the developer-docs block **MUST** reference or include the canonical portfolio source rather than restate it, so the two don't drift; project-local additions on top of the portfolio baseline are listed inline next to the include.
- **MUST** ship an **interface / contract block**: every interface the project exposes that another component, service, plugin, or human caller can drive. Examples that count as interfaces: public APIs (REST, gRPC, library API), CLI commands and their flags, plugin- or skill-extension hooks, configuration-file schemas, event / message contracts, MkDocs frontmatter or template contracts, generated artefact shapes. Generated reference surfaces (catalog generators per `spec/claude/skill-agent-catalog/`, future API-reference generators) **SHOULD** carry the bulk of this block; for hand-authored projects each interface and its contract is listed directly.
- **SHOULD** ship an **extension / contribution-flow block**: how a developer makes a change land: branching model, pull-request workflow, quality gates, release flow, where the relevant specs live. The block **MAY** reference `spec/project/branching-model/`, `spec/project/pull-request-workflow/`, `spec/project/quality-gate/`, and `spec/project/spec-driven-development/` rather than restate their content.
- **SHOULD** ship an **architecture-overview block**: a one-screen view of the system's building blocks, the boundary to external systems, and the load-bearing decisions, written for a newcomer who needs to navigate the codebase. The block is `content_mode: explanation` and follows arc42's framing ("relevant requirements and driving forces … business goals, functional requirements, quality goals, stakeholder expectations"; arc42 §1 + §3 + §5 + §9): at minimum it names the **context** (what's inside, what's outside), the **building blocks** (top-level modules / services / plugins), and the **decisions** that locked in non-trivial trade-offs (link out to ADRs rather than restating them). A repository with fewer than three top-level building blocks **MAY** embed the architecture overview inside the developer-docs landing page; larger systems ship it as a standalone page.
- **SHOULD** ship a **glossary block**: terminology specific to the project's domain, organisation, or toolchain, one-line definitions, alphabetically sorted. The block is `content_mode: glossary` (per `spec/project/mkdocs-structure/` §Content modes). Glossaries are best practice for storing terms specific to a particular industry, organisation, or team (The Good Docs Project Glossary template) and arc42 §12 ratifies the glossary as a load-bearing architecture-doc artefact. The glossary **MUST NOT** restate terms already covered by the upstream Vale vocabulary (`nolte/vale-style` per `spec/project/prose-style/`); it captures the *project-specific* delta, with a link to the upstream vocabulary for the general baseline.
- **SHOULD** ship a **developer-troubleshooting block**: common failure modes a contributor or operator hits (toolchain setup gone wrong, broken local build, failing CI, deployment surprise), paired with workarounds and resolutions following the same `symptom` / `cause` / `workaround` / `resolution` vocabulary as the user-docs troubleshooting block. The block is `content_mode: troubleshooting`.
- **MUST NOT** require these blocks on a repository whose audience artefact explicitly opts out of `developer-docs`; the opt-out note in the artefact is the canonical exemption and is verified at audit time

### Per-page contract

- **MUST** declare a `track` frontmatter key on every page under `docs/<lang>/` whose value is exactly one of the canonical tracks (or an explicitly opted-in extension track). The `track` key is an additive MUST on top of the four-key per-page MUST set (`title`, `audience`, `content_mode`, `last_updated`) defined by `spec/project/mkdocs-structure/` §Per-page structure, raising the per-page MUST count to five.
- **MUST NOT** require a `track` key on snippet fragments—files inside a `_`-prefixed folder under `docs/<lang>/` (for example `docs/<lang>/_snippets/`) are fragments, not pages, and remain free of the per-page MUST frontmatter per `spec/project/mkdocs-structure/` §Snippet inclusion (DRY)
- **MUST** treat an unknown `track` value, a missing `track` value (on a non-snippet page), or a `track` value declared by a project-type-specific spec that the repository hasn't opted into as a `docs-freshness` finding per `spec/project/docs-freshness/`
- **SHOULD** allow the Home page (`docs/<lang>/index.md`) and per-section index pages to declare `track: user-docs` *or* `track: developer-docs` based on the section's primary audience; a single page **MAY NOT** declare both tracks
- **SHOULD** assign `track: developer-docs` to genuinely meta pages as the portfolio default—the Home page when it introduces both tracks, per-section index pages, generator-emitted nav stubs (literate-nav `SUMMARY.md`), tag indexes, and ADRs that motivate the track split itself. The closed `{user-docs, developer-docs}` enumeration **isn't widened** by a `meta` track value (see §Track definitions)
- **SHOULD** treat such meta pages as exempt from the audience-to-track no-contradiction rule of §Audience-to-track mapping per §Content-mode mapping, since `content_mode: meta` already signals that the page routes readers across tracks rather than serving one
- **MAY** declare a track-specific frontmatter accent (for example a `summary` rewritten in track-appropriate language, or a `tags` entry that mirrors the track)—purely additive, never replacing the `track` key

### Audience-to-track mapping

- **MUST** map every audience listed in the project's audience artefact (per `spec/project/audience-identification/`) to exactly one of the two canonical tracks. The mapping is recorded in the audience artefact next to each audience entry (for example a `track: user-docs` field alongside the existing relationship category and confirmation tag).
- **MUST** record an explicit "no audience maps to this track" note in the audience artefact when the repository genuinely doesn't serve one of the two tracks (a library with no end-user surface omits `user-docs`; an internal-only product with no contributor surface omits `developer-docs`). The note follows the same shape as the portfolio-baseline omission note required by `spec/project/mkdocs-structure/` §Audience targeting.
- **SHOULD** map the portfolio-baseline audiences (`user`, `contributor`, `operator`, `release-manager`) as follows by default, overridable per project with a one-line rationale in the audience artefact:
  - `user` → `user-docs`
  - `contributor` → `developer-docs`
  - `operator` → `developer-docs`
  - `release-manager` → `developer-docs`
- **MUST** treat a page whose `audience` frontmatter value maps to a track different from the page's `track` frontmatter value as a `docs-freshness` finding (warning, not error) so a reviewer can resolve the contradiction deliberately

### Home-page contract

- **SHOULD** name both tracks on the Home page (`docs/<lang>/index.md`) when the repository serves both—a single paragraph that points end users at the user-docs entry point and contributors at the developer-docs entry point—so a reader on a fresh page load can self-route in one step
- **MAY** omit the track-routing paragraph on the Home page when the repository serves only one track (the omission of the other track is already recorded in the audience artefact and is therefore visible at audit time)
- A reader on the published MkDocs site discovers a page's track through nav grouping, the Home-page track-routing paragraph above, and the optional `tags` mirror (§Per-page contract MAY); a visible per-page track badge stays **MAY**, not a SHOULD or MUST. The portfolio default is nav-only signalling—mandating a visible badge is a deliberate product / UX call deferred to a future spec revision, not the baseline.

### Content-mode mapping

The `track` axis (this spec) and the `content_mode` axis (`spec/project/mkdocs-structure/` §Content modes (Diátaxis alignment)) are **orthogonal**: each page declares both, and the audit surface checks each independently. The two axes answer different questions—"who is this page for?" (track) and "what does this page deliver?" (mode). A `user-docs` track page can be a `tutorial`, a `how-to`, a `reference`, an `explanation`, a `troubleshooting`, or a `glossary`; the same is true for `developer-docs`. The Diátaxis framework explicitly takes no position on audience, and GitLab's CTRT explicitly takes no position on content-mode taxonomy; combining them along orthogonal axes is the simplest reconciliation.

- **MUST** declare `track` and `content_mode` independently on every page; a page **MUST NOT** infer one from the other
- **SHOULD** keep a baseline mapping in mind when planning a section's contents (operators rarely need extended `tutorial` material; end users rarely need an `explanation` page deep enough to substitute for an ADR), but **MUST NOT** harden any track-to-mode rule beyond the no-mixing discipline already in `mkdocs-structure`
- **MAY** ship the same conceptual topic in two pages of different `track` and / or `content_mode` values (a `user-docs` / `how-to` "Enable feature X" page and a `developer-docs` / `reference` "Configuration key X" page)—that's intentional, audience-bound repetition and is covered by the Write the Docs ARID principle ratified in `spec/project/mkdocs-structure/` §Snippet inclusion (DRY)

### Extension hook

- **MAY** introduce a project-type-specific track via a follow-up spec under `spec/`, conforming to `spec/project/mkdocs-structure/` §Extension hooks. The extension spec **MUST** name the new track value, its semantic distinction from `user-docs` and `developer-docs`, the audiences it covers, and the per-page frontmatter contract (if any) it adds beyond the baseline.
- **MUST NOT** silently widen the enumeration in any other way—neither by free-form values in `track`, nor by allowing multiple tracks on a single page, nor by renaming a canonical track
- Per-type interface granularity (per-flag, per-key, or per-field detail) is deliberately out of scope for this portfolio-wide spec; the portfolio floor is the interface-block **MUST** with generated reference surfaces carrying the bulk (§Developer-docs content contract). A follow-up project-type-specific spec (`library-api-docs`, `cli-reference-docs`) codifies per-type granularity.

## Acceptance Criteria
<!-- Testable, checkable conditions. A reviewer should be able to mark each as done/not done. -->
- [ ] Every page under `docs/<lang>/` in every portfolio repository (excluding files under any `_`-prefixed snippet folder) declares a `track` frontmatter key whose value is `user-docs`, `developer-docs`, or an explicitly opted-in extension track. Verifiable by an audit that lists files under `docs/<lang>/` and reports any whose YAML frontmatter is missing `track` or carries an unrecognised value.
- [ ] The project's audience artefact (`AUDIENCES.md` or the alternative location ratified by `spec/project/audience-identification/`) maps every listed audience to exactly one canonical track, or carries an explicit "no audience maps to this track" note for an omitted track.
- [ ] `spec/project/mkdocs-structure/` references this spec in §Per-page structure (listing `track` as the fourth per-page MUST frontmatter key) and in §Audience targeting (cross-linking the track-to-audience mapping rule).
- [ ] `spec/project/audience-identification/` references this spec where it speaks of "downstream artefacts (READMEs, specs, threat models, release notes, SLAs)"—the documentation-tracks artefact is one of those consumers, and the audience-to-track mapping field is the consuming surface.
- [ ] `spec/project/docs-freshness/` (or the implementation of `docs-freshness-checker`) flags three classes of finding: (a) a page missing `track`, (b) a page with an unrecognised `track` value, (c) a page whose `audience` value maps to a track different from the page's `track` value.
- [ ] Every repository that doesn't opt out of `user-docs` ships the four required user-docs content blocks (installation / onboarding, value proposition, audience, use cases / scenarios) reachable from the Home page within at most one navigation step; each block is a stable, identifiable unit (dedicated page, `## H2` section, or named snippet include). Verifiable by an audit that walks the `user-docs` surface and reports a missing block by name.
- [ ] Every repository that doesn't opt out of `user-docs` and has a "first observable success" surface ships a **quickstart** block separate from the full installation block; the quickstart reaches the first verifiable result without an exhaustive setup detour
- [ ] Every repository that doesn't opt out of `developer-docs` ships the three required developer-docs content blocks (setup / prerequisites, tech stack, interfaces / contracts) reachable from the Home page within at most one navigation step; each block is a stable, identifiable unit. The tech-stack block references or includes from `spec/portfolio/tech-stack/` rather than restating the portfolio capture. Verifiable by an audit that walks the `developer-docs` surface and reports a missing block by name.
- [ ] Every repository that doesn't opt out of `developer-docs` ships an **architecture-overview** block (context, building blocks, load-bearing decisions linked out to ADRs) and a **glossary** block (project-specific terminology, alphabetically sorted, no overlap with the upstream `nolte/vale-style` vocabulary)
- [ ] Every track (where the corresponding track isn't opted out) ships a **troubleshooting** block using `symptom` / `cause` / `workaround` / `resolution` as the canonical action vocabulary; user-docs troubleshooting addresses end-user-visible failures, developer-docs troubleshooting addresses contributor / operator failures
- [ ] Every page declares both `track` and `content_mode` independently; no page infers one from the other
- [ ] At least one portfolio repository (worked example: `nolte-shared` itself, or another repo of choice) has migrated its `docs/<lang>/` tree to the `track` frontmatter contract and recorded the audience-to-track mapping in its audience artefact, and `mkdocs build --strict` still passes.
