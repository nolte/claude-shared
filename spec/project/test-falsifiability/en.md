# Test Falsifiability

Status: draft
Portfolio-Scope: portfolio

## Context

A red test announces itself. A test that can't fail is indistinguishable from a test that works—until someone reads it. A stabilization campaign over a consuming project's E2E suite (kamerplanter, issues `nolte/kamerplanter#768` and `nolte/kamerplanter#778`) surfaced eleven tests and helpers that couldn't fail, or could only fail for the wrong reason. Every one was found by accident: unrelated work happened to walk past it. Two had asserted against the wrong column on the desktop profile for years. One had suppressed the evidence of a genuine product failure for the entire lifetime of the feature it covered. None was ever reported by any test run, because all of them produce a pass. That's the defining property of this defect class: it's invisible to the very mechanism the portfolio uses to find defects. Relying on someone happening to read the test doesn't scale; a defect class becomes searchable only once it's enumerable and each category has a stated way to detect it.

The corpus already touches the property in fragments: `spec/project/e2e-test-automation/` forbids tautological assertions by example, `spec/project/e2e-test-stability/` §D and §G require loud-failing helpers and readers in their E2E scope, and `spec/project/source-code-review/` D6 names "assertion-free or always-green tests" without criteria. This spec owns the property itself: the taxonomy, the detection routes, the prevention rules, and the binding that makes detection routine rather than accidental. The framing mirrors `spec/project/error-tracking/`, whose rationale that an unread tracker "produces the false confidence of 'we'd know'" describes exactly the same epistemic failure: a green suite full of tests that can't fail is strictly worse than a smaller honest one, because it converts absent verification into apparent verification.

This spec declares the identifier space T1–Tn for the taxonomy, following the precedent of the D1–D10 and F1–F11 dimension catalogs in the source-code-review family. The taxonomy applies to every test tier; the worked examples are E2E-heavy because that's where the evidence campaign ran.

Readers: authors and reviewers of test code at every tier; the tier generator and reviewer agents; the test-cycle, source-code-review, test-pyramid, and quality-gate processes; product-code authors, because falsifiable tests need addressable product hooks.

## Goals

- Make "this test can't fail" an enumerable, searchable defect class instead of an accidental discovery
- Give every taxonomy category a stated detection route: static, dynamic, or review-only—none left as "be careful"
- Make negative verification a required, evidence-bearing step when a regression test is added
- State the design rules—for test code and for product code—that prevent non-falsifiable tests from being written at all
- Bind the taxonomy into the existing review and generation processes as a named checklist dimension
- Decide the gate question explicitly: suite-quality signals such as mutation score stay advisory, and the reason is recorded

## Non-Goals

- Skip and expected-failure hygiene, including availability-dependent skips (T7): owned by `spec/project/e2e-test-stability/` §A and §E; this spec includes T7 for taxonomy completeness and cross-references it, never restates it
- The responsive/viewport causes of silent passes and the provider-side hook contract: owned by `spec/project/e2e-test-stability/` §G and `spec/frontend/testability-identifiers/`; this spec states only the general addressable-without-guessing rule those rules instantiate
- Degrading an existing falsifiable test to force a pass: owned by the no-cheating invariant of `spec/project/test-cycle-foundation/` and `spec/project/test-cycle-code-adaptation/`; that invariant covers the transition, this spec covers tests that were born weak
- Diagnosing why a red test is red: owned by `spec/project/test-cycle-result-analysis/`; this spec is the mirror image—what to do about suspicious green
- Swallowed errors in production code at runtime: owned by `spec/project/source-code-review/` D1 (review-time) and `spec/project/error-tracking/` (runtime); T1 covers the test-artifact instance only
- The composition, invocation contract, and output shape of the local quality gate: owned by `spec/project/quality-gate/`; this spec only feeds it the advisory-vs-blocking decision
- The tier taxonomy itself: owned by `spec/project/test-pyramid-foundation/`; falsifiability is a cross-cutting property of tests at every tier, not a tier
- The fidelity requirement on test doubles: owned by `spec/project/test-pyramid-foundation/` §"Test-double taxonomy" portfolio-wide and expressed per tier by the tier specs; T9 is the failure mode this spec makes citable and detectable, and restating the rule here would fork it
- The operational mechanics of static-analysis rules (rule identifiers, baselines, ratchets, noise governance): owned by `spec/project/test-tier-static-analysis/`; this spec defines what the checks look for, that tier owns how they run

## Requirements

### The taxonomy of non-falsifiable tests

- The taxonomy below **MUST** be treated as open: when a new instance doesn't fit an existing category, a new `Tn` entry **MUST** be added with the finding's mechanism and a concrete worked example recorded, in this spec, in the same change that fixes or defers the finding
- A finding, a review checklist item, or a lint rule that targets this defect class **MUST** cite the category by its `Tn` identifier, so findings stay comparable across repositories and reviewers
- **T1—Swallowed failure signals.** A post-condition or assertion wrapped in a broad exception handler whose body discards the signal (`except: pass`, an empty `catch`). Observed: a save helper whose missing-confirmation assertion sat inside a bare `except`, hiding a real failure permanently; a dropdown-dismissal helper that returned successfully with the menu still open. A test or test helper **MUST NOT** catch and discard a failure signal from an action it performed or a condition it verified; catching is legitimate only when followed by a loud failure or by explicitly reasoned control flow. Detection: static (see below) plus review; the production-code counterpart is owned by `spec/project/source-code-review/` D1
- **T2—Vacuous assertions.** An assertion satisfied by the reader's failure value, or by every value in the domain. Observed: `assert cell == ""` where the reader returns `""` when it finds nothing; `assert count >= 0` on a length; tests asserting only that no error is displayed, which can't distinguish success from nothing-happened. An assertion **MUST** be falsifiable by some achievable input, and an assertion consisting solely of a negative ("no error shown") **MUST** be paired with a positive assertion on the effect the test claims to verify. Detection: static for the literal and tautology shapes, review for the rest
- **T3—Empty-default readers.** A reader that returns an empty value (`""`, `[]`, `None`) for "I couldn't look," conflating it with "I looked and the value is empty." Observed: table-cell readers against a card layout returning `[]`; a list reader that found nothing on every viewport and silently fell back to a hard-coded dummy search term. A reader **MUST** distinguish "not found" from "found and empty" and **MUST** fail loudly on the former; this generalizes the layout-reader rule of `spec/project/e2e-test-stability/` §G to every tier and every reader. Detection: static (return-shape check) plus review
- **T4—Silent no-op state changers.** A helper performs an action that can't have an effect and reports success. Observed: a scripted `element.click()` on a component that only opens on `mousedown`; a synthetic submit event dispatched inside `if (form) { … }` with no else branch, which also bypasses the submit button entirely, so a permanently disabled button would never be noticed. A state-changing helper **MUST** verify its effect and fail loudly (the general form of `spec/project/e2e-test-stability/` §D), an injected-script guard **MUST** have a failing else branch, and a helper **MUST** exercise the user-facing control rather than a synthetic equivalent unless the synthetic path is itself the contract under test. Detection: static (guard shape, missing read-back) plus review
- **T5—Silent path substitution.** The test still passes but no longer exercises the thing it's named after. Observed: a sidebar-navigation helper that falls back to direct URL navigation whenever the nav item sits below a scroll fold—the navigation it exists to test simply stops being tested. A fallback chain **MUST** terminate in a failure, never in an empty result or a silently substituted code path; when a legitimate alternative path exists, the choice **MUST** be explicit at the call site (a parameter, a distinct helper), not a runtime fallback. Detection: review-only
- **T6—Wrong-target resolution that still passes.** The locator resolves, to the wrong element. Observed: a positional `cells[3]` reading the location column while named "phase"; three differently named locator constants holding one identical selector, where document order decides which element wins; an unscoped role selector matching hidden chrome. A locator **MUST** be unambiguous within its page or page object—two selector constants with identical values under different names are a defect—and access into collections **MUST** be key-based per `spec/project/e2e-test-stability/` §G. Detection: static (identical-selector check) plus review
- **T7—Availability-dependent skips.** A skip whose firing depends on data, ordering, or worker scheduling silently removes coverage while reporting a neutral outcome. Fully owned by `spec/project/e2e-test-stability/` §A and §E; listed here so the taxonomy is complete and findings can cite T7, with the rules living there
- **T8—Tests that execute no check.** The degenerate case the other categories presuppose away: T2 grades an assertion that's too weak, T8 covers the test where no assertion runs at all. Two shapes, both of which pass unconditionally. *No assertion present*—a body that only arranges and acts, passing because nothing threw; these are the Empty Test and Unknown Test smells of the catalog cited in §Sources, and `spec/project/source-code-review/` D6 names the shape without criteria. *An assertion that's never reached*—the canonical rotten-green shape of the literature cited in §Sources, where the assertion sits after an unconditional early return, inside a conditional branch a passing run never enters, in a helper the test defines but never calls, or inside a loop over a collection the test never asserts non-empty, so zero iterations pass vacuously. Every test **MUST** execute at least one assertion on the outcome its name claims, and an assertion whose execution isn't guaranteed on the passing path **MUST** be treated as absent. A test whose contract genuinely is "this runs without crashing" (a smoke test, an import check) satisfies the rule only when it names that contract in its own documentation; an unstated absence of exceptions doesn't. Detection: static (see below), plus mutation testing per the dynamic criteria, which kills such a test on any mutant
- **T9—Doubles that can't refuse.** A test double that's **more permissive than the collaborator it replaces**: it accepts inputs, preserves fields, or permits states the real collaborator would reject, so a passing run describes a world that can't occur. Observed: a hand-written fake repository that honoured a caller-supplied `_key` and enforced no uniqueness, standing in for a real repository that discards `_key` unconditionally and carries a unique index on the slug field. Six unit tests passed, among them a positive control written specifically to stop the refusal tests passing vacuously; the seeded record then failed every platform-admin case of the E2E matrix in *setup*, on a login timeout that read like a harness problem, while the real cause sat in the backend log as a duplicate-key error from the second boot onward. The distinguishing property against T2 and T8 is that the assertion is falsifiable, specific, and correct while the **arrangement** is what lies: grading the assertion harder finds nothing, and the double itself carries no assertion at all yet decides the outcome of every test in the file. The fidelity requirement a T9 finding cites is owned by `spec/project/test-pyramid-foundation/` §"Test-double taxonomy" and expressed per tier by the tier specs; this category is the failure mode, never the rule's home. Detection: review-only, via the fidelity question recorded under §"Detection: Review criteria" below. Negative verification **MUST NOT** be relied on to *discover* this category: where the production defect and the permissive double are introduced in the same change, no pre-fix state exists to revert to, so nothing was ever red. Once a T9 finding is confirmed, the obligation below applies, bounded as stated there: tightening the double until it refuses what the real collaborator refuses typically turns the case red immediately, and that run is the required evidence—except in the retrospective case, which §"Negative verification" routes explicitly

### Detection: Static criteria

- A repository's static-analysis tier **SHOULD** check test code for the mechanically detectable shapes of the taxonomy, at minimum: a broad exception handler with an empty or `pass` body inside a test or a helper that performs or verifies a state change (T1); an assertion whose expected literal equals the documented empty default of the reader supplying its actual value (T2); comparisons tautological over the value's domain, such as a non-negativity check on a length (T2); assertions consisting solely of a negative (T2); reader functions with an "if found, value, else empty literal" return shape (T3); an injected-script guard with no failing else branch (T4); a state-changing helper with no read-back before returning (T4); two or more locator constants with identical values in one page object (T6); a test function whose body contains no assertion statement and no call to a helper that asserts (T8); an assertion positioned after an unconditional early return, or held only in a helper the test never calls (T8); and an assertion executed only inside a loop body, where the test doesn't assert the iterated collection non-empty first (T8)
- The assertion-free shape of T8 is the cheapest check in this catalog and the one a repository **SHOULD** adopt first: it needs no type information, and its only legitimate exception—the documented smoke test—is declared in the test itself, which makes the exemption checkable rather than argued
- These checks **MUST** run under the operational regime of `spec/project/test-tier-static-analysis/` (rule identifiers, suppression discipline, baseline-and-ratchet, effective-signal governance) rather than inventing a parallel mechanism
- A static falsifiability check **MUST NOT** be promoted to a blocking severity before its false-positive rate has been measured against a real repository (a first measurement is recorded in the settled Open Questions); a noisy check gets disabled and is worse than none

### Detection: Dynamic criteria

- Mutation testing is the canonical general detector—mutate production code, and any test that still passes is a falsifiability suspect—and **SHOULD** be applied per `spec/project/test-pyramid-foundation/` §"Coverage and suite-quality metrics" at the tiers where its runtime cost is affordable, which in practice means the unit and component tiers; at tiers where it isn't affordable (E2E in particular), the review-only criteria and negative verification below are the substitute, and their application there is **MUST**, not **SHOULD**
- A test that claims to change server-side state but whose run produces no corresponding request **MUST** be treated as a falsifiability suspect; request-per-test evidence, already retained as triage material per `spec/project/e2e-test-stability/` §F, **MAY** be consulted for this purpose during review and analysis
- An assertion that has never failed in any recorded run is a candidate suspect, but per-assertion outcome history isn't obtainable with mainstream tooling and per-test history exists only window-bounded in a dedicated test-analytics store (see the settled Open Question); where such a store exists, a never-failed-in-window test **MAY** be used to rank suspects for review and **MUST NOT** be treated as proof in either direction, because history can't distinguish "can't fail" from "hasn't failed yet"

### Detection: Review criteria

- A reviewer grading a test against this spec **MUST** be able to answer, for each test: what input would make this fail; what does this assert that a stub returning empty values wouldn't satisfy; and if the feature under test were deleted, would this test notice
- When no satisfying answer exists for one of the three questions above, the reviewer **MUST** file a finding citing the closest `Tn` category rather than waving the test through
- A reviewer grading a test that relies on a test double **MUST** additionally answer, about that double and **restricted to the dimensions the test relies on**: is there an input the real collaborator would reject and this double accepts, and is there a field the real collaborator discards and this double preserves. This question's polarity is the **reverse** of the three above, and reading it the same way inverts the rule: here a *yes* on a relied-on dimension is the finding and **MUST** be filed as `T9` unless the double can't be made faithful along that dimension **and** the divergence is already declared in it, which is the two-part exemption `spec/project/test-pyramid-foundation/` §"Test-double taxonomy" grants. A *no* closes the question. Both bounds are load-bearing, and so is the exemption's second half: every stub is more permissive on *some* axis it was never asked about, so grading unrelied-on axes would bury the category in noise—but a divergence that's merely *declared* while remaining trivially closable is still the defect, or the rule could be neutralized by adding a comment. It's deliberately the mirror of the stub question above, which asks what a double returning **too little** would satisfy and therefore can't reach a double accepting **too much**

### Negative verification

- When a test is added to cover a confirmed defect (a regression test), the author **MUST** demonstrate that the test fails against the pre-fix code—by reverting the production change or an equivalent controlled experiment—and **MUST** record the evidence (the command and the observed red result) in the change's audit trail: the commit message, the PR body, or the run protocol
- A fix that closes a confirmed `T9` by **tightening a double** rather than by adding a test **MUST** record the same evidence in the same places **where that run is still obtainable**: the command and the observed red result from a run made with the double tightened and the production defect still present. The trigger is the confirmed defect, not the shape of the change that covers it, so a `T9` fix carrying no new test isn't exempt on that ground
- Where the production fix landed **before** the permissive double was recognised—the retrospective case, and the one this category was first recorded from—no such run exists to make, and the obligation above is unsatisfiable rather than merely unmet. Such a finding **MUST** be resolved into the third state of §"Findings, severity, and the gate" (not fixable without a named prerequisite), naming the absent pre-fix state as that prerequisite. A finding left carrying an obligation nobody can discharge is the process defect that rule exists to prevent
- This extends the red-before-green requirement of `spec/project/test-cycle-foundation/` with an evidence obligation; a claim of "the test was red first" without recorded evidence doesn't satisfy this spec
- A generation process that can't execute the suite it scaffolds (an agent restricted to collection-only runs) **MUST** hand negative verification over as an explicit work package for the operator or the executing session—never silently drop it

### Prevention: Designing for falsifiability

- A reader **MUST** distinguish "not found" from "found and empty" and fail loudly on the former; returning an empty value for "I couldn't look" is the common root of T2 and T3
- A state-changing helper **MUST** verify its effect and fail loudly when the effect never materializes; the E2E instance of this rule is owned by `spec/project/e2e-test-stability/` §D and §G, and this spec extends it to every tier and to the synthetic-event cases of T4
- A fallback chain **MUST** terminate in a failure; a chain whose last link silently succeeds is T5 waiting to happen
- A locator **MUST** be unambiguous within its page or page object; identical selectors under different names are a T6 defect regardless of whether they currently resolve to the same element
- Product code **MUST** make every value worth asserting addressable without guessing: a UI that renders different DOM shapes per breakpoint exposes the same key-based hooks in every shape, and position-based access is a defect on every viewport, merely undetectable on the widest one. The web instantiation of this principle is owned by `spec/frontend/testability-identifiers/`; this spec states the principle so non-web surfaces inherit it too
- Every test **MUST** execute at least one assertion on its passing path: the check sits on the unconditional path of the test body—never behind a condition, an early return, or an uncalled helper—regardless of whether further teardown follows it, and an assertion made per element of a collection **MUST** be preceded by an assertion that the collection isn't empty. This is the design-time form of T8, and it's what makes the other prevention rules matter—a reader that fails loudly protects nothing if no assertion consumes it
- An assertion **SHOULD** name, in the test's own documentation, an input that would break it, so a reviewer can check falsifiability without reconstructing it

### Findings, severity, and the gate

- A confirmed non-falsifiable test **MUST** be classified Critical and a suspected one at least Warning—never Suggestion or Info—mirroring the swallowed-error severity floor of `spec/project/source-code-review/`: a test that can't fail is a no-go, not a style preference
- A confirmed `T9` **MUST** carry that same Critical floor even though its assertion is, on its own, falsifiable: the test still can't fail for the reason it claims, because the arrangement excludes the state that would break it. Reading the floor as assertion-only would exempt the one category whose assertions look strongest, which is precisely the category that hid a shipped defect behind six passing tests
- A falsifiability finding **MUST** be resolved into exactly one of three recorded states: fixed; deferred with a written justification and a tracking pointer per `spec/claude/review-plan/`; or not fixable without a named prerequisite (a product hook, a tooling capability), routed as its own work package. A finding silently dropped is a process defect
- Mutation score and every other suite-quality signal derived from this spec **MUST NOT** become a required category of the local quality gate: `spec/project/quality-gate/` excludes coverage thresholding from the required set so local and CI runs stay identical without forcing instrumentation on every run, and the same reasoning—plus the runtime cost of mutation testing against the gate's timeout budget—applies with more force here. A repository **MAY** expose a mutation run as an additional declared gate category under that spec's MAY-extend rule; the default is advisory

### Binding into review and generation processes

- The tier reviewer processes (unit, component, integration, contract, E2E) **MUST** carry falsifiability as a named checklist dimension citing this spec's `Tn` identifiers—an explicit grading area, not a footnote
- The tier generator processes **MUST** apply the prevention rules so newly scaffolded tests are falsifiable by construction, and **MUST** include the negative-verification step (or its hand-over work package) in their output
- Test-code adaptation **MUST** check the doubles a red case relies on for `T9` before attributing that case's outcome to production code: a double more permissive than what it replaces sends the causal trace to the wrong place, so the adaptation would either declare correct production code faulty or bend it to satisfy an arrangement production can't reach. What happens next isn't for this spec to decide: `spec/project/test-cycle-code-adaptation/` owns the phase and states the routing, including that an independently confirmed defect stays in the cycle while the permissive double travels alongside it. This spec contributes the category and the pre-check, never a competing output contract
- Test-result analysis **MUST NOT** treat a pass as automatic evidence of correctness: when triaging around a confirmed defect, the analysis **SHOULD** flag neighboring tests whose green status the defect should have broken, as falsifiability suspects for review
- Source-code review and its language and surface profiles **MUST** treat T1, T3, and T8 shapes in test code as ordinary review findings under their existing dimensions, citing this spec for the criteria; T8 supplies the criteria behind the assertion-free-test wording those dimensions already carry
- Test-pyramid assessment **MUST NOT** count tests flagged as non-falsifiable toward tier coverage; a tier whose tests can't fail isn't coverage, and pyramid shape computed from such tests overstates confidence
- Test-case derivation and scenario generation (including BDD scenario work) **MUST** reject an expected result that's not observable—an unobservable expectation guarantees a T2 assertion downstream—and **MUST** reject a case or scenario that states no expected result at all, which guarantees T8

## Acceptance Criteria

## Open Questions

All five research mandates were discharged on 2026-07-25. The struck-through originals stay for the record; the triangulated sources live in §Sources.

- ~~**Mutation-testing feasibility per tier (research mandate).** Which tools per ecosystem, what runtime cost, what score is meaningful, and whether a targeted mutation run over only the code a suspect test claims to cover is affordable at the slower tiers. Discharge requires tool-level findings with sources; until then the tier split in §"Detection: dynamic criteria" stands on the campaign's experience alone~~ **Settled (2026-07-25): affordable at the unit and component tiers via coverage-targeted test selection; targeted runs are scoped by glob or diff; no universal score threshold is meaningful; the E2E tier stays out of scope.** Mature tools exist in every relevant ecosystem (mutmut and cosmic-ray for Python, Stryker for JS/TS and .NET, pitest for the JVM); the cost model is mutants times the runtime of the covering tests, which coverage-targeted selection (built into pitest, Stryker's per-test coverage analysis, and mutmut 3) keeps in the minutes for fast suites and nothing keeps affordable for E2E, where per-test coverage mapping doesn't exist. Targeted mutation over a suspect's code is practical today via mutation-scope globs, diff-scoped runs, and incremental modes. Score thresholds are project-configured (Stryker defaults: high 80, low 60, break off); equivalent mutants make a 100% target meaningless, and the largest published at-scale practice mutates only changed code and reviews surviving mutants instead of chasing a score
- ~~**Per-assertion outcome history (research mandate).** Whether "this assertion has never failed in any recorded run" is obtainable in practice—test-framework hooks, result-format extensions, CI retention—and at what cost. Potentially the highest-signal detector; currently unavailable~~ **Settled (2026-07-25): not obtainable per assertion with mainstream tooling; obtainable per test only window-bounded through a dedicated test-analytics store; demoted permanently to a suspect-ranking heuristic.** Passing assertions leave no record anywhere in the mainstream pipeline: test-framework reports are per test (the pytest assertion-pass hook is opt-in and persisted by no mainstream consumer), the JUnit XML format carries per-testcase results with assertions only as a count attribute that major consumers ignore, and raw CI retention (90 days default, 400 maximum, logs with no index) can't answer cross-run queries. Dedicated stores retain per-test history for 14 days to about 3 months, and none exposes never-failed as a first-class query. Structurally, history can't distinguish "can't fail" from "hasn't failed yet," so the sound detectors remain mutation testing and negative verification
- ~~**Static-check accuracy (research mandate).** For each criterion in §"Detection: static criteria": prototype it, measure the false-positive rate against a real repository, and decide lint-error versus lint-warning versus review-prompt per the effective-signal governance of `spec/project/test-tier-static-analysis/`~~ **Settled (2026-07-25): a five-check prototype was measured against the evidence repository; tautology checks are lint-error material, the structural checks are lint-warning or review-prompt material, and type-dependent checks stay review-only.** An AST prototype covering five criteria, run against the 144 test files of `nolte/kamerplanter` (first-party measurement, 2026-07-25): tautological comparisons scored 9 hits with no false positive in the sample (lint error); empty exception handlers in test code scored 50 hits at roughly three-quarters sampled precision, the false positives being fall-through and retry control flow, so the check should only flag a handler that ends the helper without a compensating action (lint warning); the empty-default reader shape scored 40 hits that accurately detect the shape while the defect verdict depends on the call site (lint warning routed to review); duplicate locator constants scored 19 hits with every sampled hit genuine (lint warning); `is not None` tautology detection needs type information and in its naive form flagged only legitimate optional-return assertions (review prompt, not a lint rule).
