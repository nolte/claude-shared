# End-to-End Failure Diagnosis

Status: draft

## Context

A full-suite stabilization campaign over a consuming project's E2E suite (`nolte/kamerplanter#768`, Selenium + pytest, Docker-composed stack, seven browser profiles) drove a mobile profile from 141 failures to green across six full runs (about four hours of pure runtime plus triage). The 141 failures collapsed into **six root causes**. Fixing each was cheap — usually one locator, one prop, one line. What consumed the time was **misattribution**: on three separate occasions a plausible, well-argued fix addressed something real but not the thing that was red, and one of those fixes *amplified* the actual cause, turning eight green tests red.

The dominant failure mode of E2E triage is therefore not "hard bug" — it is "confident wrong hypothesis". A companion campaign finding was worse: eight tests that were **green for the wrong reason**, each producing a pass or an empty result and never an error, two of them wrong on the desktop profile for years without any run reporting it. A red test costs an hour; a green test that asserts nothing costs the credibility of the whole suite.

`spec/project/e2e-test-stability/` owns how to *write* a suite that does not produce these hazards (interaction mechanics, truthful signals, responsive geometry, the stabilization loop); `spec/project/e2e-test-automation/` owns the suite's *shape*; `spec/project/test-cycle-result-analysis/` owns the red-side classification taxonomy. None of them owns the **diagnostic discipline** that establishes *what actually happened* before anything is changed. This spec owns that discipline: how to classify a cluster and prove its mechanism, which artefact settles which question, how to instrument a test that will not tell you why it failed, how to hunt the assertions that never fail, how to run independent evidence channels in parallel, how to build a per-library hazard catalog, which automation semantics mislead a diagnosis, and how to decide test defect versus product defect. It is grounded in the campaign and in the diagnostic literature of adjacent disciplines; each rule is written to be **testable** — an agent can tell whether it was followed.

## Goals

- Make **classification and mechanism-proof gate every remediation**, so a fix is never coded against a correlation.
- Give a **channel-to-question map** so an agent reaches for the artefact that can settle a question and distrusts one that cannot.
- Make the **green-for-the-wrong-reason class** (vacuous assertions, silent-empty readers) a first-class, systematically hunted category with a detection procedure.
- Encode the **orchestration patterns** (parallel multi-channel triage, refutation-authorised dispatch briefs) that made the campaign's hardest questions decidable.
- Define **how to build and maintain** a per-component-library hazard catalog rather than hard-coding one library's quirks.

## Non-Goals

- The suite's runtime-stability *design rules* (interaction hazards, truthful signals, responsive hazards, the stabilization loop, the cost model and stop criteria) — owned by `spec/project/e2e-test-stability/` (§C, §D, §G, §F). Issue topic §8 (cost model and stop criteria) folds into that spec's §F, not here.
- The coordinate-clicking strategy matrix and the `elementFromPoint` guard — owned by `spec/project/e2e-test-stability/` §C. This spec consumes them for diagnosis; it does not restate them.
- The falsifiability taxonomy, its static/dynamic/review detection criteria, and negative verification — owned by `spec/project/test-falsifiability/`. This spec's §D is the *diagnostic hunt* that routes into that taxonomy.
- Implementing a linter, a mutation-testing gate, or a triage harness. This spec defines procedures; the tooling is separate work (see §Open Questions).

## Requirements

### A. Classify before touching, and prove the mechanism

- Triage **MUST** be **cluster-wise, never test-wise**: group non-pass results by failure *site* (top traceback frame) and *message shape* before diagnosing, and diagnose the cluster once. Expect roughly one to two root causes per fifty failures; individually triaging N failures re-diagnoses the same mechanism N times. Co-failure across unrelated tests is itself evidence of a shared systemic cause (environment, network, dependency), not N independent bugs.
- Every cluster **MUST** be assigned exactly one primary class from `spec/project/test-cycle-result-analysis/` before any change, because the admissible proof and the correct fix differ per class.
- A hypothesis is **not actionable** until a **mechanism is demonstrated**. Exactly one of these **MUST** hold for the cluster:
  1. **Reproduced outside the suite** — a standalone, scriptable oracle reproduces the failure deterministically and its inverse passes (the `git bisect` / delta-debugging bar: a repeatable pass/fail oracle with one variable toggled).
  2. **Isolation asymmetry** — the failure toggles with one controlled variable (run order, RNG seed, single-test isolation, or a bisected commit), everything else held constant. For order-dependence this is the victim-versus-brittle test: passes alone but fails in-suite is a victim (prior-state pollution); still fails alone is brittle (intrinsic).
  3. **Discriminating counter-example** — derived from library source or an instrumented probe, an observation the leading hypothesis predicts and every rival hypothesis excludes (detached-mid-click versus overlay-covered versus not-yet-rendered are distinguished by mutually exclusive signatures, for example distinct exception types).
- A correlation, a single green re-run, or a plausible story **MUST NOT** be treated as a demonstrated mechanism. This is the fault-tree bar: the named cause must be shown *sufficient* (its presence produces the failure) and *necessary* (its absence removes it), not merely co-present.
- A change that addresses something real but **not** the failure **MUST** be reverted: it consumes a run and can amplify the actual cause. Record which changes did not fix what they targeted.
- **The single most decisive artefact is a discriminating counter-example across an A/B that varies one factor.** Where such an asymmetry exists (identical UI passing under one locator style and failing under another; fifteen page objects on `div[role='dialog']` failing while six on `data-testid` pass on the same pages), it **MUST** be constructed and recorded — it settles "test bug versus product defect" in one step where screenshots alone are ambiguous.
- **After a mechanism is proven, search for existing work on that mechanism before fixing it** (issue comment §G). File a finding against the *mechanism* the moment it is proven, so a parallel effort recognises it; two efforts that both start from the same symptom cannot see each other when the tracking artefacts describe only the symptom.

### B. Evidence channels — which artefact settles which question

- An agent **MUST** match the artefact to the question and **MUST NOT** draw a conclusion from a channel that structurally cannot answer it. The canonical map:

  | Question | Channel that settles it | Channel that cannot |
  |---|---|---|
  | What did the app show? | screenshot / video / DOM snapshot | server logs |
  | Did the action actually happen? | server request log, counted per run and diffed against a passing run | screenshot, JUnit verdict |
  | Is the element reachable? | viewport-only screenshot + `getBoundingClientRect` | full-page (`captureBeyondViewport`) screenshot |
  | Is this a flake? | run history across N runs + isolation asymmetry | a single green re-run |
  | Which DOM node received the click? | `document.elementFromPoint` at the click centre, captured at the failing action | anything read after the fact |
  | What was the DOM at step N? | a time-travel trace (where the framework has one) | a still or a live event stream |

- **Provenance before conclusion.** An artefact's filename is not proof of which configuration produced it. Every artefact **MUST** be paired with the run manifest / result file it belongs to (test id, worker, build SHA, profile) before any provenance-dependent conclusion is drawn. In the campaign, a mobile `backend.log` was read as a desktop run and a test bug was escalated to the operator as user-facing data loss; the desktop runs in fact showed the writes succeeding.
- **A count of zero is the least trustworthy measurement**, because "the thing never happened" and "I looked in the wrong place / the interceptor never armed" are indistinguishable from the number alone. A zero **MUST** be admitted only behind a **positive control**: first prove the channel captures a request it is guaranteed to see.
- **Escalating a product defect carries an evidentiary burden proportional to its consequence.** A claim of user-facing data loss **MUST** rest on a positive control *and* a second independent channel before it reaches a human.
- **The full-page-screenshot trap.** A capture taken with `captureBeyondViewport` / full-page expands the rendering surface to the document's scroll height, so viewport-unit (`100vh`), `height:100%`, and `position:fixed` elements resolve against the enlarged surface and the vertical layout no longer reflects what a real viewport showed. Such a screenshot **MUST NOT** be used to answer "is this below the fold"; its *width* still reveals horizontal overflow. A viewport-only screenshot **MUST** be captured alongside any full-page capture.
- **Soft-failure outcomes leave incomplete artefacts** (issue comment §F). A non-strict expected-failure that fails is reported as a non-failure by common harnesses, so a harness that captures artefacts only on the final red verdict keeps no screenshot and no traceback for exactly the tests already flagged as suspect. The artefact-capture gate **MUST** be driven by "an exception or failure occurred during the test body", not by the framework's final green/red verdict.
- **Per-framework channels** (named concretely; a diagnosis relies on the channel that exists, not the one assumed):
  - **Playwright** — Trace Viewer (action timeline + before/action/after DOM snapshots with the click-coordinate marker + screenshot film strip + Network tab with request/response bodies + Console tab); `recordHar` for a diffable request ledger; `page.on('console'|'request'|'response'|'pageerror')` and a CDP session for live streams. It owns a time-travel DOM snapshot.
  - **Cypress** — command log with per-command before/after DOM snapshots (the time-travel equivalent); automatic failure screenshot; `cy.intercept` (request channel, spy or stub) and `cy.request` for direct server assertions; `cy.task` for Node-side facts the browser cannot emit. Run **video is off by default since v13** and must not be assumed present.
  - **Selenium / Grid** — WebDriver BiDi console + network events (`beforeRequestSent` / `responseStarted` / `responseCompleted` / `authRequired`; response bodies and per-request timing are not first-class); the deprecated Chromium-only CDP bridge for interception and Performance metrics; the `selenium/video` sidecar MP4 (opt-in via `se:recordVideo`, topology-dependent — verify the sidecar exists, do not assume); HAR only via an external proxy. **Selenium has no native time-travel DOM-snapshot channel** — "what was the DOM at step N" needs external instrumentation (a per-step `page_source` dump). Native screenshots are viewport-only; full-page is Firefox-native or Chrome-via-CDP.

### C. Instrumentation-first debugging

- When static analysis of code and DOM cannot decide *why* a test failed, the next step **MUST** be to make the test report more, not to guess. A silent helper **MUST** be converted into one that reports its own state at the failure point (the read-back value, the surrounding UI state), because the assertion must fire *on the observed value* so the framework's automatic expected-versus-found output engages.
- A failure message **MUST** satisfy a four-part rubric — it names (1) **expected**, (2) **found** (read back from the live subject, not restated from the predicate), (3) **surrounding UI state**, and (4) the **most-likely cause as a mechanism**. A message that could be produced by more than one mechanism fails the rubric. Contrast `Option 'FREQ=WEEKLY' not found in the open dropdown` (three mechanisms produce it) with `expected 'FREQ=WEEKLY', field holds 'FREQ=MONTHLY' — the click most likely landed on a neighbouring option` (names the mechanism).
- Instrumentation that **stays** in the suite (a custom matcher, a self-reporting helper, a labelled assertion message) **MUST** be preferred over throwaway probe code, so the next failure of that class arrives already explained.
- Framework-automatic context **SHOULD** be exploited before hand-writing it, and hand-written context **MUST** carry what the framework cannot infer (the mechanism sentence, the surrounding state):
  - **pytest** — assertion rewriting shows both operands and the sub-expressions that produced them, plus type-aware diffs, automatically; a `, "message"` clause is additive. Assertion rewriting reaches only test modules, so an extracted helper library **MUST** be registered with `register_assert_rewrite` or it goes silent.
  - **Playwright** — `expect()` web-first matchers auto-retry and emit matcher, locator, timeout, expected/received, and a call log; the `expect(locator, 'cause')` message argument is where the mechanism sentence goes; `expect.poll` / `expect.toPass` extend auto-retry to custom conditions; `expect.soft` lets one run report several findings.
  - **Cypress** — retry-ability re-runs the query chain until the assertion passes or the command times out; `.should(callback)` is the idiom for a self-reporting helper that reads back the live subject; the `expect(value, 'label')` message argument disambiguates which expectation failed.

### D. Hunt vacuous assertions and silent-empty readers as a category

- A reader that can return an empty value **MUST** distinguish "empty" from "not found" and **MUST** fail loudly on the latter. Returning `""` / `[]` / `None` for "I could not look" is the defect.
- An assertion that passes on a reader's empty value is **vacuous** and **MUST** be reported as a finding, not left because it is green. An always-true assertion (for example `assert count >= 0`) is vacuous by construction.
- A helper that swallows an exception (`except …: pass`) around a post-condition **MUST** be treated as a suite defect regardless of current test status.
- Every fallback chain **MUST** have an explicit terminal failure. A fallback onto a selector that yields nothing converts a loud failure into a silent pass — the mechanism behind four of the campaign's eight instances (a navigation helper that fell back to direct URL navigation stopped exercising the sidebar it was named after, while staying green).
- The hunt **MUST** be systematic, layered from cheap-mechanical to dynamic-proof (findings route into `spec/project/test-falsifiability/`, which owns the taxonomy and severities):
  1. **Syntactic sweep (mechanical, every change).** Enable the lint rules that catch the syntactic shapes: bare `except: pass` / `except: continue` around a wait or post-condition (Ruff `S110` / `S112`, Bandit `B110` / `B112`), an `assert` inside an `except` block (Ruff `PT017`), a structurally always-true assertion such as an assert on a tuple literal (Ruff `F631`).
  2. **Enumerate empty-default readers.** Statically list every reader whose body can `return ""` / `[]` / `None` on a non-exceptional path (an AST pass over function definitions).
  3. **Trace assertions to those readers.** Flag any `assert`/`expect` comparing to an empty or falsy value whose operand traces to a step-2 reader — expressible as a custom dataflow rule (a Semgrep taint rule from the empty-`return` source to the equality-assert sink, or an AST join).
  4. **Prove falsifiability dynamically.** Where the tier allows it, run a mutation-testing gate on the changed files: a *surviving* mutant whose covering test still passes is a proof-by-construction that some assertion never fails. Coverage cannot see this defect — a called-but-unchecked return still counts as covered — so mutation score, not coverage, is the credibility signal.
  5. **Cross-check history.** A test that has executed many times and never once transitioned to a failure is a tautology *candidate* for review, not a proof.

### E. Parallel multi-channel triage and dispatch briefs

- Where several evidence modalities bear on one run, the diagnosis **SHOULD** dispatch **independent read-only analyses in parallel, one per modality**, rather than one sequential pass, because modality-partitioned channels have structurally decorrelated error, whereas same-modality analyses repeat each other's blind spots.
- Each channel **MUST** be briefed on **exactly one** evidence modality and **MUST** be blinded to the others (the code channel receives no screenshot; the pixel channel receives no source path), so the channels do not converge on the same evidence.
- Each channel **MUST** return what it settled *and* an explicit list of what it **could not** settle; an unstated gap reads to the orchestrator as "settled". A channel's contradiction or could-not-settle return is a first-class outcome.
- The orchestrator **MUST** compose, not vote: attribute each claim to the modality that owns it ("what the app showed" to the pixel channel, "what the server did" to the request-log channel), treat convergence of two independent channels as corroboration, carry every uncovered could-not-settle back as a residual open question, and on a conflict **stop-and-surface** rather than majority-rule (per `spec/claude/research-triangulate/`).
- Channel selection **MUST** cover the symptom: the code and pixel channels are the mandatory pair; a server/request-log channel is added for a timeout, a state-change assertion, or a data mismatch; a browser console/network channel is added for a no-op interaction or a suspected client crash. One channel per modality; never two analyses on the same modality.
- **Dispatch briefs MUST authorise refutation** (issue comment §H, sited here as the authoritative rule; it is not E2E-specific). Wherever a skill or agent dispatches analysis or remediation, the brief **MUST** state its hypothesis *and* explicitly authorise and expect the specialist to refute it: *if the evidence contradicts this, say so and change nothing rather than forcing the fix to fit.* Without the clause a specialist optimises for completing the stated task; with it, the campaign's specialists corrected the orchestrator's brief roughly ten times, substantively. A brief that omits the refutation clause is a defect.

### F. Library-specific hazard catalogs — how to build and maintain one

- A component-library hazard catalog **MUST** be built by reading the component's **installed source** (`node_modules`), not its documentation, because the behaviours that break E2E tests — which DOM event opens versus activates a control, which ARIA role a variant emits, where the node is portalled, where focus lands, and how positioning or scroll side-effects move the element — live in source and diverge from prose.
- **The installed version MUST be resolved from the lockfile, never trusted from documentation.** Version drift in the documented stack is itself a diagnostic hazard: in the campaign the docs claimed one major version while the lockfile resolved another, and several behaviours specific to the resolved version drove the analysis. An agent can mechanically diff the documented version against the lockfile and flag the mismatch.
- Each catalog entry **MUST** record: (1) component + resolved semver range; (2) trigger event versus activation event; (3) ARIA role and `aria-*` emitted **per variant**; (4) portal placement (portalled, `disablePortal`, `keepMounted`); (5) focus target on open; (6) positioning and scroll side-effects; (7) the resulting stable selector strategy; (8) a source anchor (file + symbol). This schema is what makes an entry re-verifiable against source on a version bump.
- The catalog **MUST** be re-verified against source on each major version bump; entries are pinned to the semver range they were verified against. A major bump is a breaking-behaviour boundary for exactly these internals.
- The worked example (recorded as illustration, not as the catalog's fixed content): a menu item is `role="menuitem"` in a plain menu but is cloned to `role="option"` inside a select's `role="listbox"`; the select opens on `mousedown` while its items commit on `click`, so a synthetic `click` on the trigger is a silent no-op; the popover clamps upward near the viewport edge; `keepMounted` leaves closed menus in the DOM so presence is not visibility; the selected-menu variant auto-scrolls and focuses the selected (not first) item; unrecognised props spread onto the form-control root, so a `data-testid` can land on a wrapper whose geometry shifts when helper text wraps.

### G. Automation semantics that mislead a diagnosis

- An agent diagnosing a **silent** interaction failure (no error raised, yet the effect did not happen) **MUST** recognise the automation-semantic traps that produce it and confirm which one was hit, rather than assuming the element was absent. The **remediation** of a wrong-target click is owned by `spec/project/e2e-test-stability/` §C (the click-strategy matrix, the decision procedure, the `elementFromPoint` guard); this section is the **diagnostic** reading of the same semantics and does not restate the matrix.
- The traps that raise no error and therefore mislead a diagnosis:
  - A clickable-condition (`element_to_be_clickable` and equivalents) is satisfied by displayed-and-enabled **regardless of viewport position**; a naked click on such an element then fails to interact.
  - A click whose centre lands on a **descendant** of the target raises no interception — it is a silent no-op or a wrong-target activation. No mainstream framework closes this descendant-tolerance gap by design.
  - Coordinate-based synthetic events (`ActionChains`, raw CDP input) perform **no interactability hit-test** and deliver to whatever sits at the point, so they are not a safe fallback despite looking like one.
  - An untrusted script click (`HTMLElement.click()`, `dispatchEvent`) is coordinate-independent but fires no `mousedown` and reports `isTrusted=false`, so it is a silent no-op against a `mousedown`-only opener or an `isTrusted`-guarded handler.
  - A displayedness check can return false for an element merely clipped by a scrollable ancestor, conflating "not rendered for this state" with "scrolled out of view".
- The diagnostic value of naming the trap is that **Playwright and Cypress eliminate several of these by design** — mandatory scroll-into-view plus a receives-events hit-test remove the viewport-position and non-descendant-overlay silent failures, and real input removes the no-`mousedown` failure — while **both retain descendant-tolerance and both expose a `force` opt-out that reintroduces the silent wrong-target**. Which framework a suite runs on therefore changes which of these hypotheses is even admissible; that fact belongs in the diagnosis and materially informs the framework conversation.

### H. Test defect versus product defect — the ordered decision procedure

- Deciding test-defect versus product-defect is a differential-diagnosis problem — one evidence set, two competing hypotheses, ordered rule-in/rule-out branches. It **MUST** be run as an ordered procedure, not a checklist, because the first branches are validity gates whose violation silently corrupts every later conclusion. Each branch names the evidence that discharges it and the failure mode of skipping it:
  0. **Artefact provenance (validity gate).** Confirm every artefact belongs to the profile/run it is labelled with (filename/metadata to test id, worker, build SHA) **before** any provenance-dependent evidence is trusted. Skipping this escalated a test bug into a reported product defect in the campaign.
  1. **Locator-style correlation (cheap, near-decisive).** If identical UI on the same build passes under one locator style and fails under another, the differentiator is the locator — a **test bug**. Construct the A/B that varies only the locator.
  2. **Human-reachability.** If a screenshot or trace shows the target in an open, rendered dialog and it passes the full actionability set (visible, stable, receives-events at the click point, enabled), it is reachable — the **test is wrong** (wrong wait, frame, or locator). A lone visibility signal is insufficient; require the full set.
  3. **Viewport-specific is not automatically a test bug.** A control genuinely unreachable at a narrow viewport but reachable wide is a **product defect** (responsive / target-size), not test noise. Discharge requires per-viewport reproduction plus evidence that no equivalent affordance exists at the narrow width — not "element not found at 393 px" alone.
  4. **Profile-independence (only after branch 0).** A clean, isolated context changing one variable at a time separates environment/state causes (passes clean, fails dirty) from a genuine defect (fails in both). Profile-independence is strong evidence *when the per-profile artefacts are correctly attributed* and misleading otherwise.
- Every branch is machine-checkable (artefact SHA/test-id match, locator-only A/B diff, `elementFromPoint` hit-target equality plus non-empty bounding box, per-viewport reproduction, per-profile pass/fail matrix), so an agent can record which branch discharged the verdict and on what evidence.

## Open Questions

Every per-topic research mandate was discharged on 2026-07-26; the sourced findings live in §Sources. The residual questions below are the parts that could not be settled decisively and are carried with a revisit condition, per the acceptance criterion that none is silently dropped.

- **Actionable-confidence bar (§A).** Medicine iterates hypotheses until confidence crosses a stated threshold; the analogous "actionable" bar for an E2E hypothesis (a required repro-count such as N/N deterministic or k failures in M isolated runs) is not fixed. *Revisit* once the campaign's per-category repro-rate data is available; set the bar from the observed victim/brittle/async-wait distribution.
- **Positive-control citation (§B).** The positive-control rule for a zero request-count is imported from experimental method and the flaky-assertion literature; no framework doc or testing paper formalises it natively. *Revisit* if a Playwright/Cypress/Selenium doc or a peer-reviewed source states it; until then it is cited as a borrowed principle.
- **Mutation-score floor (§D).** The floor value and scope (changed lines versus module) and the precision of the empty-default-reader dataflow rule through page-object indirection are not fixed. *Revisit* after a baseline mutation run and a pilot of the dataflow rule against the eight known instances; a follow-up issue owns any implemented linter or gate.
- **Multi-channel ceiling and selection (§E).** Whether four channels is the right ceiling (DOM-snapshot and video as distinct modalities), whether channel 3/4 selection should be automated from the symptom, and the real cross-channel error correlation are open. *Revisit* after at least ten real triage runs.
- **Selenium channel evolution (§B).** Whether WebDriver BiDi will expose response bodies and per-request timing, the CDP-removal release, and which HAR proxy is the portfolio standard are unresolved. *Revisit* when `selenium.dev` documents native BiDi-to-HAR export or announces the CDP-bridge removal release.
- **Displayedness direction (§G).** Whether a displayedness check returns false for a scrollable-ancestor-clipped element is documented as inconsistent, and `e2e-test-stability` §C already carries this as unconfirmed. *Revisit* by reproducing on the reference Selenium + pytest profile per driver before stating the direction normatively.
