# Projekt-Release-Artefakt

Status: draft
Portfolio-Scope: portfolio

## Kontext

Leser: Repo-Maintainer von Hobby-Projekten im nolte-Portfolio, deren `sprint-review`-Skill Sprints durch Validierung einer Artefakt-Referenz schließt, sowie die Implementierer von `sprint-review` und der `release-skill-layer`-Skills, die gegen diese Taxonomie bauen.

Die Geschwister-Spec `sprint` verlangt, dass jeder geschlossene Sprint über `artifact_ref` auf ein konkretes ausrollbares Artefakt zeigt und dass dieses Artefakt das `value_statement` des Sprints für den Endnutzer materialisiert. Sie sagt bewusst nicht, welche Form diese Referenz hat, welche Artefakt-Arten für welchen Projekttyp gültig sind oder wie die Referenz beim Sprint-Abschluss validiert wird. Diese Spec füllt diese Lücke. Sie definiert die **Artefakt-Taxonomie** je Portfolio-Projekttyp, die **Form von `artifact_ref`** für jede Art, die **Validierungsregeln**, die `sprint-review` beim Abschluss laufen lässt, und die **Dispatch-Grenze** zur bestehenden Release-Maschinerie (`release-automation` für den Übergang Draft → Veröffentlicht, `release-skill-layer` für operatorseitige Kuratierung und Auslösung). Sie definiert diese Maschinerie nicht neu; sie ist die Schicht, an der sprint-seitige Planung auf release-seitige Ausführung trifft, und ihre Aufgabe ist es, beide vor Drift zu bewahren.

## Ziele

- Die Artefakt-Taxonomie je Projekttyp festlegen (Claude-Plugin, Python-Anwendung, Python-Bibliothek, Node / TypeScript Library oder App, CLI-Tool, dokumentations-only) anhand derselben Projekttyp-Signale wie `github-issue-templates-apply` und `release-skill-layer`, damit Portfolio-Verhalten konsistent bleibt.
- Die Form von `artifact_ref` je Art festlegen (Release-Tag, Container-Image-Tag, Plugin-Version, Paketmanager-Version, Doc-Site-Deploy-URL) und welche Felder ein Sprint-Review **MUSS [MUST]** prüfen, bevor `review → closed` zugelassen wird.
- Die Dispatch-Grenze festlegen: wenn `sprint-review` Release-Maschinerie anfasst, dispatcht es `release-skill-layer`-Skills (`release-notes-curate`, `release-publish-trigger`) und **DARF NICHT [MUST NOT]** `gh release edit --draft=false` oder andere von `release-automation` deklarierte verbotene Pfade aufrufen.
- Festlegen, wie Out-of-Band-Artefakte (Hotfixes, mid-sprint Notfall-Releases) erfasst werden, damit sie die Sprint-Kadenz nicht verschmutzen, aber im Projekt-Datensatz auffindbar bleiben.
- Portfolio-weit wiederverwendbar bleiben: jedes adoptierende Repo kann seine Artefakt-Regeln allein aus dem Projekttyp-Signal ableiten, ohne pro-Repo-Konfiguration über das hinaus, was `release-automation` bereits bietet.

## Nicht-Ziele

- `release-automation` zu ersetzen. Der Übergang Draft → Veröffentlicht ist Sache seines Workflows; diese Spec erklärt nur die Artefakt-Referenz und die Validierungsregeln beim Sprint-Abschluss.
- `release-skill-layer` zu ersetzen. Skill A (Kuratierung) und Skill B (Publish-Trigger) besitzen die operatorseitigen Verfahren; diese Spec erklärt nur, wann `sprint-review` sie **KANN [MAY]** dispatchen.
- `release-notes-audience-analysis` zu ersetzen. Audience-getriebene Inhalte sind dort beheimatet; diese Spec prüft nur, dass ein Artefakt existiert und seiner deklarierten Form entspricht.
- CI/CD-Systeme zu ersetzen. Existenz und Adressierbarkeit des Artefakts ist hier wichtig, nicht die Build-Pipeline, die es erzeugt hat.
- Den Sprint- oder Feature-Lifecycle zu definieren. Jedes davon gehört seiner eigenen Geschwister-Spec; diese Spec legt nur die artefakt-seitige Oberfläche fest.
- Semver oder eine spezifische Versionspolitik zu erzwingen, über das hinaus, was `release-drafter` im konsumierenden Repo bereits durchsetzt.

## Anforderungen

### Projekttyp-Erkennung

- **MUSS [MUST]** den Projekttyp anhand derselben Signale erkennen wie `release-skill-layer` und `github-issue-templates-apply`: `.claude-plugin/plugin.json` für Claude-Plugin, `pyproject.toml`-Form für Python-Anwendung versus Bibliothek, `package.json` für Node / TypeScript, deklarierter CLI-Einstiegspunkt für CLI-Tool, `mkdocs.yml` (oder Äquivalent) für dokumentations-only.
- **KANN [MAY]** ein Pro-Repo-Override unter `.github/release-skill-layer.yml` unterstützen (dieselbe Override-Oberfläche wie `release-skill-layer`), wenn die Auto-Erkennung daneben liegt; **DARF NICHT [MUST NOT]** eine neue Override-Datei einführen.
- **SOLLTE [SHOULD]** Hybrid-Repos (ein CLI-Tool plus eigene Doc-Site) als die dominierende veröffentlichbare Art behandeln; Cross-Art-Sprints sind eine offene Frage (siehe §Offene Fragen).

### Artefakt-Taxonomie

- **MUSS [MUST]** gültige `artifact_ref`-Formen je Projekttyp auf folgende Tabelle einschränken; Werte außerhalb der Tabelle schlagen die Sprint-Review-Validierung:
  - **Claude-Plugin**: eine im Marketplace veröffentlichte Plugin-Version, formatiert als `<plugin-name>@<version>` (zum Beispiel `nolte-shared@1.7.0`); die Version **MUSS [MUST]** zu `.claude-plugin/plugin.json` am Commit des Artefakts passen, und die Version **MUSS [MUST]** vom Marketplace-Katalog auflösbar sein (typischerweise durch Inspektion von `.claude-plugin/marketplace.json` plus erfolgreichem `claude --plugin nolte-shared@1.7.0` oder Äquivalent) — ein Git-Tag ohne marketplace-auflösbare Plugin-Version reicht nicht. Bis bestätigt ist, dass die `release-publish.yml` des konsumierenden Repos die Marketplace-Katalog-Aktualisierung end-to-end durchführt, **KANN [MAY]** ein Schritt außerhalb des Workflows (manuelle Bearbeitung von `.claude-plugin/marketplace.json` mit anschließendem Commit auf `develop` oder ein gleichwertiger Dispatch) diese Anforderung erfüllen, **vorausgesetzt** der manuelle Schritt wird in `## Review notes` gemäß §Validierung beim Sprint-Abschluss festgehalten; sobald der Workflow end-to-end bestätigt ist, **MUSS [MUST]** die manuelle Fallback-Klausel entfernt werden, und für jeden Sprint, der sie danach noch nutzt, **MUSS [MUST]** ein workflow-health-Finding erhoben werden.
  - **Python-Anwendung**: ein Git-Tag (`v<semver>`) **und** ein Container-Image-Tag unter einem veröffentlichten Registry-Pfad (`ghcr.io/<owner>/<repo>:v<semver>` oder Äquivalent); beide **MÜSSEN [MUST]** als Liste gesetzt sein (`artifact_ref: [v0.4.0, ghcr.io/owner/repo:v0.4.0]`), gemäß der unten beschriebenen Listen-Form-Regel.
  - **Python-Bibliothek**: ein Git-Tag `v<semver>` **und** eine veröffentlichte Distributions-Referenz (PyPI: `<dist-name>==<version>`); beide **MÜSSEN [MUST]** als Liste gesetzt sein.
  - **Node / TypeScript Library oder App**: ein Git-Tag `v<semver>` **und** die veröffentlichte Paket-Referenz (`<pkg-name>@<version>` für npm-veröffentlichte oder das Container-Image-Tag, wenn das Paket als Runtime-Image ausgeliefert wird); beide **MÜSSEN [MUST]** als Liste gesetzt sein.
  - **CLI-Tool**: ein Git-Tag `v<semver>`; falls das CLI auch als Binär-Asset oder Container-Image verteilt wird, **MUSS [MUST]** die zusätzliche Referenz als Listen-Eintrag erscheinen.
  - **HACS-Integration** (Home Assistant Community Store Custom Component): ein Git-Tag `v<semver>`; die Version **MUSS [MUST]** zum `version`-Feld von `custom_components/<name>/manifest.json` am Commit des Artefakts passen. Die HACS-Listing-URL **KANN [MAY]** als Listen-Eintrag erscheinen, sobald die Integration in HACS selbst veröffentlicht ist.
  - **Dokumentations-only**: eine datierte Deploy-URL (`docs.example.com@<YYYY-MM-DD>`); wenn die Doc-Site inhaltsadressiert ist, **KANN [MAY]** der Deploy-Commit-SHA als Suffix erscheinen.
- **MUSS [MUST]** `artifact_ref` entweder als einzelnen String oder als Liste von Strings unterstützen, gemäß Geschwister-Spec `sprint`. Die Listen-Form ist die Standard-Form für jeden Projekttyp, der zwei oder mehr gekoppelte Artefakte in einem Sprint ausliefert (die Mehr-Artefakt-Zeilen oben zeigen das); die Listen-Form ist auch die Eskape-Hatch für Hybrid-Projekttypen, die nicht in der Tabelle stehen, wenn ein Element zu einer Zeile oben passt und das andere zu einer anderen Zeile (zum Beispiel eine Python-Bibliothek, deren Sprint zusätzlich eine Doc-Site deployt: `[v0.4.0, dist@0.4.0, docs.example.com@2026-05-08]`). Der zeilenübergreifende Mix **MUSS [MUST]** in `.github/release-skill-layer.yml` als `artifact_kinds: [python-library, documentation-only]` deklariert werden, damit `sprint-review` weiß, welche Validierungs-Befehle zu laufen sind.
- **MUSS [MUST]** für jede Form sicherstellen, dass das Artefakt zum Zeitpunkt des Sprint-Abschlusses unabhängig erneut abrufbar ist (das Tag löst weiterhin auf, die Paket-Version existiert weiterhin, die Doc-URL liefert weiterhin den deployten Snapshot); das Greifen nach kurzlebigen Build-Artefakten, die sich selbst aufräumen, ist verboten. Langfristige Re-Fetchbarkeit nach Abschluss (Registry-Rotation, Tag-Löschung Monate später) ist außerhalb des Geltungsbereichs gemäß Geschwister-Spec `sprint` — eine separate Archivierungs-Sorge des konsumierenden Repos.
- **DARF NICHT [MUST NOT]** einen reinen Commit-SHA als `artifact_ref` akzeptieren, sofern das Projekt nicht ausdrücklich per SHA veröffentlicht und der Veröffentlichungsweg in `.github/release-skill-layer.yml` festgehalten ist.

### Validierung beim Sprint-Abschluss

- **MUSS [MUST]** beim Übergang eines Sprints von `review` nach `closed` durch `sprint-review` ausführen:
  - `artifact_ref` (String oder Liste) gemäß erkanntem Projekttyp und dem optionalen `artifact_kinds`-Override in `.github/release-skill-layer.yml` parsen;
  - jede Komponente der geparsten Referenz mit dem Verifikations-Befehl je Art auflösen — `git rev-parse <tag>` für Git-Tags, `gh release view <tag>` für GitHub-Releases, `docker manifest inspect <image>` für Container-Images, `pip index versions <dist>` für PyPI-Distributionen, `npm view <pkg>@<version>` für npm-Pakete, ein HEAD-Request für Doc-Deploy-URLs, und für Claude-Plugins sowohl `git rev-parse <plugin-version-tag>` plus eine Marketplace-Auflösungs-Probe (der genaue Befehl hängt vom Host-Katalog ab; für `nolte-shared` ist das das Lesen von `.claude-plugin/marketplace.json` an HEAD und die Bestätigung, dass die Plugin-Version gelistet ist);
  - bestätigen, dass der Commit des aufgelösten Artefakts (sofern anwendbar) gleich dem `last_commit`-Frontmatter-Feld des Sprints ist oder von diesem erreichbar; das `last_commit` des Sprints ist der autoritative Anker (gesetzt durch `sprint-execute` laut Geschwister-Spec `sprint`), und ein fehlendes oder null `last_commit` blockiert den Abschluss;
  - den Übergang blockieren, wenn eine Verifikation scheitert, und den fehlgeschlagenen Check wortgetreu sichtbar machen.
- **MUSS [MUST]** bestätigen, dass das Artefakt das `value_statement` des Sprints materialisiert. Die Prüfung wird an das Feature delegiert, dessen Frontmatter-Feld `verifies_sprint_value` nicht-null ist (laut Geschwister-Spec `feature`); wenn das benannte Akzeptanzkriterium dieses Features einen Verifikations-Mechanismus hat, der ein CLI-Befehl oder ein Skill-Aufruf ist, **KANN [MAY]** `sprint-review` so konfiguriert sein, ihn gegen das veröffentlichte Artefakt aufzurufen.
- **MUSS [MUST]** das Validierungs-Ergebnis in `## Review notes` des Sprints festhalten, mit Zitat der ausgeführten Verifikations-Befehle und ihrer Ergebnisse (Exit-Codes, wichtige Output-Zeilen), damit der Audit-Pfad im Repo liegt. Da `sprint-review` bereits jeden Verifikations-Befehl je Art von oben ausführt und damit die Exit-Codes und wichtigen Output-Zeilen vorhält, **SOLLTE [SHOULD]** es den Artefakt-Validierungs-Block in `## Review notes` automatisch aus diesen erfassten Ausgaben befüllen, statt sich darauf zu verlassen, dass der Operator sie erneut abtippt; es **KANN [MAY]** vor dem Schreiben des automatisch befüllten Blocks eine Operator-Bestätigung verlangen.

### Dispatch-Grenze zur Release-Maschinerie

Dies ist die Grenze, an der die sprint-seitige Validierung an die Release-Maschinerie übergibt: der Übergang Draft → Veröffentlicht, geregelt von [`spec/project/release-automation/`](../release-automation/de.md), und die operatorseitigen Kuratierungs- und Trigger-Skills, geregelt von [`spec/project/release-skill-layer/`](../release-skill-layer/de.md). Die beiden Links unten sind die navigierbaren Einstiegspunkte in diese unteren Specs.

- **MUSS [MUST]**, wenn der Projekttyp des Sprints über `release-publish.yml` veröffentlicht (typisch für Claude-Plugin, Python-Bibliothek, Node-Library, CLI-Tool, HACS-Integration), `sprint-review` erlauben, explizit in [`release-skill-layer`](../release-skill-layer/de.md)-Skills zu chainen. Diese Spec ist die Autorität dafür, **welcher Sprint-Zustand den Dispatch auslöst** (`review` erreicht, Artefakt-Validierung bestanden, Operator-Opt-in erteilt) und **welche Skills die Verkettungs-Punkte sind** (`release-notes-curate` für den Draft-Body, `release-publish-trigger` für die Veröffentlichung). Die Geschwister-Spec `sprint` §Dispatch in die Release-Maschinerie ist die Autorität dafür, **wie das Operator-Opt-in in `## Review notes` festgehalten wird**, sowie für die Per-Sprint-Persistenz-Regeln; diese Spec **DARF NICHT [MUST NOT]** die hier deklarierten Verkettungs-Punkte oder Trigger-Bedingungen neu definieren.
- **DARF NICHT [MUST NOT]** `gh release edit --draft=false`, `gh api -X PATCH /repos/.../releases/<id> draft=false` oder einen anderen Pfad aufrufen, der den Draft-Zustand außerhalb von `release-publish.yml` umschaltet. Die Regel kommt aus [`release-automation`](../release-automation/de.md) und [`release-skill-layer`](../release-skill-layer/de.md) und ist auch hier nicht verhandelbar.
- **SOLLTE [SHOULD]**, wenn beim Abschluss eines Publish-via-Workflow-Projekts kein Draft existiert, einen Behebungshinweis sichtbar machen (`release-drafter`-Re-Run laufen lassen, sicherstellen, dass das Tag vom Default-Branch erreichbar ist), ohne den Sprint-Abschluss über das hinaus zu blockieren, was die Artefakt-Validierung ohnehin verlangt.

### Out-of-Band-Artefakte

- **KANN [MAY]** Artefakte, die außerhalb eines Sprints veröffentlicht wurden (Notfall-Hotfixes, Sicherheits-Patches, abhängigkeitsgetriebene Re-Releases), unter `project/release-artifacts/out-of-band/<NNNN>-<slug>.md` erfassen, wobei `<NNNN>` eine monoton vergebene Out-of-Band-Nummer ist, die sich von der Sprint-Nummerierung unterscheidet.
- **MUSS [MUST]** für jeden Out-of-Band-Eintrag dieselben Felder festhalten, die ein Sprint beim Abschluss tragen würde: `value_statement`, `artifact_ref`, `roadmap_items` (darf leer sein), `ended`-Datum und einen `rationale`-Absatz; die Datei nutzt dieselbe Artefakt-Taxonomie wie sprint-gebundene Artefakte.
- **MUSS [MUST]**, sobald mindestens ein Out-of-Band-Eintrag existiert, einen flachen Index unter `project/release-artifacts/out-of-band/INDEX.md` führen, der jeden Eintrag nach Nummer, Datum und einzeiliger Zusammenfassung listet, damit nachgelagertes Tooling und menschliche Leser die Out-of-Band-Historie auffinden können, ohne das Verzeichnis zu durchwandern; der Index **MUSS [MUST]** bei jedem Hinzufügen oder Entfernen eines Eintrags neu generiert werden und **DARF NICHT [MUST NOT]** außerhalb dieser Neugenerierung von Hand editiert werden.
- **DARF NICHT [MUST NOT]** Out-of-Band-Artefakte zur Sprint-Kadenz zählen; sie sind auffindbar, erfüllen aber niemals die `artifact_ref`-Anforderung eines Sprints.
- **KANN [MAY]** einen Out-of-Band-Eintrag aus den `## Review notes` des Sprints rückreferenzieren, der zum Zeitpunkt des Out-of-Band-Releases aktiv war; die Rück-Referenz ist Dokumentation, kein Bestandteil der Sprint-Abschluss-Validierung.
- Out-of-Band-Artefakte **DÜRFEN NICHT [MUST NOT]** rückwirkend an irgendeinen Sprint anhängen und erweitern die `roadmap_items`-Nachverfolgbarkeit eines Sprints nicht; die einzige Sprint-Verknüpfung ist die optionale, rein dokumentarische Rück-Referenz in den `## Review notes` des aktiven Sprints.

### Hobby-Skala-Varianz

- **DARF NICHT [MUST NOT]** Releases auf fester Kadenz erzwingen; Sprints schließen, wenn ihr Mehrwert geliefert ist, nicht nach Plan.
- **SOLLTE [SHOULD]** Sprint-Abschlüsse tolerieren, deren Artefakt ein Doc-Site-Deploy oder eine reine Konfigurations-Änderung ist, wenn die Natur des Projekts das wirklich zum nutzersichtbaren Artefakt macht (ein dokumentations-only-Repo, ein Hobby-Infra-Projekt, in dem das Readme **das** Liefergegenstand ist). Die Taxonomie erlaubt es bereits; die Spec dokumentiert die Legitimität ausdrücklich.
- **KANN [MAY]** einen Sprint `cancelled` markieren (laut Geschwister-Spec `sprint`), falls beim Abschluss kein gültiges Artefakt erreichbar ist; Abbruch ist ein erstklassiges Ergebnis, kein erzwungenes Veröffentlichen.

## Akzeptanzkriterien

- [ ] `sprint-review` erkennt den Projekttyp anhand derselben Signale wie `release-skill-layer` und `github-issue-templates-apply`; der Erkennungsschritt ist im konsumierenden Skill dokumentiert und aus seinem Transkript verifizierbar. Die erkannten Projekttypen sind Claude-Plugin, Python-Anwendung, Python-Bibliothek, Node / TypeScript Library oder App, CLI-Tool, HACS-Integration und dokumentations-only.
- [ ] Jeder Sprint, der `review` erreicht, trägt ein `artifact_ref` (String oder Liste), das auf eine der Taxonomie-Formen seines erkannten Projekttyps passt, einschließlich der Mehr-Artefakt-Listenform für Python-Anwendungen, -Bibliotheken und Node / TypeScript-Projekte; Werte außerhalb der Taxonomie schlagen die Sprint-Review-Validierung mit wortgetreuer Fehlermeldung.
- [ ] Der `artifact_ref` jedes Claude-Plugin-Sprints löst auf eine im Marketplace gelistete Plugin-Version am Commit des Artefakts auf; ein Git-Tag ohne marketplace-auflösbare Plugin-Version schlägt den Abschluss.
- [ ] Der Git-Tag jedes HACS-Integrations-Sprints in `artifact_ref` matcht das `version`-Feld von `custom_components/<name>/manifest.json` an diesem Commit.
- [ ] Kein geschlossener Sprint trägt einen reinen Commit-SHA als `artifact_ref`, sofern das Projekt nicht ausdrücklich per `.github/release-skill-layer.yml` opt-in gewählt hat.
- [ ] Das Artefakt jedes geschlossenen Sprints ist beim Abschluss erneut abrufbar: der Verifikations-Befehl seiner Art läuft erfolgreich (`git rev-parse`, `gh release view`, `docker manifest inspect`, `pip index versions`, `npm view`, Marketplace-Auflösungs-Probe oder HEAD auf die Doc-URL).
- [ ] Der `artifact_ref` jedes geschlossenen Sprints löst auf einen Commit auf, der gleich dem `last_commit`-Frontmatter-Feld des Sprints ist oder von diesem erreichbar; ein fehlendes oder null `last_commit` blockiert den Abschluss.
- [ ] Kein `sprint-review`-Lauf ruft `gh release edit --draft=false`, `gh api -X PATCH ... draft=false` oder einen äquivalenten Pfad auf; das Grep des Lauf-Transkripts findet null Treffer.
- [ ] Wenn `sprint-review` in `release-notes-curate` oder `release-publish-trigger` chained, ist die Verkettung explizit opt-in und in `## Review notes` des Sprints festgehalten, gemäß Geschwister-Spec `sprint` §Dispatch in die Release-Maschinerie.
- [ ] Out-of-Band-Artefakte, falls vorhanden, leben unter `project/release-artifacts/out-of-band/<NNNN>-<slug>.md` mit dem vollständigen Mindestschema (`value_statement`, `artifact_ref`, `roadmap_items`, `ended`, `rationale`); jeder Eintrag spiegelt sich in `project/release-artifacts/out-of-band/INDEX.md`, der bei jedem Hinzufügen oder Entfernen neu generiert wird und nie von Hand editiert wird.
- [ ] Diese Spec verlinkt abwärts auf `release-automation` (für den Draft → Published-Workflow, von dem sie abhängt) und auf `release-skill-layer` (für die Verkettungs-Punkte, die sie dispatcht) an den passenden Grenzpunkten (Validierungsregeln-Tabelle, Dispatch-Grenze); die unteren Specs deklarieren, dass sie als Dispatch-Ziel auffindbar sein **MÜSSEN [MUST]**, **DÜRFEN [MUST NOT]** aber keinen ausgehenden Link in die Gegenrichtung tragen.
- [ ] Die Geschwister-Spec `sprint` verlinkt auf diese Spec dort, wo sie das Setzen von `artifact_ref` verlangt; die Form je Art wird hier aufgelöst, nicht in `sprint`.
