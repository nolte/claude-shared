# Monitoring and Observability

Status: draft
Portfolio-Scope: portfolio

## Context

Portfolio applications run across backend services, browser frontends, and third-party dependencies, and each needs to be observable in production: you must be able to tell *what is happening*, *why*, and *whether it is meeting its objective*, from signals the running system emits. This spec governs *what* observability an application must expose to be operable—a vendor-neutral, mandatory contract—independent of *which* backend renders it (Prometheus/Grafana, Loki, Tempo, a hosted vendor, or an OpenTelemetry Collector fanning out to several).

It's the fourth sibling of `spec/project/dockerfile-best-practices/` (the build artifact), `spec/project/kubernetes-deployment-best-practices/` (the runtime deployment posture), and `spec/project/bjw-s-common-chart-deployment/` (Helm-chart generation). Those own the *build* and *deploy* surfaces; this one owns the *observability* surface—the telemetry the application produces once it's running. It carries `Portfolio-Scope: portfolio` so image- and service-bearing repositories inherit one observability bar by reference per `spec/project/portfolio-inherited-spec-layer/`, rather than each re-deriving it.

The contract anchors on **OpenTelemetry (OTel)** as the vendor-neutral standard—its Semantic Conventions for attribute naming and its OTLP wire protocol for export—plus **W3C Trace Context** for propagation and the **Google SRE** definitions of SLI/SLO/error budget. These are open, CNCF/W3C-governed standards, so mandating them binds instrumentation without binding a vendor. Four **mandatory pillars** (metrics, structured logs, distributed traces, and health + SLO/alerting) run through three **component dimensions**: backend, frontend, and third-party. Everything else is advisory.

Every mandatory requirement is phrased so a future read-only `observability-audit` scanner can verify it by **static presence and wiring** (an SDK/exporter configured, a structured-log formatter in place, a trace-propagation middleware registered, an SLO/alert rules file present and well-formed)—runtime-only behaviours (values actually flowing, a trace actually unbroken end-to-end, an alert actually firing) are stated as advisory or "verify at runtime." Every load-bearing claim here was adversarially verified against primary sources (see `Version and standard anchors`): 48 load-bearing claims, 0 refuted.

## Goals

- Every service exposes the **four mandatory pillars**: application/runtime **metrics** (RED + USE), **structured logs** correlated to traces, **distributed traces** propagated across every boundary, and **health signals + at least one SLO with a bound alert**, as a vendor-neutral, statically-checkable floor
- The binding contract is **OTel-neutral**: telemetry follows the OpenTelemetry Semantic Conventions and is exportable via **OTLP**, so any compliant backend receives it; concrete tooling (Prometheus, Grafana, Loki, Tempo, the OTel Collector) is named only as a **non-binding reference profile**
- Observability spans all **three component dimensions**: the backend, the frontend (a lightweight mandatory floor of browser-error capture + trace propagation, with full RUM/Core Web Vitals advisory), and third-party dependencies (at least one signal per critical dependency, mechanism free)
- Mandatory **guardrails** are stated as rules a scanner can check: no unbounded-cardinality metric labels, and **no PII emitted into logs or traces** (redacted at the emission boundary)
- The spec **references, not duplicates,** its neighbours: probe *wiring* is owned by `spec/project/kubernetes-deployment-best-practices/`, and the PII-class definition and audit verdict are owned by `spec/project/gdpr-audit-process/`; this spec owns the observability *semantics* and the *prevention* control
- The spec is the shared observability bar across the portfolio, so an operator moving between repositories checks the same contract and the future `observability-audit` skill emits the same posture

## Non-Goals

- The **audit/skill family that operationalises this spec**: a read-only `observability-audit` scanner agent, an audit skill, and a remediation specialist—which is follow-up work in its own working copies; this spec is only the contract they enforce
- **Kubernetes probe wiring**: declaring `readinessProbe`/`livenessProbe`/`startupProbe`, gating Service traffic on readiness, restarting on liveness, and pointing a probe at a real endpoint—which aren't application telemetry and are owned by `spec/project/kubernetes-deployment-best-practices/` §Health probes; this spec owns only *what a health endpoint reports*
- The **GDPR audit verdict**: detecting and classifying personal data in logs/errors/analytics and reporting it at `file:line` (owned by `spec/project/gdpr-audit-process/`, Art. 32); this spec adds the *producing-side* control (redact before emission) that the GDPR audit then verifies, and references its PII-class definition rather than restating it
- **Concrete numeric objectives**: specific SLO targets, latency budgets, alert-routing tiers, and cardinality ceilings—which are per-service decisions; this spec mandates the *shape and existence* of the artifact, not its numbers
- **Dashboards, visualisation, and vendor deployment**: which backend renders the telemetry, how dashboards are laid out, and how the observability stack is hosted—governed per-repository, not by the application's telemetry contract
- Restating the full OpenTelemetry, W3C Trace Context, or Google SRE reference; this spec pins the load-bearing requirements and their rationale and delegates exhaustive detail upstream

## Requirements

### Vendor-neutral core (mandatory pillar)

- Telemetry attribute naming **MUST** follow the **OpenTelemetry Semantic Conventions** (the 1.x line, current 1.43.0 or later) for the signal areas the application emits, so names carry the same meaning across services, libraries, and backends. This MUST is scoped to the convention areas actually marked **stable** (for example HTTP, network, and resource/attribute conventions, stable since v1.23.0); conventions still marked development or release-candidate are SHOULD-followed. Anchor on the 1.x *line*, not a frozen point release—the line is additive and forward-moving, and "stable" for a semantic convention permits only schema-transformable (with a deterministic migration path) breaking changes, not a zero-change guarantee
- Telemetry **MUST** be exportable via **OTLP** (the OpenTelemetry Protocol, current 1.10.0, which is **stable** for the trace, metric, and log signals), so any OTLP-compliant backend receives the same wire format and instrumentation is decoupled from any single vendor. The transport variant (OTLP/gRPC or OTLP/HTTP) is free—the Protobuf schema is identical. The stability claim **MUST NOT** be extended to the profiles signal, which is still in development
- A backend that doesn't natively emit OTLP **MUST** be bridged to it (a native OTLP exporter, a Prometheus-compatible metrics surface an OTLP pipeline can scrape, or an OTel Collector receiver), so the neutral-export requirement is satisfiable without rewriting the application's instrumentation

### Metrics (mandatory pillar)

- Every **request-driven service** (HTTP/gRPC APIs, gateways, service-mesh members, and asynchronous message consumers) **MUST** expose the **RED** signals: **Rate** (requests per second), **Errors** (count/rate of failing requests), and **Duration** (a request-latency *distribution*, not just a mean). RED is the canonical per-service, consumer-experience method (Tom Wilkie, Weaveworks, 2015)
- Every **infrastructure resource** the service depends on (CPU, memory, disk, network, and constrained software resources such as thread/connection pools and locks) **MUST** be covered by the **USE** signals: **Utilization** (fraction of time the resource was busy), **Saturation** (queued/unserviceable extra work), and **Errors** (Brendan Gregg). RED and USE are complementary—RED measures the consumer experience per service, USE measures internal bottlenecks per resource; RED deliberately omits saturation (it lives in USE), which is the boundary between them. RED parallels Google's Four Golden Signals (Golden = RED + saturation); frame it as a parallel, not a derivation—RED predates the 2016 SRE book
- Metrics **MUST** be exposed through a vendor-neutral registry/exporter reachable by an OTLP pipeline (a native OTLP metric exporter or a Prometheus-compatible endpoint); the *presence and wiring* of that exporter is the statically-checkable mandatory floor. Whether the emitted values are correct is a runtime concern

### Structured logs (mandatory pillar)

- Logs **MUST** be emitted as **machine-parseable key/value records** (consistent, machine-readable; JSON is the recommended default)—a free-text-only log line **MUST NOT** be the primary log surface. A record remains structured while still carrying a human-readable `message` field alongside its typed fields; the floor is consistent parseable key/value, not a fully predefined schema
- Every log emitted within request processing **MUST** carry the active **`trace_id` and `span_id`** as first-class fields, sourced from the request's trace context, so a log line can be joined to its trace. The OpenTelemetry Logs Data Model defines `TraceId`/`SpanId`/`TraceFlags` as *optional* top-level fields; mandating their presence is a valid downstream strengthening. When present, the wire format **MUST** be W3C-compatible lowercase hex: `trace_id` 32 hex characters, `span_id` 16 hex characters, no `0x` prefix, and the field names **MUST** be consistent and backend-recognised across all services (`trace_id`/`span_id` are the OTel-canonical JSON-log names)
- Log records **MUST** observe **severity discipline** using the OTel `SeverityNumber` ranges (TRACE 1–4, DEBUG 5–8, INFO 9–12, WARN 13–16, ERROR 17–20, FATAL 21–24), with `SeverityText` holding the source label. The admission contract: **ERROR** = a failure that prevents completing a user request; **WARN** = an unexpected-but-recovered/degraded condition; **INFO** = significant business events; **DEBUG/TRACE** = troubleshooting detail. There **MUST NOT** be *severity inflation* (labelling non-critical events ERROR/FATAL), which drives alert fatigue. The production default level **SHOULD** be INFO/WARN, with DEBUG/TRACE off by default and opt-in during investigation (DEBUG volume commonly runs 10–100× INFO)
- A **stable field schema** (uniform field names and types across a service's logs) **SHOULD** be maintained, and an OTel-aware log appender / Logs Bridge integration **SHOULD** be used to inject `trace_id`/`span_id` automatically; a specific logging library **MUST NOT** be mandated. (PII discipline in logs is governed by the PII-redaction pillar below.)

### Distributed traces (mandatory pillar)

- When a request crosses a **service or third-party boundary**, trace-context propagation **MUST** be configured end-to-end using **W3C Trace Context** (a W3C Recommendation, 2021-11-23): the incoming context is read from and the outgoing context is written to the **`traceparent`** header (format `00-<32-hex trace-id>-<16-hex parent-id>-<2-hex flags>`), with vendor state carried on **`tracestate`**. This aligns with OpenTelemetry's default propagator (a composite of W3C Trace Context + W3C Baggage), so it doesn't diverge from the neutral core
- Every service **MUST** register trace-context propagation on **both** its inbound and outbound boundaries (an instrumentation/middleware layer that extracts context from incoming requests and injects it into outgoing calls), so a trace isn't broken at a hop—restating the standard's own minimum-compliance rule that a tool **MUST** propagate the traceparent and tracestate headers and guarantee traces aren't broken. The *presence* of inbound and outbound propagation instrumentation is the statically-checkable floor; actual end-to-end continuity is runtime-verifiable and **SHOULD** be checked in a live trace
- Spans **SHOULD** carry the OTel-semantic-convention attributes for their operation (for example the stable HTTP client/server attributes) so a span is self-describing across backends

### Health, SLO and alerting (mandatory pillar)

- Every long-running service **MUST** expose a **health-signal endpoint** whose *semantics* are defined: it reports the service's own liveness/readiness plus the health of its critical downstream dependencies, and **SHOULD** expose build/version identity (for example `service.version`, commit). This spec owns *what the endpoint reports*; the probe *wiring* that consumes it (readiness gating traffic, liveness restarting the container, a probe targeting a real endpoint) is owned by `spec/project/kubernetes-deployment-best-practices/` §Health probes and **MUST NOT** be restated here
- Every service **MUST** define at least one **SLO**, and a well-formed SLO **MUST** declare all of: (1) an **SLI**: a quantitative measure of service level, expressed as *good events / valid events*; (2) a **target**: a target value or range for that SLI; (3) an **evaluation/compliance window**: a rolling window (Google favours 4-week rolling) or a calendar window. The SLO's evaluation window **MUST NOT** be conflated with the SLI's aggregation interval (for example "averaged over 1 minute" is an aggregation interval, not the compliance window). The **error budget** is derived as `100% − SLO`, not an independent number
- Every SLO **MUST** be paired with **at least one alert bound to it**: an SLO/error-budget-based (burn-rate) alert, not merely a resource/cause alarm—so paging is tied to user-visible impact and budget consumption. The recommended alert shape is **multi-window, multi-burn-rate** (a long window catching sustained consumption paired with a short window confirming the error is still active, short ≈ long/12 as a guideline)
- The *existence and well-formed shape* of the health-endpoint semantics, the SLO (SLI + target + window), and the bound alert is the mandatory, statically-checkable floor—for example an SLO/alert rules file that's present and parses. The concrete numeric targets, windows, and alert-routing tiers are **project-defined**. This pillar governs **SLOs** (internal objectives), explicitly **not SLAs** (a contractual commitment with consequences), which are out of scope

### Frontend observability (mandatory floor + advisory depth)

- A project that ships a **browser frontend MUST** capture uncaught client-side errors via the two native global listeners—the window **`error`** event (uncaught synchronous throws and resource-load failures) and **`unhandledrejection`** (rejected promises)—feeding them into the structured-logs/errors pillar. (Same-origin coverage is complete; cross-origin script errors are sanitised by the browser to `"Script error."`, a known limitation, not a gap in the requirement)
- A browser frontend **MUST** propagate **W3C trace context from the browser into the backend** on its outbound calls (for example OTel JS `fetch`/XHR instrumentation injecting `traceparent`), so a trace spans the browser→server boundary and the traces pillar stays coherent. Injection is turnkey **same-origin**; the common cross-origin (CORS) browser→API case additionally requires configuring the propagation target URLs (for example `propagateTraceHeaderCorsUrls`) **and** allow-listing `traceparent`/`tracestate`/`baggage` in the backend CORS policy—still lightweight relative to full RUM, but not zero-config
- Full **Real User Monitoring**, comprising **Core Web Vitals** (LCP ≤ 2.5 s, **INP** ≤ 200 ms, CLS ≤ 0.1 at the 75th percentile; use **INP**, which replaced FID as a stable Core Web Vital on 2024-03-12, never FID) and sourcemap-resolved stack traces, **SHOULD** be adopted where user-experience data is valued, but is **advisory**, not the mandatory floor: Core Web Vitals are field/RUM metrics that need real-user sampling, a metrics beacon, and p75 aggregation across device classes (lab tools can't measure INP at all and produce only an incomplete CLS), materially heavier than the two-listener + trace-propagation floor

### Third-party dependency monitoring (mandatory floor)

- Every **critical third-party/external dependency** (one on the request path or in the availability chain) **MUST** carry at least one observability signal, satisfiable by either canonical shape: **black-box** synthetic probing (externally-visible availability/latency, for example a Prometheus Blackbox-Exporter-style probe emitting a `probe_success` availability signal, probe duration, and TLS-certificate expiry) **or** **white-box** client-side instrumentation of the outbound call (a client span plus request-duration and error-type metrics on the caller, for example the stable OTel HTTP client instrumentation). The *presence of at least one signal per critical dependency* is the mandatory floor; which mechanism is the project's choice
- The two shapes are complementary (SRE guidance: heavy white-box with modest but critical black-box), and a project **SHOULD** combine them for a critical dependency. Note the observability split: latency and errors are externally (black-box) observable and saturation is internal (white-box), but **aggregate traffic isn't straightforwardly black-box-able** (a single prober sees only its own requests) and **MUST** be measured internally or at the edge

### High-cardinality guardrail (mandatory)

- Metric labels **MUST NOT** use **unbounded-cardinality dimensions** as values—raw user IDs, email addresses, request IDs, full URLs, session tokens, or timestamps—because every unique label-value combination is a distinct time series and unbounded values explode storage and cost (Prometheus naming guidance names user IDs, emails, and "other unbounded sets of values" explicitly; request IDs, full URLs, and timestamps fall under the same unbounded-set rule). This is a mandatory *rule*; the concrete cardinality budget (the maximum acceptable series count per metric) is project-defined
- Genuinely high-cardinality, per-event dimensions **SHOULD** be carried on **logs and traces** (which are built for them) rather than metric labels, and unbounded values **SHOULD** be replaced by bounded low-cardinality buckets (a user *tier* rather than a user ID; a route template rather than a full URL)

### PII redaction at emission (mandatory)

- A service **MUST NOT** [locked] emit personal data (PII) into logs or trace/span attributes; redaction **MUST** [locked] happen **at or before the point telemetry leaves the process or environment**, never relying on the backend to scrub. In an OTel Collector this is a redaction/attribute processor between receivers and exporters (before any exporter sends); in-process it's a custom OTel SDK log/span processor that scrubs attributes before export
- Redaction **SHOULD** use a **fail-closed allow-list** (only explicitly allowed attribute keys are retained, so a newly-added field carrying PII is dropped by default rather than leaked) in preference to a deny-list, and **SHOULD** prefer deletion or allow-listing over hashing for low-entropy identifiers (hashes of a small, predictable input space are reversible in practice)
- What counts as personal data—and the audit verdict that a leak occurred—is owned by `spec/project/gdpr-audit-process/` (Art. 32, personal data in logs/errors/analytics, reported Critical at `file:line`). This spec **MUST** reference that spec for the PII-class definition and verdict rather than restating it: `gdpr-audit-process` *detects*, this spec *prevents at emission*. The two are complementary—no producing-side redaction contract exists elsewhere in the corpus, so this pillar fills the gap, it doesn't duplicate

### Static verification and delimitation

- Every **mandatory** requirement above **MUST** be phrased so a read-only scanner can verify it by static presence/wiring (an SDK/exporter configured, a structured-log formatter and trace-correlation in place, inbound/outbound trace-propagation registered, a health endpoint declared, an SLO/alert rules file present and well-formed, a redaction processor wired), and the Acceptance Criteria section as a whole closes with the "a reviewer can hold a real application against this checklist" clause. Runtime-only behaviours (real metric values, an actually-unbroken trace, an alert actually firing) **MUST** be stated as advisory SHOULD or explicit "verify at runtime," never as a statically-hard-failing MUST
- The spec **MUST NOT** duplicate its neighbours: it references `spec/project/kubernetes-deployment-best-practices/` for probe *wiring* and `spec/project/gdpr-audit-process/` for the PII-class/verdict, owning only the observability semantics and the emission-time prevention control

### Reference profile (non-binding)

- Concrete tooling **MAY** be named only inside a dedicated, explicitly **non-normative** reference-profile section, so audits bind to the OTel-neutral contract, not the tools. The portfolio reference profile is: **OpenTelemetry SDKs + Collector** for instrumentation and export; **Prometheus** (metrics), **Loki** (logs), **Tempo** (traces), and **Grafana** (dashboards/alerting) as one coherent OTLP-compatible backend. A project **MAY** substitute any OTLP-compliant backend (a hosted vendor, or another self-hosted stack) and still satisfy every mandatory requirement—the profile is illustrative, never required to be present

### Version and standard anchors

- The spec's normative content **MUST** be read against these pinned standards, current as of 2026-07-10: **OpenTelemetry Semantic Conventions** 1.x (current 1.43.0; stability declared per-convention); **OTLP** 1.10.0 (stable for traces/metrics/logs; profiles in development); the **OTel Logs Data Model** (spec v1.53.0); **W3C Trace Context** Level 1 (W3C Recommendation, 2021-11-23); the **RED** method (Tom Wilkie, Weaveworks, 2015) and the **USE** method (Brendan Gregg); the **Google SRE** book and SRE Workbook (SLI/SLO/error budget, multi-window multi-burn-rate alerting); **web.dev Core Web Vitals** (LCP/INP/CLS, INP-since-2024-03-12); and the **Prometheus** metric-and-label naming guidance (high-cardinality prohibition)
- An `observability-audit` implementation **SHOULD** pin the specific standard/tool versions it checks against, because semantic-convention areas and tool rule sets drift, and **SHOULD** treat a convention area's stability marker (stable / release-candidate / development) as gating whether it's a MUST or a SHOULD

## Acceptance Criteria

- [ ] `spec/project/monitoring-observability/` exists with `en.md` (canonical) and `de.md` (translation), carries `Portfolio-Scope: portfolio`, and is listed in `spec/README.md`
- [ ] The **vendor-neutral core** is a mandatory section: telemetry follows OTel Semantic Conventions (1.x, stable areas as MUST) and is OTLP-exportable, stated with RFC 2119 keywords, with the reference profile explicitly non-binding
- [ ] The **four mandatory pillars** are each a mandatory section with RFC 2119 keywords and rationale: Metrics (RED for services + USE for resources, neutral exporter present), Structured Logs (machine-parseable, `trace_id`/`span_id` present, severity discipline), Distributed Traces (W3C Trace Context propagated on inbound + outbound), and Health + SLO/Alerting (health-endpoint semantics + SLO shape [SLI + target + window] + a bound burn-rate alert)
- [ ] The **frontend floor** is stated: browser error capture (`error` + `unhandledrejection`) + browser→backend trace propagation are mandatory; RUM/Core Web Vitals (INP not FID) are advisory, with the same-origin-vs-CORS propagation caveat noted
- [ ] The **third-party floor** is stated: at least one signal (black-box probe or white-box client instrumentation) per critical dependency, mechanism free, with the traffic-not-black-box-able note
- [ ] The **high-cardinality guardrail** is a mandatory rule (no unbounded-cardinality metric labels; budget project-defined) and the **PII-redaction** pillar is mandatory and `[locked]` (no PII in logs/traces; redact at the emission boundary; fail-closed allow-list), referencing `gdpr-audit-process` for the PII-class/verdict
- [ ] The **SLO-vs-SLA** boundary, the **evaluation-window-vs-aggregation-interval** distinction, and the **error-budget = 100% − SLO** derivation are each stated
- [ ] Neighbour delimitation is explicit: probe **wiring** is delegated to `spec/project/kubernetes-deployment-best-practices/` and the PII-class/verdict to `spec/project/gdpr-audit-process/`, each referenced, not restated
- [ ] The version/standard anchors are pinned (OTel SemConv 1.x, OTLP 1.10.0, OTel Logs Data Model v1.53.0, W3C Trace Context L1, RED/USE, Google SRE, Core Web Vitals, Prometheus naming)
- [ ] Every mandatory requirement is phrased to be statically checkable by presence and wiring, and a reviewer (or the future `observability-audit` skill) can hold a real application against this checklist and mark each requirement done or not done

## Open Questions

- **`observability-audit` skill/agent family.** This spec defines the contract; the read-only scanner agent, the audit skill, and the remediation specialist that enforce it are follow-up work in their own working copies, mirroring the `dockerfile-audit` sibling. Their exact shape (which checks are static hard-fails vs runtime-advisory, the report format) is fixed when they're authored.
- **Precise "critical dependency" criterion.** The third-party floor (R8) applies to *critical* dependencies. The checkable definition—on the request path / in the availability chain vs a best-effort or offline dependency—is settled in principle here and finalised (with any opt-out marker) when the audit skill is authored.
- **OTel Semantic Conventions version-pinning policy.** Anchoring on the 1.x *line* (not a frozen tag) with per-convention stability gating is the stated policy; whether the audit pins one exact SemConv release per portfolio cycle, and how it treats a project on an older stable line, is an audit-implementation detail.
- **Static-vs-runtime carve-out wording.** Which sub-clauses of the metrics, traces, and health pillars a static scanner hard-fails on versus documents as runtime-verify is settled in principle (presence/wiring = static, values/continuity/firing = runtime); the exact per-clause split is fixed when the audit skill is authored.
- **Minimal health-endpoint field set and metric/label taxonomy.** The exact minimum fields a health endpoint must report and any portfolio-standard metric/label naming beyond the OTel conventions are left to the audit-skill authoring step.
