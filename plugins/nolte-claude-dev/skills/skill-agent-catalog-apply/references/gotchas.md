# Gotchas

Per `spec/claude/skill-management/` §Gotchas: concrete corrections to non-obvious environment facts the executing agent would otherwise get wrong when running `skill-agent-catalog-apply`.

- **`mkdocs-static-i18n` folder mode silently drops `mkdocs-gen-files` pages.** This is the load-bearing i18n prohibition: `mkdocs-static-i18n` 1.3.x only classifies files whose `abs_src_path` is under `docs_dir`, and gen-files virtual pages live in a temp dir, so under `docs_structure: folder` every generated page is discarded and the catalog renders **empty** — with no build error to warn you. In a folder-mode repo (this one included), the surface **must** be the `on_pre_build` hook (recommended default) or the standalone pre-build step, both of which write physical files that `static-i18n` collects like hand-authored pages. Detect the i18n mode from `mkdocs.yml` *before* choosing a surface.
- **The `on_pre_build` hook is the recommended default and needs no Taskfile or CI wiring.** It fires inside every `mkdocs build` (bare build, `mkdocs serve`, and the `mkdocs gh-deploy` the shared deploy reusable runs), so the catalog regenerates at deploy time with no committed tree and no freshness gate. Don't "fix" a repo that already wires `gen_catalog.py` under `hooks:` — that is the conformant, recommended shape, not drift against a missing `gen-files` plugin.
- **`mkdocs-literate-nav` and `pyyaml` must be pinned for every surface.** Without literate-nav the catalog navigation fails (opaque plugin-not-found or a catalog-less nav); without `pyyaml` the standard-YAML frontmatter parse the spec requires (nested `dont_use_when`/`examples` mappings) can't run. `mkdocs-gen-files` is pinned **only** for the gen-files surface. Verify the required lines exist in `docs/requirements.txt` before assuming the build picks the catalog up.
- **The generator only runs at build time, not on file save.** Changes to `skills/<name>/SKILL.md` or `agents/<name>.md` don't appear in the rendered catalog until the next build (a bare `mkdocs build` suffices with the `on_pre_build` hook; otherwise the next `task docs` or CI build). When the user edits an artefact and asks why the catalog doesn't show it, the answer is almost always that the build hasn't run yet, not that the generator's broken.
- **Plugin source roots in `docs/catalog-sources.yml` are repo-relative paths, not install paths.** In plugin mode the entry is `local: .` (the current repo *is* the plugin). In consumer mode the entry points at where the plugin's repo content actually lives on disk relative to the docs build, typically `local: ../claude-shared` for a sibling checkout, or a vendored or submoduled subdirectory. The generator resolves the path at build time relative to the `mkdocs.yml` location; the runtime `.claude/plugins/<plugin>/` install path is for skill discovery at session-start, not for docs generation.
- **Consumer mode forbids the local-plugin entry.** A consumer-mode repo (one that installs `nolte-shared` rather than being it) **MUST NOT** declare `local: .` as a source; the walker would then look for `skills/` and `agents/` at the consumer's repo root, find nothing, and emit an empty catalog or a hard error. Plugin mode and consumer mode are deliberately exclusive on this point.
- **`docs/<lang>/by-task.md` is one-shot on the first run only.** The generator pre-populates the file from `use_when` entries the first time it runs against a docs language; every subsequent run sees the file exists and leaves it alone. Two operational consequences: (a) when a consumer adds new artifacts later, the generator does not auto-add them to the curated landing page — the maintainer integrates them by hand; (b) when bootstrapping a fresh catalog, the maintainer typically deletes both `docs/<lang>/by-task.md` files once after migrating all artifacts so the regenerated skeleton reflects the full set of `use_when` entries.
- **The cross-linking pass only transforms inline-code spans.** Plain-text occurrences of artifact names (e.g. "use spec-readiness-reviewer to audit") stay as plain text. To get a link, the author must wrap the name in single backticks (`` `spec-readiness-reviewer` ``). This is the false-positive guard from spec §Cross-linking — generic words that happen to collide with an artifact name (a hypothetical skill called `build`, say) stay untouched in prose.
- **`_translation-pending` is never an author-declared tag.** Source `SKILL.md` and agent files **MUST NOT** put `_translation-pending` (or any other `_…` tag) in their `tags:` frontmatter; the generator emits the auto-tag per page per docs language based on summary-resolution fallback. Declaring it in source frontmatter fails the docs build immediately.
