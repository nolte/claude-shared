# Runner exit codes and not-probed routing

Loaded by `capability-reach-audit` `run` step 2. The runner is `scripts/reach_audit.py` (invoked only as `python3 "${CLAUDE_PLUGIN_ROOT}/skills/capability-reach-audit/scripts/reach_audit.py" --repo <path>`); its exit codes and reason strings are the contract this file maps to an operator-facing next step. Nothing here re-derives a verdict: the report's classes and ratios are quoted, never recomputed.

Contents: §Exit codes · §Findings (exit 4) · §Removed probes and retirement · §Not-probed reasons and their routing · §Derivation anchors · §Re-baseline rule

## Exit codes

| Exit | Runner meaning | What the skill does next |
|---|---|---|
| `0` | report written, no findings | run `report`; the headline may still say `Not probed: <n> of <total>`, which is a coverage fact to surface, not a pass |
| `1` | runtime error (unreadable probe set, report not writable, git failure) | relay stderr verbatim; don't retry blind; the fix is in the target's state, not in the invocation The history scan stops with ``the history of project/reach-probes/ names <n> probe revision(s) this repository does not hold (first: <blob>); a partial or incomplete clone hides which probe ids existed. Fetch the full history and objects (`git fetch --refetch`, or a clone without --filter) and run again.``: a partial (`--filter`) or otherwise incomplete clone lacks probe revisions the history names, so the removed ids can't be determined and nothing is judged; fetch the missing objects as the message says, then `run` again |
| `2` | usage error, non-local or shallow target | relay the message verbatim; a remote address, a missing directory, a missing `.git`, a subdirectory, a bare repository, a repository with no commit, or a shallow clone (`… is a shallow clone …`) is refused by design; never route around it. A shallow clone hides every probe change before its boundary, so its fix is the full history: `git fetch --unshallow` (or `fetch-depth: 0` in CI), then `run` again. A symlinked `project` or `project/reach-probes` is refused with `<path> is a symlink. The probe set must live in project/reach-probes/ as a real directory under version control; the runner does not follow links in the audited tree. Replace the link with the directory and commit it.`: git records only the link, so the history would read every probe as deleted; the operator replaces the link with the real directory and commits it |
| `3` | no probe file: `project/reach-probes/` is absent, empty, or holds only the manifests (`_not-constructible.yml`, `_retired.yml`); nothing was executed | **not** a clean result. Without a not-constructible manifest the report says "no probe set"; with manifest entries it is a full report in which every entry is not probed. Either way route to `derive` (with a manifest, the actionable entries are the work to do first). A set that lost probe files is no empty set: each removed id is a finding (exit `4`); once all of them are retired the run exits `3` and Provenance still lists the retirements |
| `4` | report written with findings (weakened, invalid, or removed probes, approval mismatches, contradictions, manifest defects, invalid `supersedes` records, retirement findings); takes precedence over 3. The runner prints `report written with findings (weakened, invalid, removed, or unapproved-content probes, a manifest finding, an invalid supersedes record, or a retirement-manifest finding)` | run `report` leading with the Findings section, then the headline; see §Findings and §Removed probes and retirement |
| `5` | PyYAML or jsonschema missing | relay the runner's `pip install` hint verbatim and stop; never parse or validate probes yourself |
| `6` | `--check-migration` only: a migration candidate (a `.md` declaration without `declaration.sections`) isn't clean, is invalid, is also a manifest entry, or carries an invalid `supersedes` record, or the manifest is unreadable; a superseded probe is no candidate; nothing written | stop `migrate`; relay each `refused` line and follow its route (`references/reconfirm-and-migrate.md` §Migration step 1) |

A negative or zero `--environment-timeout` also exits `2` before anything runs.

## Findings (exit 4)

- **weakened** `<id>`: the probe file changed after the commit that recorded its `derived_from`, or has uncommitted changes. The probe was **withheld** (`not probed`, reason `weakened: …`), never executed as approved. Lead with these. The operator either reverts the change (restoring the approved text) or re-derives the entry (`derive` with the entry filter) after a real declaration change, which records a new `derived_from` and a new baseline only while no earlier derivation in the probe's chain was itself weakened; when the reason says `its previous derivation was no re-derivation either` or `the probe changed in …`, no re-derive clears it, and the exit is a supersede (§Re-baseline rule). Editing the file again is never the fix.

| Weakened reason (as written by the runner) | Meaning | Next step |
|---|---|---|
| `probe changed in <commits> after its derivation was recorded in <baseline>` | a later commit changed the probe. An entry `merge <sha12>` is a merge whose result for the probe differs from every parent (a conflict resolution, or an edit made while merging); the probe's history walk never lists merges, so the runner searches for them separately | revert the probe to its approved text; otherwise the exit is a supersede (§Re-baseline rule), since a later re-derivation reaches back over the change. Commit the replacement in a plain commit, never inside a merge |
| `the probe's oldest listed revision <sha12> does not create <path> but records <a change to it / a rename from <src> / …>: the probe's origin isn't in its listed history but in a merge the walk can't follow, and a derivation recorded in a merge cannot be judged` | the probe was created, or renamed into its path, inside a merge; the walk follows neither, so its history starts at a later plain commit that can't stand in for the derivation | no re-derive clears it, since the oldest listed revision stays the same: derive and approve a new probe under a new id that lists this one in `supersedes`, and commit it in a plain commit, not in a merge (§Re-baseline rule) |
| `<sha12> changed <path> under the id <id>, but the probe's history walk does not list it, so the listed history is incomplete and no derivation in it can be judged` | a plain commit wrote this probe's id on one of its paths, and the `git log --follow` walk did not list it: an earlier probe under the same id at that path (deleted, re-created elsewhere, and moved back), or a change the walk missed. The runner checks the walk against every probe revision in the history and fails closed | no re-derive clears it: derive and approve a new probe under a new id and file name that lists this one in `supersedes` (§Re-baseline rule) |
| `the probe was created in <sha12> as a copy of <src> at <path>, which already held a file in <sha12>: git follows the copy instead of that path, so the path's earlier revisions are not in the listed history and can't be judged; …` | the probe file was re-added as a copy of another probe at a path an earlier file held; the walk follows the copy into its source, so the path's own earlier revisions, which a delete-and-re-add otherwise keeps, are not listed | derive and approve the probe under a new id and a file name no earlier file used; to clear a weakened probe that held that path, keep its file and list its id in `supersedes`, and `retire` an id whose file was deleted (§Re-baseline rule) |

- **invalid probe** `<file>`: the file fails the probe schema. Quote the runner's error list. The fix is a re-derive of that entry; a hand edit to satisfy the schema would itself be a weakening.
- **invalid probe** `<file>` with the error `symlink: refused and not read; a probe file must be a regular file`: a symlink under `project/reach-probes/` is listed and never followed, so a probe set can't pull in text from outside the directory. Remove the symlink, re-derive the entry so a real file lands there, and commit it; never copy the link target into place by hand.
- **approval mismatch** `<id>`: the change-detection state whose reason is `approval does not cover the current observation step`; the committed `observe`, `environment`, or `teardown` no longer match `approval.observation_digest`. The probe was withheld. Re-derive and re-approve the entry; never hand-edit the digest to make it match. Read §Re-baseline rule when the operator asks why a re-approval didn't clear an older `weakened` finding at the same time.
- **contradiction** `<id>`: the id is both a probe file and a manifest entry; the probe is **not executed** and the row is not probed. The manifest is stale from a round that turned the entry into a probe: re-run `derive` with the entry filter set to that entry's declaration path, which rewrites the manifest without it; never delete the probe file to resolve it.
- **invalid manifest** (`_not-constructible.yml`): the file is unparseable or fails the schema above `entries/<i>`; none of its entries is counted and the headline says so. The fix is a re-run of `derive`, which rewrites the manifest from the scanner's payload; never repair it by hand.
- **invalid manifest entry** `<id>`: one entry fails the schema (a bad reason code, a missing `derived_from`, an unquoted `recorded_at`); it still counts as not probed. Re-run `derive` for that entry.
- **invalid supersede** `<id>`: the probe's `supersedes` record takes no effect: it lists the probe's own id, an id that is no valid probe file on disk (a deleted superseded file included) or is a manifest entry, a probe that leads back through `supersedes` (a cycle), a probe that isn't weakened (it keeps running), a probe on another declaration entry (`declaration.source`, `location`, `path`, `inherited_spec`, or `hub` differ), a probe that is also a manifest entry, a replacement whose `approval.mode` is `reconfirmed` or that moves the entry to T2 from a lower tier (a default run withholds T2), or a probe whose history git pairs with this probe's own revisions (`it descends from this probe or sits on its earlier path`: the new file isn't a copy of the untouched old one, or the cut would reach a revision carrying this probe's id). A record that takes no effect leaves the probe that carries it judged on its full history. Editing the record is a probe change and weakens the probe. Restore a deleted superseded file from history; otherwise delete the probe that carries the record and, in a second commit, derive it afresh under a new id without the faulty entry, and `retire` the deleted probe's id (`derived-in-error`), since its deletion now reads `removed`. Never delete a superseded file, since it's the record of what was replaced: deleting it now reads `removed` for its id, and a retirement record is the only exit that keeps it deleted, which still leaves this `invalid supersede` finding on the replacement standing. Restoring the file clears both.
- **duplicate manifest id** `<id>`: listed more than once, counted once. Re-run `derive`; the scanner's ids are unique per payload, so a duplicate means two rounds were merged by hand.
- **removed** `<id>`, **retirement contradiction**, **invalid retirement record**, **invalid retirement manifest**: a probe id that left the set, or a defect in `project/reach-probes/_retired.yml`; see §Removed probes and retirement.

## Removed probes and retirement

A probe id that a committed file under `project/reach-probes/` carried anywhere in the history of HEAD (merges included, approved or not) and that no probe file carries now is a **removed** finding, `` - **removed** `<id>` (<file>): <reason> ``, where `<file>` is the path it last existed in. Its Probes-table reason is `removed: <reason>`, it counts as not probed, and the reach-per-tier table lists it in the row `none (removed)`; it's never executed. Identity is the `id` field (an unparseable historic revision counts under its file name stem): a rename that keeps the id is no removal, and editing the id in a kept file removes the old id. The only exit that keeps the probe gone is an approved, committed retirement record in `project/reach-probes/_retired.yml`, written by `retire` (`references/retirement.md`); restoring the file is the other exit.

| Removed reason (as written by the runner) | Cause | Remedy |
|---|---|---|
| `no probe file carries this id any more; it last existed in <path> at <commit>; <why>` | a commit deleted the file, replaced it, or changed its id; `<commit>` is the full hash of the last commit that still carried it | restore the file, or `retire` the id with `last_revision` set to `<commit>` |
| `no probe file carries this id any more; it last existed in <path> at HEAD <commit>, and its removal is not committed; <why>` | the file is gone or changed only in the working tree | commit the deletion together with its record, or restore the file |
| `no probe file carries this id any more; no commit that removed it was found; <why>` | the id left the set where the walk names no removing commit | `retire` with a `last_revision` the operator names and verifies (`references/retirement.md` §Source and eligibility), or restore the file |
| `exchange under the same id: it last existed in <path> at <commit>, and <file> carries it now, but that file's own history first carries it in <sha12>` (or `… holds no committed revision that carries it`) `; a retirement record can't account for an exchange under the same id: give the replacement a new id and retire this one, or restore the earlier file and supersede it` | another file took the id over from a file that's gone, a replacement under the old id, while the file at HEAD is judged on its own | no record clears it (one is a contradiction): derive the replacement under a new id and `retire` the old id, or restore the earlier file and supersede it (§Re-baseline rule) |

`<why>` names why no record takes effect:

| `<why>` | Remedy |
|---|---|
| `no retirement record accounts for it` | `retire` proposes one |
| `the retirement manifest is unreadable (see Findings), so no record in it takes effect` | resolve the `invalid retirement manifest` finding first; no record in the file counts until then |
| `its retirement record is invalid (see Findings), so it takes no effect` | `retire` replaces the record named in the `invalid retirement record` finding |
| `its retirement record carries no approval, so it takes no effect` | `retire` re-proposes it with an approval; a record is never approved on the operator's behalf |
| `its retirement record is not committed, so it takes no effect` | commit `_retired.yml` |
| `a retirement record can't account for a removal that is not committed` | commit the deletion |
| `its retirement record was already in project/reach-probes/_retired.yml at <sha12>, before the removal in <sha12>, so it can't account for that removal` | the record predates this removal (the probe was restored and deleted again, or the record was committed before the deletion): `retire` writes a new record |
| `project/reach-probes/_retired.yml can't be read at <sha12>, before the removal in <sha12>, so it can't be shown that the record postdates that removal` | the manifest at the last commit that still carried the probe is unparseable, so the runner can't rule out that this record was already there; it fails closed and the record takes no effect. That commit can't be changed, so no record retires the id: restore the probe, or leave the finding standing and say why in the pull request |

Retirement findings, each `` - **<kind>** `<id>` (project/reach-probes/_retired.yml): <text> ``:

| Finding | Runner text | Remedy |
|---|---|---|
| `retirement contradiction` | `the probe file <files> still carries this id; a retirement record accounts only for a probe that left the set, and an exchange under the same id can't be retired: the replacement takes a new id` | remove the record, or delete the probe and replace the record with a fresh one |
| `invalid retirement record` | `no committed probe file under project/reach-probes/ in the history of HEAD ever carried this id` | remove the record; a mistyped id usually sits beside the real `removed` finding |
| `invalid retirement record` | `fails the retirement schema: <errors>` / `listed more than once; only the first record is read` | `retire` replaces the record or keeps one of the duplicates |
| `invalid retirement manifest` (no id) | `not parseable as YAML: …` / `refused and not read: …` / a schema error of the document itself | restore the committed manifest or re-propose its records through `retire`; never repair a record by guessing |

Provenance always states the retirement manifest, one of:

- `` - No retirement manifest `project/reach-probes/_retired.yml`: no probe id is retired. ``
- `` - The retirement manifest `project/reach-probes/_retired.yml` is present but unreadable (see Findings); no record in it takes effect. ``
- `` - Retired probe ids in `project/reach-probes/_retired.yml`: <n>, <k> of them new since the manifest's previous commit. ``, followed per retired id by `` - Retired `<id>` (<reason>)[, **new since the manifest's previous commit**]: <detail>; last existed at <sha12>; approved by <who> at <when>. ``

Quote these lines; a record marked new is a retirement the current change adds, which the reviewer must see. With removed ids the audited-set line ends `…, plus <r> removed probe id(s) that no effective retirement record accounts for, …`, and the headline names them: `**Not probed: N of T probes, R of them removed.**` without a readable not-constructible manifest, `**Not probed: N of T entries, L of them not constructible, R removed.**` with one. Quote the headline as written.

## Not-probed reasons and their routing

The runner writes every not-probed reason into the report's Probes table. These are the ones that call for a next step from the skill:

| Reason (as written by the runner) | Meaning | Next step |
|---|---|---|
| `declaration changed since derivation: …` | the declaration's content at HEAD is no longer the `blob:` anchor (`the content of <rel> at HEAD is no longer <df>`), the file is gone (`<rel> no longer exists at HEAD`) or is no regular file (`<rel> is not a regular file at HEAD`), it has uncommitted edits, its latest commit postdates a commit anchor, or a moved inherited `ref` (stale, R2). Under a section anchor the reason names each locator: `in <rel>, heading 3.1 changed`, `in <rel>, row AK-OS-07 not found`, `in <rel>, heading 3.1 is ambiguous (2 matches)`, joined by semicolons | offer `reconfirm` (per probe, after the diff; `references/reconfirm-and-migrate.md`) and, for the rest, `derive` with the entry filter set to exactly these probes' declaration paths (R5). A locator that is `not found` or `ambiguous` can't be re-confirmed, since the runner never follows a renumbered section: `derive` |
| `probe file is not committed; …` | the approved set isn't under version control yet (R11) | the operator commits `project/reach-probes/`, then `run` again |
| `not approved` | a probe file without an `approval` block, for example a copied example | the file was never approved through the gate; re-derive and approve the entry, or remove it: an uncommitted file just goes, but a committed one then reads `removed` and needs a `retire` record (`derived-in-error`) |
| `approval does not cover the current observation step` | the probe's `observe`, `environment`, or `teardown` no longer match `approval.observation_digest`: a later commit swapped the argv or a target and left the old approval in place, or the block was written without the digest | the probe was **withheld**, never executed. Never recompute or paste the digest by hand; re-derive and re-approve the entry, and tell the operator to read the file's history, since the approved step and the committed step differ |
| `tier T2 not requested` | T2 probes withheld by default (R8) | say so; add `--include-t2` only on the operator's explicit request |
| `not constructible: <code>` | a manifest entry: no probe exists at any tier, counted in the headline | `missing_environment_target` and `missing_observation_helper` are work in the target repository (the `detail` names it), after which `derive` turns the entry into a probe; the other three codes stay counted until the declaration or the environment changes |
| `environment target <name> failed (…)` | the Taskfile target didn't come up (R10) | relay the target's output; this is infrastructure, never "not reached" |
| `observation step exited <n>: …` / `observation step timed out …` | the observe argv failed or hung | relay; the probe's argv or the host's tooling (`gh` auth, `psql`) needs attention in the target |
| `observation step printed nothing` | the argv exited 0 without output; for a count and a set alike, silence is no observation and is never read as zero or as an empty set | the argv must print the observation (one integer, or one member per line, or a genuine `0` when nothing matches); re-derive the entry with an argv that does |
| `observation has <n> digits; a count has at most 18` | the printed count exceeds eighteen digits, which is a runaway command, not a measurement | relay; the argv is counting the wrong thing (a byte count, a concatenation); re-derive the entry |
| `anchor … lies outside the repository; change is not monitored` | external anchor (R6) | inform the operator; re-derive only on their request |
| `derived_from … is not a commit of the target repository` / `… not in the history of HEAD` | a commit anchor doesn't resolve in this clone (rewritten history, a squash merge that dropped the derivation commit; a shallow clone is refused before this, exit `2`) | re-derive, which records a content anchor; never edit `derived_from` by hand |
| `derived_from <df> is a content anchor, but an inherited spec is anchored by its pinned inherits[].ref` / `derived_from <df> is a content anchor, but <where>; a content anchor needs a declaration file inside the repository` / `derived_from <df> is not a content anchor of the form blob:<40 hex digits>` | a `blob:` anchor on an inherited or external declaration, or a malformed one (unresolved) | re-derive the entry; the scanner records the right anchor form per §Derivation anchors |
| `derived_from <df> is a section anchor, but declaration.sections is absent` / `declaration.sections needs derived_from of the form sections:<64 hex digits>, not <df>` / `derived_from '<df>' is not a section anchor of the form sections:<64 hex digits>` / `declaration.sections lists <kind> <loc> more than once` / `derived_from <df> does not match the digests in declaration.sections` / `declaration.sections is not a list of heading or row locators with a digest` / `derived_from <df> is a section anchor, but an inherited spec is anchored by its pinned inherits[].ref` / `… is a section anchor, but <where>; a section anchor needs a declaration file inside the repository` | the section anchor is inconsistent: hand-edited, a locator listed twice, a digest that doesn't produce the recorded `derived_from`, or sections on a declaration that can't carry them (unresolved) | re-derive the entry, or migrate it again with the helper in `references/reconfirm-and-migrate.md`; never adjust a digest or the anchor by hand |

Every other reason is quoted as written and needs no routing.

An executed probe whose `approval.mode` is `reconfirmed` carries the note `approval is a re-confirmation, not a re-derivation`, and Provenance lists them as `- Probes whose approval is a re-confirmation rather than a re-derivation: N (ids).` Quote both; they tell a re-approved probe from a re-derived one (R6) and are no finding.

A weakened probe that a clean, approved probe lists in `supersedes` is reported `superseded` (not probed, never executed, no finding) with the reason `superseded by <ids>; it was weakened: <reason>`, and Provenance lists them as `- Weakened probes superseded by a clean, approved probe, not executed: N (ids).` A replacement also needs `approval.observation_digest`, and one that is also a manifest entry (a contradiction) never takes effect. Provenance also carries one line per effective record, `- Supersede <old> by <new>: now expected <…>, tier <…>; before expected <…>, tier <…>; …; the replacement's approval is the only check of this change.`, the new side first; between two sets it lists the members added and removed, otherwise each set's members, every value as a code span and at most ten per list, a longer list ending `… and <n> more (shortened)`. Quote it, since a lower expectation shows only there. A second file that only shares a superseded id (a duplicate, a symlink, an unparseable file) keeps its own finding. While no listed replacement is clean and approved with that digest, the probe stays `weakened` and its reason ends with `supersede by <id> not in effect: it is <state>`.

## Derivation anchors

`derived_from` takes one of four forms (probe schema v1.2, a revision that keeps every v1.1 probe valid):

- **Content anchor** `blob:<40 hex>` for an in-repository declaration: the declaration file's git blob at derivation (`git rev-parse <commit>:<path>`). It names no commit, so a probe re-derived in the same pull request as its declaration change stays clean after a squash merge. The probe is stale when the file is dirty, gone at HEAD, or its HEAD blob differs. A directory or submodule at the path is no regular file and reads as stale; a symlink is anchored by its link text, not by the file it points to.
- **Section anchor** `sections:<64 hex>` for a Markdown declaration whose cited sections each resolve exactly once: `declaration.sections` lists one locator per cited section, `heading: "3.1.1"` (the heading's first token, one trailing dot stripped) or `row: AK-OS-07` (a pipe-table row's first cell), each with `digest`, the SHA-256 of that section's exact bytes; `derived_from` is the SHA-256 of `json.dumps([[kind, locator, digest], …], separators=(",", ":"), ensure_ascii=False)` in list order (`reach_audit.section_anchor()`). The probe is stale only when a cited section changed, no longer resolves, or matches more than once; an edit elsewhere in the file leaves it clean. The free-text `location` stays the citation. SHA-256 repositories can use it too, since it hashes bytes, not git objects. Two limits of the locators: a `row` digest covers only that row's own line, so a change to the table's header or a move of the unchanged row into another table leaves the probe clean; and the runner never cross-checks `declaration.location` against `declaration.sections`, so a citation that names another section than the locators isn't detected. The approval gate is the safeguard for both: the approver reads the locators and the citation together. Headings are ATX headings only; lines in fenced code, in an HTML comment block (`<!--` through `-->`), and in front matter (opening on the first line, after a byte order mark if there is one, and closed by a `---` or `...` line) are never headings or rows.
- **Pinned ref** for an inherited spec, compared with `inherits[].ref`; a content anchor there is refused.
- **Commit** for an external anchor (HEAD, unmonitored), and, as a migration rule, for an in-repository probe derived before v1.1: it stays valid, with its commit-ancestry check, until the next re-derivation records a content anchor. In a SHA-1 repository a move onto a commit anchor for an in-repository declaration is never a re-derivation and reads `weakened`: between two commits the runner can only tell that the declaration file was touched, not that it changed, which a path re-pointed at a decoy, a rename that's later restored, or an edit that's reverted all satisfy. Such a move recorded earlier, which a later move's walk reaches, is held to the content rule instead: the declaration's content at the new anchor, read at the path the move recorded, must differ from its content at the old one, or the move is only a re-anchoring (onto a squash merge's commit, say) that may change nothing but `derived_from` and the approval; a move that changes `declaration.path` is accepted only as a pure move of unchanged content that changes nothing else; and it must build on a legitimate derivation, as every content-anchor move does. The migration check routes this reason to a re-derivation, not to a supersede. A SHA-256 repository keeps commit anchors, since the content anchor is SHA-1 only.

Two limits to state when asked: an edit that goes A→B→A reads clean against A, since the content is the anchored one again (an accepted trade-off); and any byte change, whitespace included, is a change.

## Re-baseline rule

The runner's baseline for a probe is the commit that recorded its current `derived_from`. Moving `derived_from` starts a fresh baseline, and that is exactly how a single commit could lower an expectation and bump `derived_from` to launder its own weakening. The runner therefore accepts a moved `derived_from` as a **re-derivation only when the declaration itself changed**, and only when it builds on a legitimate previous derivation:

- every move of a content or section anchor, and of an inherited pin, whether re-derivation, re-confirmation, migration, or relabel: no commit between the previous derivation's recording commit and the move may have changed the probe (an intermediate plain probe change is never adopted), and the previous derivation must itself have been legitimate by the same rule, checked back to the probe's first commit or to a commit-anchor derivation, which keeps the rules below;
- section anchor: every new digest must be its section at the baseline commit, each locator resolving once there, a previously anchored section (or, from a file anchor, the file) must have changed since the recording commit, and at least one of the **new** anchor's sections must differ from the recording commit: a move answers to a change of what it now anchors on, not of something the previous anchor happened to cite. Moving a file anchor onto sections of an unchanged file is a migration: clean only when nothing but `derived_from`, `declaration.sections`, and `approval` changed. The reverse relabel, sections back to a `blob:`, is accepted on the same terms;
- re-confirmation (`approval.mode: reconfirmed`): on top of the anchor proof, only `derived_from`, the section digests, and `approval` may differ from the derivation it re-confirms, compared against the commit that recorded that derivation;
- content anchor: the new `blob:` must be the declaration's content at the baseline commit, and the previously anchored content (the old blob, or for a migrating commit anchor the file's content at that commit) must differ from it. A pure rename keeps the blob and moves `declaration.path`; the runner recognises it by path plus blob; a rename that records another anchor form at the same time (a commit, `blob:`, or `sections:` anchor onto another of them) is held to the same pure-move rule when the old path changed and the previously anchored content is unchanged at the new path;
- commit anchor (SHA-256 repository): the old `derived_from` must hold the declaration's content at the commit that recorded it, and the declaration's latest commit as of the new `derived_from` must lie outside the old one's history, so an anchor moved back to an older commit and then forward again across a change the probe had already seen proves nothing; when either commit no longer resolves (a squash merge dropped it), the declaration's content at the commit that recorded it stands in, and the two contents must differ; a declaration absent at the old anchor proves nothing;
- inherited spec: the pin in `spec/.spec-config.yml` must have moved to the new value;
- external anchor: it can't show a change, so its re-baseline is never accepted.

Otherwise the probe is reported `weakened` with `re-baselined without a declaration change: <moved>`, where `<moved>` names the baseline and the old and new anchor (or, for a path move, `<baseline> moved the declaration of <df> from <old> to <new>`), followed by the reason:

| Reason suffix | Meaning |
|---|---|
| `…, but <new> is not the content of <rel> at <baseline>` | the new blob isn't what the declaration held when the probe was recorded |
| `…, but <new_df> is not a content anchor of the form blob:<40 hex digits>` | the new anchor is malformed |
| `…, but a content anchor needs a declaration file inside the repository` | the new anchor sits on a declaration without a repository path |
| `…, but the previous derived_from is not a content anchor of the form blob:<40 hex digits>, so no declaration change can be shown` | the old anchor was a malformed `blob:` value |
| `…, but the previous derived_from cannot be resolved to a commit, so no declaration change can be shown` | the old commit anchor is gone (for example after a squash merge) |
| `…, but a move onto a commit anchor is never a re-derivation for a declaration inside the repository; re-derive it, which records a content or section anchor` | a SHA-1 repository's probe moved onto a commit anchor; re-derive, which records a `blob:` or `sections:` anchor |
| `…, but <rel> did not exist at the previous derived_from <commit>, so no declaration change can be shown` | the old commit anchor holds no declaration at that path, so it can't be proven where it was recorded |
| `…, but the content of <rel> did not change in between, and a re-anchoring may change nothing but derived_from and the approval` | a SHA-1 repository's earlier move onto a commit anchor, reached by a later move, kept the content and changed the probe |
| `…, but the declaration is missing at one of the two anchors, so no declaration change can be shown` | that earlier move names a declaration path that doesn't exist at one of its two anchors |
| `…, but it also moved the declaration from <rel> to <path>, and only a pure move of an unchanged declaration can change its path` | that earlier move re-pointed the probe at a file with other content, which a comparison across two files would read as a declaration change |
| `…, but <rel> did not change in between` | the anchored content is the same before and after the move |
| `…, but the previous derived_from <df> is not the content of <rel> at <recording>, where it was recorded, so no declaration change can be shown` | the old `blob:` anchor never matched the declaration when it was recorded, so it proves no change |
| `…, but the content of <rel> at the previous derived_from <commit> is not its content at <recording>, where it was recorded, so no declaration change can be shown` | the old commit anchor pointed at other declaration content than the file held when it was recorded, for example an anchor moved back to an older commit before this move forward |
| `…, but the same commit changed the probe beyond declaration.path, which a pure move of the declaration does not justify` | a pure move may change only `declaration.path` and the `approval` stamp of its re-derive; `expected`, `observe`, `tier`, or `declaration.location` changed too |
| `…, but it also changed which declaration the probe anchors on (<old> to <new>), which no re-derivation can show; derive a new probe instead` | the move switched between an inherited spec and a declaration file, or to another inherited spec, so neither side's anchor check covers it |
| `…, but it also moved the declaration from <rel> to <new_rel>, where the previously anchored content is not; record the rename as a pure move first, then re-derive` | a move re-pointed the probe at another file while the old declaration changed or went away; a rename with an edit takes two commits |
| `…, but it also moved the declaration from <rel> to <new_rel>, and that is no rename: …` | the old path still exists at the move, or the new one already existed where the previous derivation was recorded, so the move is a copy or a re-point, not a rename |
| `…, but <new_rel> already held <new_df> when the previous derivation was recorded in <recording>, so re-pointing at it shows no declaration change` | the probe was re-pointed at a file that already held that content, so nothing changed |
| `…, but the probe changed in <commits> after its previous derivation was recorded in <recording>` | the probe was edited between the derivation this move replaces and the move; the move would adopt that edit. An entry `merge <sha12>` is a merge that edited the probe |
| `…, but merge <sha12> changed derived_from after the previous derivation was recorded and before <baseline>, and a derivation recorded in a merge cannot be judged` | a merge recorded a derivation of its own, which the history walk can't list, so the later commit would be credited with the merge's changes. The merge stays in the probe's history, so a later re-derivation doesn't clear it either: the exit is a supersede. Record every derivation in a plain commit, never inside a merge |
| `…, but its previous derivation was no re-derivation either: <reason>` | the derivation this move replaces was itself a re-baseline without a declaration change; `<reason>` names why |
| `…, but none of the sections it now anchors on changed since the previous derivation was recorded in <sha>` | the move's new sections are all as they were when the previous derivation was recorded; a change elsewhere in the file, or in a section only the previous anchor cited, doesn't justify it |
| `…, but the recorded sections are not the content of <rel> at <sha>: <mismatches>` | a new section digest isn't what the declaration held at the baseline commit, or a locator didn't resolve once there |
| `…, but the previous derived_from <df> is not the content of its sections of <rel> at <sha>, where it was recorded, so no declaration change can be shown` | the old section anchor never matched the declaration when it was recorded |
| `…, but the anchored sections of <rel> did not change in between` | a section anchor moved although none of its sections changed |
| `…, but <rel> already held these sections when the previous derivation was recorded in <sha>, so re-pointing at it shows no declaration change` | the probe was re-pointed at another file that already held the same sections |
| `…, but a re-confirmation may change only derived_from, the section digests and approval, and it also changed <fields> against the derivation recorded in <sha>` | a re-confirmation also changed `expected`, `observe`, `tier`, `environment`, the declaration target, or a locator; revert it and re-derive instead |

Consequences to state plainly to the operator:

- A corrected typo in `derived_from`, a re-approval made "to be safe", or any `derived_from` move on a probe with an external anchor stays `weakened` until its declaration changes. The way back to clean is a re-derive **after a real declaration change**, never a hand edit and never a revert of the revert. That holds only for the first such move: a later re-derive builds on it, so once a weakened re-baseline is in the chain, every later move reads `its previous derivation was no re-derivation either`, real declaration change or not, and the exit is a supersede (next item).
- The rule can't tell a whitespace-only declaration change from a substantive one; a reformatting commit to the declaration file counts as a change. That is a stated limit of the mechanism, not a bug to route around.
- A probe that was weakened for another reason (a later commit to the file) isn't cleared by a re-approval, a re-confirmation, or a re-derivation after a real declaration change: every later move reaches back over that commit. The finding stands on the old probe until it's replaced by a newly derived and approved one. The runner walks the probe file's history with `git log --follow`, which pairs a new file with a deleted (rename) probe file of at least 50 % similarity, so the history goes on: overwriting the file with a fresh derivation, deleting it and adding a fresh one at the same path, and renaming it all still read `weakened`. A file created as a copy of a probe file that stays in place, untouched by that commit, starts its own history there: a similar probe added under a new id and file name is judged from the commit that created it, and inherits neither the old probe's revisions nor its `weakened` finding. The copy doesn't end the old probe's finding either. A copy that carries an id any probe file carried before it (the old probe's id included, even when that file was deleted and its path re-created since), or whose source is rewritten in the same commit, is read as an earlier probe moved and keeps its history; one re-added as a copy at a path an earlier file held reads `weakened` (`the probe was created in … as a copy of …`). The exit is a **supersede**: keep the weakened file, and derive and approve a new probe under a new id and file name on the same declaration entry that lists the old id in `supersedes` (schema v1.3). While the new probe is clean and approved with a matching `observation_digest`, the old one is reported `superseded`; the new one is judged on its own derivation, and its history walk ends before the old file's revisions, only when the new file was created as a copy of the kept old one: a record whose cut would reach the new probe's own revisions (the old file is a copy of the new one, or sits on its earlier path) is a finding. The record must be in the new probe's first commit, and that commit must be a plain commit: a probe created inside a merge reads `weakened` (`the probe's oldest listed revision …`). Adding the record later is a probe change that weakens the new probe. The runner can't judge whether the new expectation is weaker than the old one, and `approval` is unauthenticated metadata a commit can copy: the approval gate reviewing the replacement as a new probe is the only protection against a weaker one. The superseded row keeps the old weakening reason and Provenance shows both expectations and tiers for that review.
- A move to another declaration path, where the old one changed or is gone, is accepted only as a pure move: a rename (the old path gone at the move, the new one absent where the previous derivation was recorded), the previously anchored content unchanged at the new path, whichever anchor form the move records, and nothing else changed. A copy of the old content beside an edited original is no rename and reads `weakened`. Deleting or renaming the declaration and re-pointing the probe at a changed file in the same commit reads `weakened`; a rename with an edit takes two commits, the pure move first and the re-derivation after it. Where the old content exists nowhere any more (the declaration was edited, then renamed, before the probe followed), restore the old file for the one commit that records the pure move, or supersede the probe.
- A symlink is no declaration file: its blob is the link text, which stays put while the file it points to changes. A declaration that is a symlink at HEAD reads stale (`is not a regular file at HEAD`), and no move proves an anchor on one.
- A probe whose first commit already recorded an anchor that isn't the declaration there (it was derived before the declaration changed on the default branch and landed after) reads stale from that commit. Its first revision lowered nothing, so a re-derivation or re-confirmation that changes nothing but the anchor and the approval heals it (a section anchor is judged by the sections it names as that commit found them, not by the whole file); one that also changes the probe reads `weakened`.
- Residual risk: a commit anchor that doesn't resolve is judged by the declaration's content at the commit that recorded it, so a made-up commit anchor recorded together with a real declaration change reads like a squash-merged derivation.
- Residual risk: in a SHA-256 repository commit anchors keep the pre-v1.1 rules, including the two-commit re-anchor that a content anchor now refuses and reading a touched declaration as a changed one; re-derive to a section anchor (SHA-256) or content anchor to close it. A later pure move over an old commit anchor that no longer resolves reads `weakened`.
