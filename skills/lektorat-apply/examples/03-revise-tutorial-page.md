# Example 03: `revise` on a tutorial page with readability and voice findings

## Input prompt

"Revise docs/de/tutorials/erste-schritte.md — die ist zu schwer lesbar und springt zwischen aktiv und passiv."

## Input files (optional)

- `docs/de/tutorials/erste-schritte.md` — DE tutorial page, frontmatter declares `audience: end-users`, `track: end-user-docs`, `content_mode: tutorial`
- `AUDIENCES.md` — declares `end-users` with a property list that includes "no SRE background", "no command-line proficiency assumed"
- `spec/.spec-config.yml` — `canonical_language: en`, `languages: [en, de]`
- A `Lektorat`-local DE pipeline configured (for example LanguageTool with German rule set; the exact tool is recorded in `run.json`)
- The page is currently 187 lines, contains 12 fenced code blocks, 3 admonitions (`!!! note`), 2 Mermaid diagrams, 1 block-quoted citation, and frontmatter with five keys (`title`, `audience`, `track`, `content_mode`, `tags`)

## Expected behaviour

1. **Run `audit` first** on `docs/de/tutorials/erste-schritte.md` (single file, not a set — `revise` is per-artefact). Resolve language as DE (path segment under `docs/de/`); resolve audience as `end-users` from frontmatter (priority rule 1 wins over artefact-type defaults). Dispatch `lektorat-scanner` for the single-file scan; cache the pre-`revise` findings list and the pre-`revise` total count (for example: 2 critical, 8 warning, 14 suggestion = 24 total).
2. **Audit findings include**: D1 readability (WSTF 11.4 for `tutorial` content_mode exceeds the `crit` threshold of 10 → `critical`); D4 writing-style inconsistency (mixed active/passive voice in adjacent sentences in three locations → `warning`); D4 mixed address (one `du`-Anrede slipped into a section that otherwise uses `Sie` → `warning`); D2 unexplained abbreviation (`SRE` appears without expansion at first use, line 42 → `warning` — and the audience artefact explicitly says `end-users` have no SRE background, so the audience-fit angle is real).
3. **Compose the rewrite** addressing every `critical` and `warning` finding in a single pass: shorten the longest sentences (D1 metric improvement targets WSTF ≤7 corridor for `tutorial` mode), unify the voice to active (D4), unify the address to `Sie` throughout (D4), expand `SRE` to "Site Reliability Engineering (SRE)" at first use and use `SRE` thereafter (D2). `suggestion`-level findings are adopted only when they don't extend the rewrite scope; for example a `suggestion` to lift a single hidden prerequisite is folded in, but a `suggestion` to reorganise the page structure is not (out of scope for `revise` per §Operation C).
4. **Enforce semantic preservation** — every fact, claim, command, identifier, link target, frontmatter key, and code block from the original must still be present in the rewrite. Specifically: all 12 fenced code blocks stay byte-identical, all 3 admonitions stay byte-identical (markers `!!! note` plus indented bodies), both Mermaid diagrams stay byte-identical, the single block-quoted citation (`> …`) stays byte-identical, the frontmatter keeps all five keys in original order with their original values (no key churn).
5. **Forbid new factual content** — if the rewrite would introduce a new command, file path, product name, or URL not present in the original, surface a `suggestion` to the operator instead and stop. For example: the rewrite must not add "siehe auch: `taskfile`-Setup unter `setup/taskfile.md`" if the original did not mention that page.
6. **Render the unified diff** of the full-artefact rewrite, labelled `[revise] [addresses findings: 7f3c, a91b, c204, …] docs/de/tutorials/erste-schritte.md`, with at least three context lines. The diff is large (full-page rewrite); present it through the operator's diff-review channel rather than inline in the chat when the channel supports it.
7. **Wait for explicit operator decision** on the full diff: `approve` writes the rewrite to disk; `reject` discards it and the on-disk artefact stays untouched; `revise` invites operator edit instructions ("the second paragraph still feels too long", "keep the casual tone here") and re-composes the rewrite before showing the diff again. Until approval lands, the file on disk is unchanged.
8. **Re-run `audit` on the rewrite** before declaring success — produce `post-revise.json`. Compare the post-`revise` total finding count (for example: 0 critical, 2 warning, 16 suggestion = 18 total) against the cached pre-`revise` total (24). 18 < 24 → not a regression. If the post count had been higher (for example a clumsy phrasing introduced a new D4 finding), label the run a **regression** in the operator-facing confirmation and let the operator decide whether to keep, reject, or `revise`-again.
9. **Update the audit-trail folder** at `.audits/lektorat/2026-05-21-1455/` with `pre-revise.json` (cached audit), `post-revise.json` (rewrite audit), `rewrite.diff` (unified diff), and updated `summary.md` recording the non-regression status; do not overwrite the original `audit` reports — `revise` artefacts are siblings.
10. Confirm in German with the audit-trail folder path, the metric improvement (WSTF 11.4 → WSTF 6.8 — inside the `tutorial`-corridor), the dropped finding counts per dimension, and a follow-up reminder: the operator still needs to stage the file (`git add docs/de/tutorials/erste-schritte.md`), commit, and open a PR via `nolte-shared:pull-request-create`. This skill **never** stages, commits, bumps the plugin version, or opens PRs.
