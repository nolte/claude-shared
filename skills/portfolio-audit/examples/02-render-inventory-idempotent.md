# Example 02 — Render is idempotent when no manifests changed

A Render run from inside `claude-shared` regenerates the aggregated
portfolio inventory under `docs/<lang>/portfolio/`. Because no
Portfolio-Member's `project/portfolio.yml` has changed since the
previous render, the freshly rendered files are byte-identical to
what is already on disk and `task docs --strict` passes without any
drift. Exercises Operation 2's no-change happy path and the
auto-generated-header convention from `mkdocs-gen-files`.

## Input prompt

> Render the portfolio inventory.

## Input files

The active checkout is `claude-shared`; both detection markers
(`.claude-plugin/plugin.json` and
`spec/portfolio/portfolio-management/`) are present.

`docs/en/portfolio/index.md` and `docs/de/portfolio/index.md`
already exist from the previous render, each carrying the
`<!-- AUTOGENERATED -->` header that `mkdocs-gen-files` recognises
so `task docs` does not treat them as unmanaged drift.

The resolved Portfolio-Member set is the same as in Example 01
(three repositories: `release-tooling`, `changelog-bot`,
`docs-portal`). Each ships a `project/portfolio.yml`, a
`project/mission.md`, and an audience artefact under
`project/audiences.md`. None of those files have been modified since
the previous render — every relevant file's last commit on `develop`
is older than the previous Render run's commit on `claude-shared`.

`mkdocs.yml` declares both `en` (canonical) and `de` (translation)
in its `i18n` plugin block.

No prior Audit operation ran in this turn.

## Expected behaviour

1. **Repository-role detection passes.** The skill confirms it is
   inside `claude-shared` and selects the Render operation.
2. **Manifest collection runs afresh.** Because the same
   conversation has not already collected manifests in this turn
   (no preceding Audit), the skill performs the same `gh api`
   collection flow as Operation 1 step 2 and reduces each manifest
   to the structured per-repository summary.
3. **Per-repository sections generated** for each of the three
   Portfolio-Members: mission statement quoted verbatim from
   `project/mission.md` (never paraphrased), capability list with
   status badges (`active` / `experimental` / `deprecated`),
   audiences cross-referenced to each repository's audience
   artefact, and the outbound peer-reference list.
4. **Mermaid diagram generated** per
   `spec/project/mermaid-diagrams/`: `flowchart` direction `LR` for
   the cross-repo capability map, with the mandatory
   `<!-- diagram-source ... -->` marker, and English-only labels
   even inside the `docs/de/` translation.
5. **Historical-capabilities appendix omitted.** No archived
   repository in the resolved set carries previously registered
   capabilities, so the appendix section is not emitted (rather
   than emitted with an empty body).
6. **Files written** at
   `docs/en/portfolio/index.md` (canonical) and
   `docs/de/portfolio/index.md` (translation), each carrying the
   `<!-- AUTOGENERATED -->` header so `task docs` recognises them
   as managed.
7. **Build verified.** The skill runs `task docs` (which invokes
   `mkdocs build --strict`); the build passes.
8. **Idempotency confirmed.** Because no manifest, no
   `project/mission.md`, and no audience artefact changed since the
   previous render, the freshly written files are byte-identical to
   what was already on disk. The closing message in the operator's
   language explicitly notes this: lists the two written paths,
   names the three Portfolio-Member sections that were included, and
   adds the one-line note that the rendered output did not change
   (regeneration is idempotent when manifests didn't change), per
   Operation 2 step 7.
9. **Hard rules honoured.** No source-of-truth manifest modified;
   no spec edited; nothing published (publication remains the
   `task docs` / MkDocs pipeline's job); no rendered file written
   outside `claude-shared`; no mission or audience text invented
   (every quoted block is verbatim from the source file).
