## Kernaussage

Eine State-of-the-Art-Lizenzprüfung läuft end-to-end als Kette:
**Inventory/Discovery → SBOM → Lizenz-Identifikation → Klassifizierung →
Policy-Gate (allow/deny/review) → Remediation → Attribution/NOTICE → CI-Dauerprüfung.**
Die gesamte Kette ist an **SPDX** verankert: Jede Lizenz hat eine standardisierte
Kurz-ID (`SPDX-License-Identifier`), einen vollen Namen, den maschinenlesbaren
Volltext und eine kanonische permanente URL.

## Verifizierte Befunde (alle 3-0 bzw. 2-1 bestätigt)

### 1. SPDX ist das universelle Identifikations-Rückgrat — `high`
+ Jede Lizenz/Exception: standardisierte Kurz-ID + voller Name + Volltext + kanonische URL.
+ SPDX License Expressions: zusammengesetzte Formen (`OR` / `AND` / `WITH`) und
  `LicenseRef-[idstring]` für nicht-gelistete Lizenzen (SPDX-Spec Clause 10).
+ Quellen: spdx.org/licenses/, github.com/spdx/license-list-data, reuse.software/spec-3.3/

### 2. Jede SPDX-ID löst deterministisch zu Volltext + Metadaten auf — `high` ⭐
**Das ist der Kern für die Operator-Anforderung „jederzeit den vollständigen Lizenzinhalt nachlesen".**
+ Volltext als JSON: `https://spdx.org/licenses/[ID].json` → Feld `licenseText` (live verifiziert für MIT, Apache-2.0)
+ HTML-Seite: `https://spdx.org/licenses/[ID].html` (z. B. `MIT.html`, `Apache-2.0.html`, `GPL-2.0-only.html`)
+ Master-Index: `https://spdx.org/licenses/licenses.json`
  + Feld `licenseListVersion` (live: **3.28.0**)
  + Array `licenses`, je Eintrag: `licenseId`, `name`, `detailsUrl`, `isOsiApproved`, `isDeprecatedLicenseId`
+ Im Repo: `text/<ID>.txt` (Plaintext) und `json/details/<ID>.json` (Volldetails)
+ Einzel-JSON-Felder: `licenseText` (Volltext), `standardLicenseTemplate` (JSON-Key: `standard-license-template`),
  `standardLicenseHeader` (empfohlener Notice-Header), `seeAlso` (URL-Liste), `crossRef` (reichere Metadaten).
+ Quellen: github.com/spdx/license-list-data/blob/main/accessingLicenses.md

### 3. `github.com/spdx/license-list-data` = kanonische maschinenlesbare Distribution — `high`
+ Formate: JSON, RDFa, RDF/XML, RDF Turtle, RDF NT, JSON-LD, HTML, Text, SPDX-2.0-Template (1:1 zu Ordnern).
+ Wird automatisch bei Commits auf `master` aus der **autoritativen Quelle** `github.com/spdx/license-list-XML` gebaut.
+ CAVEAT: Der XML-Quelltext liegt im *separaten* `license-list-XML`-Repo; `license-list-data` enthält nur generierte Outputs.

### 4. ScanCode LicenseDB — größte freie Lizenz-DB, geht über SPDX hinaus — `high`
+ 2300+ community-kuratierte Lizenztexte (Recherche-Stand; „2000+" konservativ).
+ URL-Muster: `https://scancode-licensedb.aboutcode.org/<key>.<format>`
  + `.json` (strukturierte Metadaten), `.yml` (YAML), `.LICENSE` (roher Volltext) — live verifiziert für `gpl-2.0`
+ Jeder Eintrag: `spdx_license_key` → offizielle SPDX-Kurz-ID; Fallback `LicenseRef-scancode-<key>`,
  wenn kein SPDX-Match. Deprecated/alternative Keys unter `other_spdx_license_keys`.
+ Index-Endpunkte: `index.json` / `index.yml` (alle Keys + Links zu Detail-/Textdateien) → für programmatische Portfolio-Validierung.
+ Quellen: scancode-licensedb.aboutcode.org/help.html, aboutcode.readthedocs.io

### 5. ClearlyDefined — `high`
+ Früher: nur SPDX-gelistete Lizenzen, sonst `NOASSERTION`/`OTHER`.
+ v2.0 (ScanCode ≥ v32): mappt Nicht-SPDX-Lizenzen auf `LicenseRef-scancode-`-Formen;
  Organisationen entscheiden Handhabung per Allow-/Deny-Listen („All new LicenseRefs that are acceptable will need to be added to your allow list").

### 6. FSFE REUSE-Spec (v3.3) — In-Repo-Compliance + Volltextauflösung — `high`
+ Jede „Covered File" MUSS Licensing Information tragen: Comment-Header mit
  `SPDX-FileCopyrightText` (Copyright) + `SPDX-License-Identifier` (gültige SPDX-Expression).
  Alternativen: `.license`-Sidecar-Dateien, `REUSE.toml`, (deprecated) DEP5.
+ `LICENSES/`-Verzeichnis im Projekt-Root: ein Plaintext-File **pro SPDX-ID** für jede verwendete Lizenz
  (z. B. `LICENSES/GPL-3.0-or-later.txt`) → deterministische ID→Datei-Auflösung im Repo.
+ CAVEAT: REUSE verlangt nur Plaintext-Format, nicht dass der Inhalt = kanonischer SPDX-Text ist
  (echte Kanonisierung bleibt bei `license-list-data`). REUSE löst **keine** Kompatibilität/Korrektheit auf.

### 7. Policy-Gates / ORT — `high`
+ ORT trennt Klassifizierung von Regel-Auswertung:
  + `license-classifications.yml`: `categories` (permissive, copyleft, copyleft-limited, free-restricted,
    public-domain, source-available, commercial) + `categorizations` (SPDX-ID → Kategorie),
    z. B. `0BSD → [permissive, include-in-notice-file]`, `AGPL-3.0-only → [copyleft, include-in-notice-file, …]`.
    Header: generiert aus scancode-licensedb.aboutcode.org.
  + `evaluator.rules.kts`: Kotlin-Script-DSL-Ruleset → liefert Liste von Policy-Violations (CI-Gate via Severity-gated non-zero exit).
+ Quellen: github.com/oss-review-toolkit/ort-config, oss-review-toolkit.org/ort/docs/tools/evaluator

### 8. Reale OSS-Allowlists referenzieren SPDX-IDs — CNCF als kanonisches Beispiel — `high`
+ CNCF `allowed-third-party-license-policy`: explizite SPDX-IDs, verankert an der SPDX License List
  („License IDs refer to the SPDX License List, except where a URL is specified…").
+ Apache-2.0-Dependencies brauchen **kein** weiteres Review (gleiche Lizenz wie CNCF-Projekte selbst).
+ Allowlist (illustrativ): `0BSD, BSD-2-Clause, BSD-3-Clause, MIT, MIT-0, ISC, OpenSSL, PSF-2.0,
  Python-2.0, PostgreSQL, UPL-1.0, X11, Zlib`; Google-Patent-Lizenz für Golang als URL-spezifizierter Nicht-SPDX-Eintrag.
+ ⚠️ WIDERLEGT (1-2): die stärkere Aussage „CNCF ist rein permissiv / no copyleft by default / stützt permissive default-allow".
  → CNCF NICHT als reine Permissive-Allowlist überzeichnen; es ist eine SPDX-ID-verankerte Allowlist, die zufällig permissiv-lastig ist.

## Offene Fragen für die Spec

1. Default Allow/Deny/Review-Policy für ein permissiv ausgerichtetes Portfolio: CNCF-Allowlist
   bestätigt (permissiv-lastig), aber Deny-Liste (GPL/AGPL strong-copyleft) und Review-Tier
   müssen aus den (noch fehlenden) Pflichten-Evidenzen abgeleitet werden.
2. Konkrete Pflichten je Kategorie + copyleft↔permissive-Matrix → dedizierter Sourcing-Pass (GNU, Blue Oak, tldrlegal, choosealicense).
3. Verifizierter Tooling-Vergleich Python/Node/Go (SPDX-Expression-Output, CycloneDX vs. SPDX-SBOM, Genauigkeit).
4. KI-Provenienz im Lizenz-Inventar (LLM-Code, KI-Assets, Generator-Output-Lizenzen, SBOM/REUSE-Provenienz-Attribut).
