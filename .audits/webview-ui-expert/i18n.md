# Internationalisation (i18n) — Research notes for the webview-ui stack

Scope: Browser `Intl.*` primitives, `i18next` ^26 + `react-i18next` ^17 +
`i18next-browser-languagedetector` ^8, React 19, Vite 8, MUI v9 (incl. RTL
pipeline), `@mui/x-date-pickers` + `dayjs` (incl. `localizedFormat` plugin),
`react-hook-form` + `zod`, `notistack`, `react-router` v7, static-asset
delivery via nginx (`Content-Language`). Canonical app language for
kamerplanter is German (DE); English secondary.

## Methodology

- Two-source rule: every practice cites at least two independent authoritative
  sources (W3C i18n WG, Unicode CLDR / ICU, MDN, official library docs at
  i18next.com / react.i18next.com / mui.com / day.js.org / reactrouter.com /
  vitejs.dev, web.dev, Mozilla Hacks). Single-source claims are marked
  `unverified` and must be re-checked before normative use.
- Confidence levels: `high` (two or more first-party / standards sources),
  `medium` (one first-party plus strong corroborating secondary),
  `unverified` (single source or weak corroboration).
- Sources are linked directly; Medium and dev.to are excluded from the
  load-bearing slot.

## Best practices

### 1. Use `Intl.NumberFormat` for every numeric output

- **Practice:** Format every locale-sensitive number (decimals, currencies,
  percentages, units, file sizes) with `new Intl.NumberFormat(locale, opts)`
  instead of `toFixed`, `toLocaleString` ad-hoc, or hand-rolled separators.
  For currency, the `style: 'currency'` option requires `currency` (ISO 4217)
  and automatically supplies the correct fraction digits and symbol per
  locale (`26254.39 → "26.254,39 €"` in `de-DE`, `"$26,254.39"` in `en-US`).
- **Why:** The browser's CLDR data already encodes the locale-correct
  thousands separator, decimal mark, currency symbol position and digit
  shape; reimplementing this with `replace` regexes silently breaks for
  every locale you didn't test.
- **Applies to:** kamerplanter numeric KPIs, currency display, "X items"
  counters paired with `Intl.PluralRules` (see §3).
- **Sources:**
  - <https://developer.mozilla.org/en-US/docs/Web/JavaScript/Reference/Global_Objects/Intl/NumberFormat>
  - <https://developer.mozilla.org/en-US/docs/Web/JavaScript/Reference/Global_Objects/Intl/NumberFormat/NumberFormat>
  - <https://www.w3.org/International/questions/qa-number-format>
- **Confidence:** high.

### 2. Use `Intl.DateTimeFormat` / `Intl.RelativeTimeFormat` for every date or relative-time output

- **Practice:** Format absolute dates and times with `Intl.DateTimeFormat`
  (style or component options, never hand-built `${y}-${m}-${d}` strings)
  and relative spans ("vor 3 Tagen", "in 2 weeks") with
  `Intl.RelativeTimeFormat`. Use `dayjs` only where the project already
  depends on it (e.g., MUI-X DatePicker — see §11), and even then route
  *display* strings through `Intl` where the format is locale-only.
- **Why:** Both APIs ship CLDR-correct skeleton resolution and pluralised
  relative units out of the box. Hand-built strings break for non-ISO
  calendars (`u-ca-`), 12/24h conventions, and date-month order.
- **Applies to:** all timestamps, "letzte Bearbeitung", schedule labels.
- **Sources:**
  - <https://developer.mozilla.org/en-US/docs/Web/JavaScript/Reference/Global_Objects/Intl/DateTimeFormat>
  - <https://developer.mozilla.org/en-US/docs/Web/JavaScript/Reference/Global_Objects/Intl/RelativeTimeFormat>
  - <https://www.w3.org/International/articles/definitions-characters/>
- **Confidence:** high.

### 3. Plural keys use the JSON-v4 suffixes (`_one`, `_other`, …) backed by `Intl.PluralRules`

- **Practice:** Author plural variants with the i18next v4 suffix grammar —
  `key_one`, `key_other` for English/German; full CLDR set
  (`_zero`, `_one`, `_two`, `_few`, `_many`, `_other`) where the target
  language needs it. Do not branch on `count === 1` in component code.
  Polyfill `Intl.PluralRules` for legacy targets (i18next v21+ requires
  the Intl API and no longer ships its own fallback).
- **Why:** CLDR plural categories differ across locales (Arabic has six,
  Russian has four). Hard-coded `if (count === 1)` is wrong for every
  non-Germanic language and silently degrades.
- **Applies to:** every `t()` call with a `{{count}}` placeholder.
- **Sources:**
  - <https://www.i18next.com/translation-function/plurals>
  - <https://www.i18next.com/misc/json-format>
  - <https://developer.mozilla.org/en-US/docs/Web/JavaScript/Reference/Global_Objects/Intl/PluralRules>
  - <https://cldr.unicode.org/index/cldr-spec/plural-rules>
- **Confidence:** high.

### 4. Never concatenate translated fragments; pass values via interpolation placeholders

- **Practice:** Compose every translated sentence as a single key with named
  placeholders (`t('welcome', { name })` → `"Willkommen, {{name}}"`), even
  if the same fragments appear elsewhere. Treat string concatenation
  (`t('hello') + ' ' + name + ' ' + t('today')`) as a hard ban.
- **Why:** Word order, declension, gendered adjectives and bidi shaping
  vary across locales — a fragment-concatenated sentence cannot be
  reordered or inflected by the translator. The W3C i18n WG calls
  concatenation out as a primary i18n anti-pattern.
- **Applies to:** every UI string with a runtime variable. Static glue
  ("OK", labels) can remain split because there is no inter-locale word
  order to preserve.
- **Sources:**
  - <https://www.w3.org/International/questions/qa-text-rendering>
  - <https://learn.microsoft.com/en-us/globalization/internationalization/concatenation>
  - <https://www.i18next.com/translation-function/interpolation>
- **Confidence:** high.

### 5. Keep `html[lang]` and `html[dir]` synchronised with the active i18next language

- **Practice:** On every language change emitted by i18next, set
  `document.documentElement.lang` to the resolved BCP-47 tag (`de`, `en`)
  and `document.documentElement.dir` to `'rtl'` for RTL languages
  (Arabic, Hebrew, Persian) and `'ltr'` otherwise. Bootstrap both from
  the detected language during init so the first paint is correct.
- **Why:** `lang` drives screen-reader pronunciation (WCAG 3.1.1, Level A),
  CSS `:lang()` selectors, browser hyphenation, spell-check, and quote
  rendering. `dir` drives the entire bidi layout including MUI-emitted
  styles (see §10).
- **Applies to:** app bootstrap (`i18n.on('languageChanged', …)`).
- **Sources:**
  - <https://www.w3.org/International/questions/qa-html-language-declarations>
  - <https://developer.mozilla.org/en-US/docs/Web/HTML/Global_attributes/lang>
  - <https://www.w3.org/WAI/WCAG21/Understanding/language-of-page.html>
- **Confidence:** high.

### 6. Use the `<Trans>` component (with component slots) for translations that contain inline markup

- **Practice:** Whenever a translated sentence contains formatting (`<a>`,
  `<strong>`, `<br/>`) or embedded React elements, use the `<Trans>`
  component with numbered (`<0>…</0>`) or named (`<bold>…</bold>`)
  component slots — *not* `dangerouslySetInnerHTML`, *not* string-built
  HTML. Keep `i18next` interpolation `escapeValue` at its default `true`
  so any plain `{{var}}` insertion is HTML-escaped.
- **Why:** `<Trans>` lets translators move components around inside the
  sentence while the rendered output stays under React's reconciler — no
  raw HTML reaches the DOM, so XSS surface is limited to the components
  you explicitly pass in. `dangerouslySetInnerHTML` defeats that
  guarantee and requires DOMPurify on every insertion site.
- **Applies to:** marketing copy with links, legal blurbs, any text that
  needs bold/emphasis inside a single sentence.
- **Sources:**
  - <https://react.i18next.com/latest/trans-component>
  - <https://www.i18next.com/translation-function/interpolation>
  - <https://react.dev/reference/react-dom/components/common#dangerously-setting-the-inner-html>
- **Confidence:** high.

### 7. Configure the language-detector order with explicit caches: `querystring -> cookie -> localStorage -> navigator -> htmlTag`

- **Practice:** In `i18next-browser-languagedetector` set
  `detection.order = ['querystring','cookie','localStorage','navigator','htmlTag']`
  and `detection.caches = ['cookie','localStorage']`. Use a deterministic
  cookie name (`i18next`) and storage key (`i18nextLng`) so the SSR layer
  and edge nginx can read the same source of truth.
- **Why:** A persisted user choice (cookie/localStorage) must beat the
  browser's `navigator.languages` so a German user on a colleague's
  English laptop sees their own language. The querystring slot is the
  override hatch for support / link-sharing.
- **Applies to:** `i18n.ts` init, nginx `Accept-Language` redirect when a
  cookie is present (see §16).
- **Sources:**
  - <https://github.com/i18next/i18next-browser-languageDetector#readme>
  - <https://www.i18next.com/overview/configuration-options>
  - <https://www.npmjs.com/package/i18next-browser-languagedetector>
- **Confidence:** high.

### 8. A persisted user choice always overrides automatic detection

- **Practice:** When the user picks a language in the UI, call
  `i18n.changeLanguage(lng)` *and* write the choice through to the
  caches the detector reads (`detection.caches`). Never silently
  re-detect on each load. On `i18next.init`, prefer `lng` set from the
  persisted value over `navigator.languages`.
- **Why:** Detector caching is unreliable when `changeLanguage` is
  invoked manually; explicit persistence prevents the next session from
  flipping back to the browser default and losing the user's choice.
- **Applies to:** the language-switcher component, app bootstrap.
- **Sources:**
  - <https://www.i18next.com/overview/configuration-options>
  - <https://github.com/i18next/i18next-browser-languageDetector#caches>
  - <https://www.w3.org/International/questions/qa-lang-priorities>
- **Confidence:** high.

### 9. Split translations by feature namespace and lazy-load per route

- **Practice:** Organise JSON files as one namespace per feature
  (`auth.json`, `plants.json`, `settings.json`, `common.json`), and
  load namespaces on demand via `i18next-http-backend` (or
  `i18next-resources-to-backend` for Vite dynamic imports). Declare
  required namespaces on each route or via `useTranslation(['plants'])`;
  combine with React's `Suspense` (`react.useSuspense: true`) so the
  route doesn't paint untranslated keys.
- **Why:** A single monolithic `translation.json` grows with every
  feature and is downloaded entirely on first paint. Per-namespace lazy
  loading keeps the initial bundle small and aligns translation
  ownership with feature ownership.
- **Applies to:** Vite chunk-splitting strategy, route-level data
  loaders.
- **Sources:**
  - <https://www.i18next.com/principles/namespaces>
  - <https://react.i18next.com/guides/multiple-translation-files>
  - <https://www.i18next.com/how-to/add-or-load-translations>
- **Confidence:** high.

### 10. Set MUI v9 `direction: 'rtl'` and wire the Emotion `stylis-plugin-rtl` cache when an RTL locale is active

- **Practice:** When the active locale is RTL, build the MUI theme with
  `createTheme({ direction: 'rtl', ... })` *and* mount an Emotion
  `CacheProvider` whose cache uses `[prefixer, rtlPlugin]` from
  `@mui/stylis-plugin-rtl`. Mirror the choice with `dir="rtl"` on the
  HTML root (§5). For LTR locales mount the default cache.
- **Why:** MUI emits logical-property CSS via Emotion; the stylis plugin
  rewrites `margin-left`/`padding-left` and friends to their RTL
  equivalents at insertion time. Without the cache plugin the layout
  flips text direction but leaves the component spacing broken.
- **Applies to:** root provider tree (`CacheProvider -> ThemeProvider ->
  App`), MUI component overrides that hard-code `marginLeft` etc.
- **Sources:**
  - <https://mui.com/material-ui/customization/right-to-left/>
  - <https://www.npmjs.com/package/@mui/stylis-plugin-rtl>
  - <https://emotion.sh/docs/@emotion/cache>
- **Confidence:** high.

### 11. Wire MUI-X `LocalizationProvider` with the matching `dayjs` locale and `localeText` preset

- **Practice:** Pass three things in lockstep: (a) the dayjs locale (e.g.
  `import 'dayjs/locale/de'` + `dayjs.locale('de')` on language change),
  (b) `LocalizationProvider dateAdapter={AdapterDayjs} adapterLocale="de"`,
  and (c) `localeText={deDE.components.MuiLocalizationProvider.defaultProps.localeText}`
  from `@mui/x-date-pickers/locales`. Extend dayjs once with
  `localizedFormat` and prefer `format('L LT')` over hand-built tokens.
- **Why:** `adapterLocale` controls the format mask and weekday/month
  names; `localeText` controls the *button and label* strings inside the
  picker. They are independent — setting only one leaves the picker
  half-translated (e.g., German calendar, English "Today" button).
- **Applies to:** every `<DatePicker>`, `<DateTimePicker>` etc., the
  i18n bootstrap (loading dayjs locales lazily alongside the i18next
  resource).
- **Sources:**
  - <https://mui.com/x/react-date-pickers/adapters-locale/>
  - <https://mui.com/x/react-date-pickers/localization/>
  - <https://day.js.org/docs/en/plugin/localized-format>
  - <https://day.js.org/docs/en/i18n/changing-locale>
- **Confidence:** high.

### 12. Translate `zod` validation errors via a custom `errorMap` driven by `react-i18next`

- **Practice:** Author Zod schemas with stable error *keys*, then provide
  a custom `errorMap` (set via `z.setErrorMap` or `zodResolver(schema,
  { errorMap })`) that resolves each key through `t()` at validation
  time. Alternatively use the `zod-i18n-map` adapter. Keep schemas free
  of `t()` calls so they remain serialisable and reusable outside React.
- **Why:** Embedding `t()` inside the schema (a) freezes the message at
  module-load time (before i18next is ready), (b) couples server-shared
  schemas to the React tree, (c) prevents type-inference and reuse.
- **Applies to:** every Zod schema feeding `react-hook-form`'s
  `zodResolver`.
- **Sources:**
  - <https://zod.dev/?id=customizing-errors-with-zoderrormap>
  - <https://react-hook-form.com/docs/useform#resolver>
  - <https://github.com/aiji42/zod-i18n>
- **Confidence:** high.

### 13. Pass translated strings into `notistack` at call sites — do not store keys in the message queue

- **Practice:** Resolve translations with `t()` *immediately before*
  calling `enqueueSnackbar(t('errors.savePlant'), { variant: 'error' })`.
  Where messages must update on language change (long-lived snackbars),
  render a custom `content` component that subscribes to `useTranslation`
  internally.
- **Why:** `notistack` is a render queue: storing a raw key delays
  resolution and breaks if the consumer renders outside the i18next
  React tree (e.g., from an axios interceptor). Resolving at the call
  site keeps the message stable for the lifetime of the toast.
- **Applies to:** axios error interceptors, mutation `onError` handlers,
  any background task that fires a snackbar.
- **Sources:**
  - <https://notistack.com/getting-started>
  - <https://notistack.com/api-reference>
  - <https://react.i18next.com/latest/usetranslation-hook>
- **Confidence:** medium.

### 14. Configure `fallbackLng` + `supportedLngs` explicitly; do not rely on accidental fallback

- **Practice:** Declare `supportedLngs: ['de','en']` (canonical first) and
  `fallbackLng: 'de'` (or a per-language map, e.g. `{ 'de-CH': ['de','en'],
  default: ['de'] }`). Set `nonExplicitSupportedLngs: true` only if you
  intend `en-US` to resolve to `en` resource files; combined with an
  HTTP backend, watch out for spurious 404s for variant tags.
- **Why:** Without these, i18next silently falls back to `en-US` and may
  request resource files (`/locales/cimode/...`, `/locales/dev/...`)
  that don't exist. Explicit allow-listing is also a defence against
  resource-path injection via the language detector's querystring slot.
- **Applies to:** `i18n.init`.
- **Sources:**
  - <https://www.i18next.com/overview/configuration-options>
  - <https://www.i18next.com/principles/fallback>
- **Confidence:** high.

### 15. Use locale-prefixed URLs (`/de/...`, `/en/...`) via React Router v7 — not cookie-only routing

- **Practice:** Encode the locale in the path with a React Router v7
  dynamic segment (`/:locale/*`) or the `prefix(...)` helper, with the
  canonical locale (`/de/`) implicit at the root or explicit by
  redirect. The router becomes the single source of truth for the
  current locale; on every navigation, sync i18next via
  `i18n.changeLanguage(params.locale)`.
- **Why:** Locale-in-URL is shareable, bookmarkable, cache-friendly
  (CDN keying), and gives crawlers a deterministic URL per language
  variant (precondition for `hreflang`, §17). Cookie-only routing
  cannot be served as a per-language variant by static infrastructure
  and silently re-detects on every browser.
- **Applies to:** route tree, link rendering (a `LocaleLink` wrapper
  that prepends the active locale), redirects from the locale-less
  root.
- **Sources:**
  - <https://reactrouter.com/start/framework/routing>
  - <https://developers.google.com/search/docs/specialty/international/managing-multi-regional-sites>
  - <https://www.w3.org/International/questions/qa-when-xhtmlplus.en>
- **Confidence:** high.

### 16. Drive nginx `Accept-Language` redirects only at the locale-less root, and emit `Content-Language` on every localised response

- **Practice:** Configure nginx so that requests to `/` (and only `/`)
  consult the `Accept-Language` header — typically via the
  `nginx-module-accept-language` module or a small Lua block — to
  302-redirect to `/de/` or `/en/`. Honour an existing `i18next` cookie
  ahead of `Accept-Language`. Add `add_header Content-Language $locale`
  on `/de/*` and `/en/*` location blocks. Use `=` location matching to
  avoid redirect loops on deep links.
- **Why:** RFC 7231 specifies `Accept-Language` for request-side
  negotiation and `Content-Language` for the response label. Returning
  `Content-Language` lets browser caches and downstream proxies key
  variants correctly. Restricting negotiation to `/` prevents the
  rewrite from clobbering deep links shared between users.
- **Applies to:** nginx `server { ... }` block, deployment config.
- **Sources:**
  - <https://datatracker.ietf.org/doc/html/rfc7231#section-3.1.3.2>
  - <https://datatracker.ietf.org/doc/html/rfc7231#section-5.3.5>
  - <https://www.nginx.com/resources/wiki/modules/accept_language/>
- **Confidence:** high.

### 17. Render `hreflang` alternates server-side (or at build time) in the initial HTML — never inject from React

- **Practice:** Emit one `<link rel="alternate" hreflang="de" href="https://kamerplanter.example/de/<path>">`
  per supported locale plus an `hreflang="x-default"` link to the
  negotiation root, inside `<head>` of the static `index.html` (or via
  the Vite build step that emits one HTML per locale). Make
  relationships bidirectional (each locale lists every other one,
  including itself). Use ISO 639-1 language + optional ISO 3166-1
  Alpha-2 region codes.
- **Why:** Google's crawler typically processes static `<head>` markup
  but may skip JS-injected tags; React Helmet-style runtime injection
  is unreliable for `hreflang` discovery. Bidirectional relationships
  are a hard requirement of Google Search Central.
- **Applies to:** `index.html` template, per-locale build outputs.
- **Sources:**
  - <https://developers.google.com/search/docs/specialty/international/localized-versions>
  - <https://developers.google.com/search/blog/2013/04/x-default-hreflang-for-international-pages>
  - <https://www.w3.org/International/questions/qa-html-language-declarations>
- **Confidence:** high.

### 18. Mark in-page foreign passages with `lang="..."` on the wrapper element (WCAG 3.1.2)

- **Practice:** For any phrase or block whose language differs from the
  document language, wrap it in an element with `lang` (e.g.
  `<span lang="en">user-facing string</span>` inside a German page).
  Exclude proper names, technical terms, and assimilated loanwords.
  Make this the default for any in-content code block whose comments
  remain in English on a German page.
- **Why:** WCAG 3.1.2 (Level AA) requires the language of parts to be
  programmatically determinable so screen readers switch
  pronunciation. Improves search engine accuracy for mixed-locale
  content.
- **Applies to:** docs pages, marketing pages, MDX content embedded in
  the SPA.
- **Sources:**
  - <https://www.w3.org/WAI/WCAG22/Understanding/language-of-parts.html>
  - <https://webaim.org/techniques/language/>
- **Confidence:** high.

### 19. Use `Intl.Collator` for locale-aware sorting; never rely on `Array.sort()`'s default Unicode-code-point order

- **Practice:** Create one reusable `new Intl.Collator(locale, {
  sensitivity: 'base' })` per locale and pass `collator.compare` to
  `Array.prototype.sort`. Treat `String.prototype.localeCompare` as
  acceptable for a single comparison but switch to `Intl.Collator`
  for any sort longer than ~50 items (60–80 % faster in practice).
- **Why:** The default lexicographic order miscompares German `ä`,
  Swedish `ö`, accented French vowels, and Turkish dotless-i. Collator
  honours CLDR collation tables per locale.
- **Applies to:** plant lists, table column sorts, autocomplete option
  ranking.
- **Sources:**
  - <https://developer.mozilla.org/en-US/docs/Web/JavaScript/Reference/Global_Objects/Intl/Collator>
  - <https://www.unicode.org/reports/tr10/>
- **Confidence:** high.

### 20. Use `Intl.ListFormat` for human-readable lists; never hand-roll `arr.join(', ')` + " and "

- **Practice:** Format conjunctive ("A, B und C") and disjunctive
  ("A, B oder C") lists with
  `new Intl.ListFormat(locale, { style: 'long', type: 'conjunction' })`
  / `{ type: 'disjunction' }`. Combine with `style: 'narrow'` for
  compact UI where applicable.
- **Why:** Joiners (`und`/`and`/`et`/`Oxford comma`) and final-item
  punctuation vary by locale; CLDR encodes the rules.
- **Applies to:** "Plants needing water today: A, B and C" copy,
  multi-select summary chips.
- **Sources:**
  - <https://developer.mozilla.org/en-US/docs/Web/JavaScript/Reference/Global_Objects/Intl/ListFormat>
  - <https://tc39.es/proposal-intl-list-format/>
- **Confidence:** high.

### 21. Enable a missing-translation reporter in dev and a silent missing-key counter in production

- **Practice:** In development, set `debug: true` and
  `saveMissing: true` plus a `missingKeyHandler` that logs `(lng, ns,
  key, fallbackValue)` to the console. In production, replace the
  handler with a sampled error-reporter (Sentry / custom backend)
  so untranslated keys appear in observability dashboards instead of
  in user-facing strings. Keep `saveMissing` *off* in production to
  avoid stray write traffic.
- **Why:** Translation drift is silent — keys ship without resources
  and only show as the raw key string. A reporter makes the drift
  detectable; pseudo-localisation (§22) makes it visible during
  QA.
- **Applies to:** `i18n.init` config branched on `import.meta.env.MODE`.
- **Sources:**
  - <https://www.i18next.com/overview/configuration-options>
  - <https://github.com/i18next/i18next/issues/1082>
- **Confidence:** medium.

### 22. Run pseudo-locale tests (`i18next-pseudo`) in CI before every release

- **Practice:** Add a `pseudo` post-processor (e.g. `i18next-pseudo`)
  that wraps every translated string with markers and expands its
  length 30–40 %. Wire a CI job — or a manual QA toggle — that
  switches the app to the pseudo locale and runs Playwright/Cypress
  visual snapshots. Failure modes detected: missing keys (no
  markers), text truncation (markers cut off), layout overflow,
  hard-coded English strings.
- **Why:** German is 30 % longer than English; Finnish more.
  Pseudo-localisation catches truncation and missing keys before a
  real translator sees the strings.
- **Applies to:** CI workflow, MUI components with fixed widths.
- **Sources:**
  - <https://www.npmjs.com/package/i18next-pseudo>
  - <https://www.w3.org/International/articles/article-text-size/>
- **Confidence:** medium.

### 23. Wrap the React tree in `<Suspense>` and set `react.useSuspense: true` so first paint cannot show untranslated keys

- **Practice:** Initialise `initReactI18next` with
  `react: { useSuspense: true }` (the default). Wrap each route in
  `<Suspense fallback={<RouteSkeleton/>}>` so namespace lazy-loads
  block the render. If you opt out (`useSuspense: false`), gate every
  consumer on `const { t, ready } = useTranslation(); if (!ready)
  return null;`.
- **Why:** Without Suspense (or the `ready` guard), the first paint
  prints raw keys (`"plants.title"`) or fallback English text in the
  middle of a German UI. Suspense is the only way to keep a
  locale-prefixed route paint coherent.
- **Applies to:** root router, every route component that calls
  `useTranslation`.
- **Sources:**
  - <https://react.i18next.com/latest/usetranslation-hook>
  - <https://react.dev/reference/react/Suspense>
- **Confidence:** high.

### 24. Load dayjs locales as default-export modules and switch them in tandem with i18next

- **Practice:** Import locales as default-export modules
  (`import locale_de from 'dayjs/locale/de'`) and call
  `dayjs.locale(locale_de)` on every i18next `languageChanged` event.
  Avoid bare side-effect imports (`import 'dayjs/locale/de'`) because
  some bundlers (esp. server builds, Nuxt) drop them.
  Bundle dayjs locales into the per-locale chunk via
  `import(/* @vite-ignore */ \`dayjs/locale/${lng}.js\`)`.
- **Why:** Side-effect imports are fragile under tree-shaking and
  SSR. Coupling the locale-switch to the i18next event prevents
  date pickers from drifting out of sync with the rest of the UI.
- **Applies to:** the `languageChanged` listener; MUI-X picker setup
  (§11).
- **Sources:**
  - <https://day.js.org/docs/en/i18n/changing-locale>
  - <https://day.js.org/docs/en/i18n/loading-into-browser>
  - <https://day.js.org/docs/en/plugin/localized-format>
- **Confidence:** high.

### 25. Treat keys as stable, lowercase, dotted identifiers — not English sentences

- **Practice:** Author keys like `plants.list.empty` or
  `auth.login.submit`, not the English text itself. Reserve a
  `common` namespace for buttons, errors, and other reusable atoms;
  feature-specific keys live in feature namespaces (`plants`,
  `settings`, …). Document the convention in CONTRIBUTING so two
  developers don't put the same string in two namespaces.
- **Why:** Text-as-key (`t('Welcome, {{name}}!')`) is appealing for
  prototypes but breaks the moment the English wording changes: the
  key changes too, and every translation falls out of sync. Stable
  identifier keys decouple the source language from the wording.
- **Applies to:** translation file layout, code review.
- **Sources:**
  - <https://www.i18next.com/principles/namespaces>
  - <https://www.i18next.com/principles/best-practices>
- **Confidence:** medium.

### 26. Pre-load only the canonical + active locale; defer the rest

- **Practice:** Bundle the canonical locale (`de`) and the active
  locale (resolved by the detector) into the first paint via static
  imports. Load every other locale through `i18next-resources-to-backend`
  with Vite dynamic imports
  (`(lng, ns) => import(\`./locales/${lng}/${ns}.json\`)`) so each
  locale + namespace pair becomes its own Vite chunk. Pair with
  `partialBundledLanguages: true` so already-imported resources
  short-circuit the backend.
- **Why:** Loading every locale up-front balloons the initial JS
  payload by hundreds of KB. Vite's dynamic-import code-splitting
  produces one chunk per `(locale, namespace)` pair automatically, so
  the only network cost on language switch is the new chunk.
- **Applies to:** `i18n.ts` resource loader, Vite build config.
- **Sources:**
  - <https://vitejs.dev/guide/features#dynamic-import>
  - <https://www.i18next.com/how-to/add-or-load-translations>
  - <https://www.i18next.com/overview/configuration-options>
- **Confidence:** high.

## Currency addendum (2026-07-24)

- RFC 7231 is superseded by RFC 9110 (June 2022); the `Accept-Language`/`Content-Language` semantics are unchanged.
- Zod 4 removes `setErrorMap`/`errorMap` in favor of the unified `error` parameter and `z.config({ customError })`; the spec rule is now phrased version-aware (Zod 3 and Zod 4 forms).
- The `nginx-module-accept-language` third-party module is unmaintained and the cited nginx wiki is retired; `map`-/njs-based negotiation is the current standard route. The spec additionally pins negotiation to the locale-less root (exact-match location) so deep links are never rewritten.
