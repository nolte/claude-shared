## §1  (settled=True)

Mature diagnostic disciplines refuse to act on a hypothesis until a MECHANISM is demonstrated, and all three reference disciplines converge on the same falsifiable bar. Fault-tree analysis (FTA) defines a minimal cut set as a set of basic events that is jointly NECESSARY AND SUFFICIENT for the top event — correlation is never enough. Differential diagnosis confirms a cause only by a pathognomonic finding or a collectively unique/discriminating feature set, arrived at by an iterative hypothetico-deductive loop, not by the most available guess. git bisect and delta debugging both operationalise ISOLATION ASYMMETRY: a cause is proven when there is a reproducible oracle (fails-when-present, passes-when-absent) and a good/bad or passing/failing boundary such that flipping the one changed factor flips the outcome (ddmin's 1-minimal difference). This grounds three admissible proofs of mechanism — (a) reproduced outside the suite via a standalone scriptable oracle, (b) isolation asymmetry (the failure toggles with one controlled variable: run order, seed, single-test isolation, or a bisected commit), (c) derived from library source with a discriminating counter-example that predicts one behaviour and excludes the rival hypothesis. Triage must be CLUSTER-WISE — group failures by traceback frame plus message shape, because clustering many failures repeatedly collapses to a handful of root causes, whereas test-wise triage re-diagnoses the same mechanism N times. The spec should encode a checklist gate: no remediation until the failure is classified into a root-cause category (async-wait, order-dependency, concurrency, environment, network, locator/selector) AND at least one of (a)/(b)/(c) holds for the cluster it belongs to.

**Per-framework:**
- **selenium**: Reproduce-outside-suite (proof a): drive the single failing interaction with a minimal standalone WebDriver script (bypassing pytest) that asserts the same condition; deterministic repro + inverse pass = oracle. Isolation asymmetry (proof b): rerun the one test in a fresh WebDriver session / clean profile to distinguish victim (passes isolated -> prior-test state pollution) from brittle (still fails isolated -> intrinsic race, typically an implicit/explicit-wait gap). Discriminating counter-example (proof c): read Selenium source / exception type — StaleElementReferenceException vs ElementClickInterceptedException vs ElementNotInteractableException vs NoSuchElement/TimeoutException are mutually-exclusive signatures that each pick out a different mechanism (detach vs overlay-cover vs not-yet-interactable vs not-rendered).
- **cypress**: Reproduce-outside-suite: run the single spec headed via `cypress run --spec <file>` (optionally `--env grep=<title>`) so the failure is observed independent of the surrounding suite; the command video/screenshot is the oracle artifact. Isolation asymmetry: use `it.only` plus `Cypress._.times`/`--config retries=0` to repeat the one test and toggle `testIsolation` (Cypress 12+ clears state between tests) to separate state-pollution victims from intrinsic brittles. Discriminating counter-example: Cypress's retry-ability error text distinguishes 'element detached from DOM' (re-query needed) from 'element covered by another element' (overlay) from 'never found' (render/route) — each maps to a distinct mechanism.
- **playwright**: Reproduce-outside-suite: `playwright test <file> -g "<title>" --repeat-each=N --workers=1` reproduces the one test deterministically outside the full run; the trace (`--trace on`) is the standalone oracle. Isolation asymmetry: `--workers=1` vs parallel and toggling per-test fixtures/`test.describe.configure({ mode })` separates order/parallel victims from intrinsic brittles; `--repeat-each` forces intermittent (async/race) failures to surface. Discriminating counter-example: Playwright auto-waits for actionability, so a TimeoutError's actionability log ('element is not visible' / 'intercepts pointer events' / 'not stable / animating' / 'not attached') is the discriminating signature that names the mechanism.

**Findings:**
- FTA defines a minimal cut set as a group of basic events collectively NECESSARY AND SUFFICIENT to cause the top event; remove any one member and it is no longer a cut set. This is the discipline's bar for 'mechanism established' — a demonstrated necessary-and-sufficient condition, not a correlation. Spec analogue: a failure hypothesis is actionable only when the named cause is shown sufficient (its presence produces the failure) and necessary (its absence removes it). _[generic]_  
  — source: https://www.nrc.gov/docs/ML1216/ML12160A316.pdf
- NUREG-0492 (NRC Fault Tree Handbook) is the canonical treatment of qualitative fault-tree evaluation and minimal cut set determination via Boolean reduction; a minimal cut set is the necessary-and-sufficient combination of basic faults for the top event. Citeable authority for the necessary-and-sufficient criterion. _[generic]_  
  — source: https://dspace.mit.edu/bitstream/handle/1721.1/106497/16-63j-fall-2012/contents/related-resources/MIT16_63JF12_faulttree.pdf
- In differential diagnosis, PROOF of a diagnosis demands a pathognomonic finding, or findings that considered collectively are uniquely characteristic of that disease and no other; discriminating (discriminatory) features rule categories in or out. Spec analogue for proof (c): the mechanism is demonstrated when library source or an instrumented probe yields a DISCRIMINATING counter-example — an observation the leading hypothesis predicts and every rival hypothesis excludes (e.g. the element was detached mid-click vs. covered by an overlay vs. not yet rendered are distinguished by different, mutually-exclusive observable signatures). _[generic]_  
  — source: https://getoncourse.ai/notes/us-medical-pg/diagnosis/differential-diagnosis/
- Diagnostic reasoning is the hypothetico-deductive method: generate initial hypotheses, gather targeted discriminating information, revise probabilities, and iterate until confidence crosses a threshold — not first-plausible-cause commitment. The 1971 Annals of Internal Medicine paper 'Logical Principles in Differential Diagnosis' is the citeable primary source that a diagnosis is confirmed only by uniquely-characteristic (pathognomonic/discriminating) findings and is otherwise held as a ranked, testable hypothesis. Spec analogue: an agent must maintain a ranked hypothesis set for each failure cluster and only escalate the top hypothesis to 'actionable' after a discriminating observation, never on availability alone. _[generic]_  
  — source: https://www.acpjournals.org/doi/10.7326/0003-4819-75-1-89
- git bisect performs binary search across a good/bad commit boundary and is trustworthy ONLY given a reproducible test that FAILS when the bug is present and PASSES when it is absent — the isolation-asymmetry oracle. This grounds proof (a) 'reproduced outside the suite': the mechanism is demonstrated when a standalone scriptable check reproduces the failure deterministically and its inverse passes, independent of the full E2E suite. Cost is ~log2(n) tests, motivating a scripted oracle over manual repro. _[generic]_  
  — source: https://ldpreload.com/blog/git-bisect-run
- git bisect requires a clean working tree and a repeatable pass/fail oracle; 'a repeatable test is what makes bisect trustworthy.' Reinforces that isolation asymmetry (proof b) is only valid when exactly one variable — here the commit — is toggled between the pass and fail observations, with everything else held constant. _[generic]_  
  — source: https://gun.io/news/2025/05/git-bisect-debugging-guide/
- Delta Debugging (Zeller & Hildebrandt, ddmin) isolates the DIFFERENCE between a passing and a failing configuration and reduces it to a 1-minimal failure-inducing change — a change set where removing any single element makes the failure disappear. This is the formal operational definition of proof (b) isolation asymmetry: the mechanism is demonstrated when the failure toggles with one minimized changed factor (test-run order, RNG seed, an injected wait, a single fixture, or a bisected line/commit), everything else fixed. _[generic]_  
  — source: https://homes.cs.washington.edu/~mernst/teaching/6.893/readings/zeller-tse.pdf
- Cluster-wise triage is empirically justified: clustering thousands of failures reveals that most noise traces back to a handful of root causes, and manual stack-trace inspection of systemic (co-occurring) flaky failures identifies shared root causes far faster than reading traces one at a time. Spec rule: group failures by traceback frame + message shape and diagnose the CLUSTER once, not each test; co-failure across unrelated tests is itself evidence of a shared systemic mechanism (environment/network/dependency) rather than N independent bugs. _[generic]_  
  — source: https://dl.acm.org/doi/10.1145/3756681.3756945
- Empirical flaky-test taxonomy gives the closed classification set an agent must place a cluster into before acting: order-dependency is a leading category, followed by async/wait (~45% of flaky cases), concurrency/race (~20%), randomness, environment, network, and platform. Classification-before-touching means every cluster is assigned exactly one primary category, because the admissible proof and the remediation differ per category (e.g. async-wait -> explicit condition wait; order-dependency -> fixture isolation). _[pytest]_  
  — source: https://arxiv.org/pdf/2101.09077
- Order-dependency splits into VICTIM vs BRITTLE (Gruber et al.: of 4,461 order-dependent flaky tests, 3,168 victims, 738 brittles). This is isolation asymmetry made concrete for the suite: run the test in isolation — if it PASSES alone but fails in-suite it is a victim (polluted by prior state); if it still FAILS alone under the recorded seed it is brittle (self-polluting). The isolated pass/fail flip is the demonstrated mechanism; a hypothesis that cannot produce this flip is not yet actionable. _[pytest]_  
  — source: https://www.sciencedirect.com/science/article/pii/S0164121223002327
- Per-framework reproduction-outside-the-suite and isolation-asymmetry tooling exists and is scriptable, so the spec's proof gates are testable: pytest-randomly prints and accepts --randomly-seed to deterministically replay an order-induced flake, and -p no:randomly plus running a single node id (-k / node id) isolates the test; pytest-repeat / pytest-flakefinder run one test N times to force a non-order intermittent failure to reproduce. pytest's own flaky-tests doc is the canonical reference. An agent can therefore mechanically execute (a) standalone repro and (b) isolation-asymmetry checks. _[pytest]_  
  — source: https://github.com/pytest-dev/pytest-randomly
- The pytest documentation's Flaky-tests page is the citeable framework-owner reference recommending isolation and controlled reproduction (fixed seed, isolated runs, explicit waits over sleeps) as the route from symptom to mechanism, aligning the spec's admissible proofs with official guidance rather than blog folklore. _[pytest]_  
  — source: https://docs.pytest.org/en/stable/explanation/flaky.html

## §2  (settled=True)

Every diagnostic channel answers a bounded class of question and is silent (or actively misleading) outside it, so the discipline is matching artefact to question rather than collecting artefacts. The layered channels are: rendered-state (screenshot, video, DOM snapshot) answers "what did the app show at moment T"; the network/request channel (Trace Viewer network tab, cy.intercept, BiDi/CDP network, HAR) answers "did the action actually reach the server and with what payload/response"; console/log channels answer "did the client throw"; and time-travel snapshots (Playwright trace, Cypress command log) answer "what was the DOM at the instant of the action". A screenshot can never settle "did the action happen" — only the server-side request record can — and a full-page screenshot taken with captureBeyondViewport/fullPage cannot settle "is this below the fold" because stretching the rendering surface to the full document height re-resolves viewport-relative (100vh/height:100%) and fixed elements against the enlarged surface, distorting vertical layout while leaving width (and therefore horizontal-overflow evidence) truthful; a viewport-only screenshot must always be paired. Request-count diffing between a known-good baseline run and the candidate run localizes regressions, but a measured count of zero is the least trustworthy result — it cannot distinguish "the app correctly issued no request" from "my interception never armed" — so a zero is only admissible behind a positive control that first proves the channel captures a request it is guaranteed to see.

**Per-framework:**
- **playwright**: Trace Viewer (actions timeline + before/action/after DOM snapshots with click-coordinate marker + screenshots film strip + Network tab with request/response headers & bodies + filtered Console tab) is the primary bundle; page.screenshot({fullPage,clip,animations}) for rendered state with the fullPage/captureBeyondViewport fold-distortion caveat (pair fullPage:false); browser.newContext({recordHar}) for the replayable HAR request ledger; recordVideo for whole-run video; page.on('console'|'request'|'response') and CDP session for live console/network; page.on('pageerror') for uncaught client errors.
- **cypress**: Command log with time-travel before/after DOM snapshots per command (the trace-viewer equivalent); automatic failure screenshot (screenshotOnRunFailure, on by default); run video (video, OFF by default since v13, opt-in); cy.intercept for observing/asserting/stubbing HTTP (the network channel, spy or stub); cy.request for direct server assertions independent of the UI; cy.task for Node-side/server/filesystem logging the browser cannot emit; Cypress.log/cy.log for annotations that surface inside the screenshots and video.
- **selenium**: selenium/video (ffmpeg) sidecar container mapped 1:1 per browser node, per-session in Dynamic Grid, opt-in via capabilities (the video channel — verify topology, do not assume); BiDi/CDP addConsoleListener for console (client-error channel) and BiDi network interception for requests (action-propagation channel); HAR captured via a proxy (BrowserMob-style) in front of the browser for the persisted, diffable request ledger; TakesScreenshot / getScreenshotAs for rendered state (full-page needs CDP Page.captureScreenshot with the same captureBeyondViewport caveat).

**Findings:**
- Playwright Trace Viewer is a single artefact that answers several distinct questions at once: an actions timeline with duration/status/locator (which step failed and how long it took), before/action/after DOM snapshots with the click coordinate marked (what the DOM was at the action, where the pointer landed), a screenshots film strip (what was rendered), a Network tab exposing per-request method/status/headers/request body/response body (did the request go out, with what payload, what came back), and a filtered Console tab (did the client log/throw). It CANNOT answer questions about traffic outside the traced context window or server-internal state. _[playwright]_  
  — source: https://playwright.dev/docs/trace-viewer
- A rendered-state screenshot answers 'what did the app display at moment T' but cannot answer 'did the action actually happen / reach the backend' — a button can look clicked, show a spinner, or show success text while no request was dispatched; only the network/request record settles whether the action propagated. This is the core channel-to-question mapping: UI-render evidence and action-propagation evidence are different artefacts. _[generic]_  
  — source: https://learn.cypress.io/cypress-fundamentals/how-to-debug-failing-tests
- The captureBeyondViewport/fullPage trap: a full-page screenshot expands the rendering surface to the document's full scroll height (CDP Page.captureScreenshot captureBeyondViewport:true 'ignores the window constraints and renders the full height of the document', typically paired with Emulation.setDeviceMetricsOverride). Elements sized in viewport units (100vh) or height:100% and position:fixed elements are then resolved against the enlarged surface, so they stretch/repeat/float and the vertical layout no longer reflects what a real viewport showed. Consequently a full-page screenshot cannot answer 'is element X below the fold' — the fold itself was redefined. Width is not resized, so horizontal-overflow evidence remains truthful. Rule: always pair a viewport-only screenshot (fullPage:false / captureBeyondViewport:false) with any full-page capture. _[playwright]_  
  — source: https://screenshotone.com/blog/capture-beyond-viewport-in-puppeteer-and-chrome-devtools-protocol/
- Playwright fullPage screenshots are documented to misbehave with sticky/fixed elements: 'A header with position:fixed renders in its normal viewport position for every slice Playwright captures, so it can appear repeated or floating over content in the final stitched image'; the recommended workaround is to hide the offending element for the capture. This corroborates that full-page captures distort vertical placement and cannot be used to reason about below-the-fold position. _[playwright]_  
  — source: https://github.com/microsoft/playwright/issues/30149
- Playwright records all context network traffic into a HAR via recordHar on browser.newContext (headers, cookies, content, timings, request/response bodies), giving a replayable, diffable request ledger; HAR replay matches URL+method (and POST payload) strictly. HAR answers 'exactly which requests were issued and what the full request/response envelope was' across the whole context lifetime — a superset of what the per-step trace network tab scopes to. _[playwright]_  
  — source: https://playwright.dev/docs/mock
- Cypress diagnostic channels: the command log records every command with a time-travel DOM snapshot before/after each action (what the DOM was at the step); screenshots are captured automatically at the point of failure (what was rendered); video of the whole run is recordable but is DISABLED by default since Cypress v13 (video:false) so its availability cannot be assumed; cy.intercept observes/asserts HTTP requests (did the request go out, with what body, spy or stub); and cy.task pushes data from the browser context to the Node process to emit logs the browser channel cannot (server/filesystem-side facts). _[cypress]_  
  — source: https://docs.cypress.io/app/guides/screenshots-and-videos
- Cypress video recording default flipped to off (video:false) as the shipped default, so on a failing CI run a video may not exist; screenshotOnRunFailure (screenshots on failure) is independently toggleable. A diagnosis playbook must therefore treat Cypress video as opt-in, not a guaranteed artefact, and fall back to the command-log DOM snapshots + failure screenshot. _[cypress]_  
  — source: https://github.com/cypress-io/cypress/issues/26157
- Selenium 4 exposes console logs and network as live channels via the BiDi/CDP bridge: addConsoleListener registers a callback for every browser console message (client-error channel) and the network interception APIs let the test observe/mock requests and auth (action-propagation channel). These are the framework-native equivalents of Playwright's console/network trace tabs and Cypress cy.intercept. _[selenium]_  
  — source: https://reflect.run/articles/selenium-4-events/
- Selenium Grid video is not built into the browser node: recording requires a separate selenium/video (ffmpeg) sidecar container mapped 1:1 to each browser container, and in Dynamic Grid the video container is provisioned per session and the recording saved on teardown. Video is disabled by default in Selenium 4 and must be opted into via capabilities. So 'is there a video for this failure' depends on Grid topology, not on the client test — a diagnosis rule must verify the sidecar mapping rather than assume a recording exists. _[selenium]_  
  — source: https://github.com/SeleniumHQ/docker-selenium
- Selenium network traffic is captured in HAR form via a proxy in front of the browser (network logs captured as HTTP Archive/HAR), the classic BrowserMob/proxy pattern, giving the same diffable request ledger that Playwright recordHar and Cypress cy.intercept provide natively. The HAR answers 'complete list of requests + full envelopes'; unlike BiDi live listeners it survives the run as a file. _[selenium]_  
  — source: https://www.gridlastic.com/selenium-4-guide.html
- Request-count diffing and the positive-control rule: comparing per-endpoint request counts between a known-good baseline run and the candidate run localizes a regression to a specific call, but a measured count of zero is the least trustworthy measurement because it is indistinguishable from a broken/never-armed interceptor. The flakiness literature's underlying warning is that insufficiently-guarded assertions (a passing zero is a maximally weak assertion) are a direct source of tests that pass while measuring nothing. The disciplinal fix, borrowed from experimental method, is a positive control: before trusting a zero, first assert the channel captures a request it is guaranteed to see, proving the apparatus works. _[generic]_  
  — source: https://dl.acm.org/doi/fullHtml/10.1145/3476105

**Open questions:**
- Is there an authoritative, directly citeable software-testing source that names the 'positive control' rule for network/interception assertions (that a zero count is inadmissible without first proving the channel captures a guaranteed request), as opposed to importing the term from experimental science and the adjacent flaky-assertion literature?  
  — revisit: Revisit if a Playwright/Cypress/Selenium doc, a testing-discipline book, or a peer-reviewed paper explicitly formalizes a positive-control / apparatus-verification step for request-count assertions; until then cite it as a borrowed experimental-method principle plus the flaky-assertion survey rather than a native testing citation.
- Does captureBeyondViewport distort ONLY viewport-unit (100vh/vh) and position:fixed/sticky elements, or does it also perturb percentage-height (height:100%) chains and background-attachment:fixed in a way that changes the width-truthful / height-distorted split the rule relies on? The primary sources confirm the fixed/viewport-unit cases and that width is not resized, but do not exhaustively enumerate every CSS construct affected.  
  — revisit: Revisit if a controlled reproduction (or a Chromium/Playwright issue) shows a case where horizontal-overflow evidence in a full-page capture is ALSO unreliable, which would weaken the 'width still reveals horizontal overflow' half of the pairing rule and require narrowing it.
- For Selenium, is there a single first-party (selenium.dev) reference that pairs BiDi console/network capture with HAR export in one supported workflow, or does grounded practice still rely on a third-party proxy (BrowserMob) for the persisted HAR while BiDi covers only the live stream?  
  — revisit: Revisit when selenium.dev documents native BiDi-to-HAR export (removing the proxy dependency), at which point the Selenium per_framework mapping should drop the proxy caveat.

## §6  (settled=True)

A per-component-library hazard catalog is built by reading the component's actual installed source (node_modules), not its docs, because the behaviours that break E2E tests — which DOM event opens vs. activates a control, what ARIA role is emitted in a given variant, where the node is portalled, where focus lands, and how positioning/scroll side-effects move the element — live in source and diverge from prose. MUI is the worked example: a MenuItem is role="menuitem" in a plain Menu but is cloned with role="option" (inside a role="listbox") when used in a Select; the Select opens on onMouseDown (left-button-only) while items commit on onClick; the Popover clamps upward past a 16px marginThreshold; keepMounted leaves closed menus in the DOM; selectedMenu auto-scrolls and focuses the selected (not first) item; and unrecognised props spread onto the FormControl/root DOM node. Each entry records component + resolved version range, trigger-vs-activation event, per-variant role/aria, portal placement, focus target, positioning/scroll side-effects, the resulting stable selector strategy, and a source file+symbol anchor. The catalog is kept from rotting by pinning every entry to a semver range and re-verifying against source on each major bump — and version drift itself (docs said MUI 7, package.json resolved MUI 9) is a first-class diagnostic hazard: always resolve the installed version from the lockfile, never trust the documented one.

**Per-framework:**
- **selenium**: Resolve the installed MUI version from the lockfile before writing locators. Open a Select by dispatching a real mouse press (Actions.moveToElement(trigger).clickAndHold()/pointerDown or a click that produces mousedown) — a bare .click() on the trigger may not open it; select by clicking the item. Query the portalled listbox from the document root (By.cssSelector with role='listbox'/role='option'), not from the trigger's subtree; wait on visibility (visibilityOfElementLocated), not mere presence, because keepMounted leaves nodes in the DOM.
- **cypress**: cy.get('[role=\"button\"]').trigger('mousedown', {button: 0}) to open the Select (Select responds to mousedown, not click), then cy.get('[role=\"option\"]').contains(...).click() to commit. Scope to the portal with cy.get('body [role=\"listbox\"]') since content is portalled outside the trigger; assert .should('be.visible') rather than existence because keepMounted keeps closed items mounted.
- **playwright**: page.getByRole('combobox').click() opens it (Playwright's click issues a real mousedown/mouseup so it works), then page.getByRole('option', {name}).click(). Query by role scoped to the page (portalled to body) — getByRole('option') not getByRole('menuitem') inside a Select; use toBeVisible() over count assertions because of keepMounted, and avoid coordinate/boundingBox asserts because the Popover clamps upward near the viewport edge.

**Findings:**
- Authoritative behaviour lives in the component's installed source, not its docs: MUI's Select opens the menu on handleMouseDown (guarded to left-click only, `if (event.button !== 0) return`) and closes by committing on the item's onClick via handleItemClick → update(false). A catalog entry must therefore state the trigger event (mousedown) separately from the activation event (click), because a test that only fires click on the trigger never opens the menu. Rule is testable: an agent can assert the harness dispatches a real mousedown to open and a click to select.  
  — source: https://raw.githubusercontent.com/mui/material-ui/master/packages/mui-material/src/Select/SelectInput.js (handleMouseDown, handleItemClick)
- Role assignment is variant/context dependent and must be recorded per variant: MenuItem defaults to role='menuitem' (hardcoded default in MenuItem.js), but when rendered inside a Select the child is React.cloneElement'd with `role: 'option'` and `aria-selected`, and the surrounding list slot is given `role: 'listbox'`. Consequence for tests: getByRole('menuitem') finds nothing inside a Select — the same visual component is queried as role='option' there. The catalog entry must map variant → emitted role, and the selector rule is testable by role.  
  — source: https://raw.githubusercontent.com/mui/material-ui/master/packages/mui-material/src/MenuItem/MenuItem.js (role='menuitem' default) and .../Select/SelectInput.js (cloneElement role:'option', list role:'listbox')
- Popover positioning clamps to the viewport: marginThreshold defaults to 16px, and on bottom overflow getPositioningStyle shifts the popover upward (`top -= diff`) while also adjusting elemTransformOrigin. A menu opened near the viewport bottom therefore does not sit at its nominal anchor offset, so any coordinate-relative-to-anchor assumption in a test is fragile. The catalog entry records this as a positioning side-effect; the derived rule (assert by role/text, never by pixel offset) is testable.  
  — source: https://raw.githubusercontent.com/mui/material-ui/master/packages/mui-material/src/Popover/Popover.js (getPositioningStyle, marginThreshold default 16)
- keepMounted plus portalling breaks DOM-order and presence-based selectors: keepMounted='If true, the component is kept mounted on the DOM even after closing', so a closed menu's items remain in the DOM. Combined with portalling, DOM order does not match React order. The catalog entry must note that presence in the DOM is not visibility — tests must assert on the open/visible state (e.g. the item is in an unhidden portal), not merely that a node exists. Testable: assert visibility, not query-count.  
  — source: https://mui.com/material-ui/api/portal/ and https://v4.mui.com/api/portal/ (keepMounted, disablePortal semantics)
- Portalled content lives outside the trigger's DOM subtree while React events still bubble through the React tree, not the DOM tree. So a test must scope its query to the portal container (typically document.body / the injected portal root), not to the trigger element's descendants; and focus after open lands inside the portal. The catalog entry records the portal placement and the scoping rule, which is testable by asserting the queried node's ancestor is the portal root.  
  — source: https://react.dev/reference/react-dom/createPortal (portal keeps React-tree position; events bubble through React tree not DOM tree)
- selectedMenu is an auto-scroll/auto-focus hazard: 'simple menus attempt to vertically align the currently selected menu item with the anchor element, and the initial focus will be placed on the selected menu item'; setting variant='menu' opts out of that positioning and focus behaviour. So on open the selected item (not the first item) receives focus and the list may be scrolled to bring it into view — a test that assumes focus/keyboard navigation starts at the first item, or that the item sits at a fixed scroll position, is wrong. Catalog records focus-target and scroll-on-open per variant; testable via activeElement.  
  — source: https://mui.com/material-ui/react-menu/ (Selected menu / variant='menu' section)
- Unrecognised props spread onto the root DOM node: MUI's convention is that props not consumed by the component are passed through `...other` onto the root element (e.g. a Select's props reach the underlying FormControl/input root). Two catalog-relevant consequences: arbitrary attributes leak to the DOM, and a data-testid handed to the component may land on an outer root rather than the interactive node, so the test-id anchor must be verified against the rendered node. The rule (verify which node receives the test-id) is testable by inspecting the attribute's owner element.  
  — source: https://mui.com/material-ui/api/select/ and MUI slot/`...other` prop-spreading convention documented across component APIs

## §7  (settled=False)

All five Selenium hazards hold except one direction issue. Selenium's element_to_be_clickable resolves on displayed+enabled alone, doing NO viewport or hit-test check; its native click targets the element's in-view centre but is descendant-tolerant, so a centre landing on an inner node clicks that descendant with no interception raised (a silent wrong-target/no-op); ActionChains dispatch pointer events at coordinates with no interactability hit-test (delivering silently to whatever overlay sits on top); and a JS HTMLElement.click() is coordinate-independent but fires only the click event with no mousedown/mouseup and isTrusted=false. Playwright and Cypress both eliminate the pointer-position and non-descendant-overlay hazards BY DESIGN via mandatory auto-scroll-into-view plus a receives-events/"covered" hit-test at the action point, and eliminate the JS-click no-mousedown hazard by dispatching real (Playwright) or native-like (Cypress) input; both retain the descendant-tolerance gap by design and both expose force:true to opt out of the hit-test entirely. The only Selenium claim that does not settle is is_displayed() returning False for a scrollable-ancestor-clipped element: framework behaviour here is documented as inconsistent and this repo's own §C already flags the direction as unconfirmed.

**Per-framework:**
- **playwright**: Eliminates BY DESIGN: (a) viewport-position hazard — auto-scrolls into view and requires Stable (two-frame bounding-box stability); (b) non-descendant overlay/occlusion hazard — the Receives-Events check hit-tests the actual action point and fails if another element intercepts; (c) JS-click no-mousedown hazard — dispatches real trusted browser input (full pointer/mouse sequence). RETAINS BY DESIGN: descendant-tolerance — the injected hit-target check accepts a descendant at the point, so a container click can still land on an inner node. OPT-OUT: force:true disables the Receives-Events hit-test (re-introduces silent wrong-target); trial:true runs the checks without acting. Actionability source: playwright.dev/docs/actionability.
- **cypress**: Eliminates BY DESIGN: (a) viewport-position — ALWAYS scrolls the element into view before acting; (b) non-descendant overlay hazard — the 'not covered' check hit-tests the element's centre coordinates and additionally nudges the page past fixed-position coverers; (c) disabled/hidden/readonly/detached/animating are each checked. RETAINS BY DESIGN: descendant-tolerance — 'if a child element covers the exact coordinate, the event fires on the child' rather than raising. NUANCE: events are native-like but not necessarily isTrusted like a real driver dispatch. OPT-OUT: {force:true} bypasses ALL checks including 'covered', forcibly firing at the element. Source: docs.cypress.io/app/core-concepts/interacting-with-elements.
- **selenium**: Confirms all four core hazards. element_to_be_clickable = displayed && enabled only (no viewport, no hit-test). Native element.click() targets the in-view CENTRE and is descendant-tolerant — raises `element click intercepted` only for a NON-descendant obscurer, silent on a descendant. ActionChains (Actions API) dispatch pointer events at coordinates with NO interactability hit-test — silent delivery to an overlay. JS HTMLElement.click() is coordinate-independent but fires only `click` (no mousedown/mouseup, isTrusted=false) — a silent no-op on mousedown-only or isTrusted-guarded components. Selenium eliminates NONE of these by design; a suite must add its own elementFromPoint guard (a diagnostic aid, not a race-free gate — TOCTOU/CWE-367). The is_displayed()-clips-under-scroll-ancestor claim is unconfirmed (see open question).

**Findings:**
- Selenium's element_to_be_clickable / elementToBeClickable is satisfied by displayed && enabled ALONE — the implementation is literally `element != null && element.Displayed && element.Enabled`. It performs no viewport-position check and no overlay/occlusion hit-test, so an element outside the viewport or fully covered still resolves the condition as clickable. _[selenium]_  
  — source: https://cezarypiatek.github.io/post/why-click-with-selenium-so-hard/ (also selenium.dev expected_conditions API: https://www.selenium.dev/selenium/docs/api/py/selenium_webdriver_support/selenium.webdriver.support.expected_conditions.html)
- WebDriver native element.click() computes the in-view CENTRE point and only raises `element click intercepted` when the element receiving the pointer event is OBSCURING the target — defined as an element that is neither the target nor a DESCENDANT of it. When the centre lands on a descendant, the click is not intercepted and dispatches on the descendant with no error: descendant-tolerance makes a wrong-target click on a container silent. This gap is closed by no mainstream framework by design. _[selenium]_  
  — source: W3C WebDriver2 Element Click algorithm + `element click intercepted`/`obscuring` definitions (https://www.w3.org/TR/webdriver2/#element-click); verified in-repo strategy matrix at spec/project/e2e-test-stability/en.md lines 70,76
- Selenium ActionChains (move_to_element(_with_offset) then click, i.e. the W3C Actions API) dispatch raw pointer events at the resolved coordinates and perform NO interactability/hit-test check — unlike element.click() they do not verify the target receives the event, so they deliver silently to whatever element sits at the point (e.g. an overlay). _[selenium]_  
  — source: selenium.dev ActionChains / W3C Actions API (https://www.selenium.dev/documentation/webdriver/actions_api/); verified in-repo matrix spec/project/e2e-test-stability/en.md line 79
- A JavaScript executeScript element.click() (HTMLElement.click()) is coordinate-independent (bypasses occlusion entirely because it targets the node, not a point) but is a synthetic dispatch: it fires ONLY the click event — no mousedown, no mouseup, no pointer events — and the resulting event has isTrusted=false. It is therefore a silent no-op against components that activate on mousedown (e.g. a MUI Select trigger) or that guard on isTrusted. _[selenium]_  
  — source: MDN HTMLElement.click() (https://developer.mozilla.org/en-US/docs/Web/API/HTMLElement/click) + MDN Element/mousedown notes on synthetic click; verified in-repo matrix spec/project/e2e-test-stability/en.md line 77,87

Playwright auto-waits for all relevant checks before acting and scrolls the element into view. _[playwright]_  
  — source: https://playwright.dev/docs/actionability and https://github.com/microsoft/playwright/blob/main/docs/src/actionability.md (per-action check table)
- Playwright's Receives-Events check is the hit-target test at the action point — it detects an intercepting overlay (some other element capturing the click) and, combined with mandatory scroll-into-view and Stable, eliminates BY DESIGN the Selenium viewport-position hazard and the non-descendant-overlay silent-click hazard. Because it dispatches real trusted browser input, it also eliminates the JS-click no-mousedown hazard. It does NOT eliminate the descendant-tolerance gap: Playwright's injected hit-target check is a descendant-tolerant elementsFromPoint walk, so a descendant at the point is still accepted. _[playwright]_  
  — source: https://playwright.dev/docs/actionability (Receives events / auto-waiting); verified in-repo matrix spec/project/e2e-test-stability/en.md lines 70,81,161
- Playwright force:true disables NON-ESSENTIAL actionability checks — explicitly it does not check that the element receives events (the hit-test) — so a forced click re-introduces the silent wrong-target hazard by design and is opt-in. (Playwright also offers trial:true, which runs the actionability checks but does not perform the action.) _[playwright]_  
  — source: https://github.com/microsoft/playwright/blob/main/docs/src/actionability.md (Force option) and https://playwright.dev/docs/actionability
- Cypress runs, before every action command, in order: scroll the element into view; ensure not hidden; not disabled; not detached; not readonly; not animating; not covered; scroll the page if still covered by a fixed-position element; then fire the event at the desired coordinates. Hidden = width/height 0, visibility:hidden or display:none on element/ancestors, or position:fixed and offscreen/covered. The 'not covered' check hit-tests the element's CENTRE coordinates. _[cypress]_  
  — source: https://docs.cypress.io/app/core-concepts/interacting-with-elements
- Cypress eliminates BY DESIGN the viewport-position hazard (it ALWAYS scrolls the element into view before acting), the disabled/hidden hazards, and the non-descendant-overlay hazard (the 'not covered' centre-coordinate hit-test, including a page-nudge past fixed-position coverers). It does NOT eliminate the descendant-tolerance gap: Cypress documents that if a child element covers the exact targeted coordinate, 'the event fires on the child' instead — a descendant re-issue rather than an error. _[cypress]_  
  — source: https://docs.cypress.io/app/core-concepts/interacting-with-elements (covering detection: 'the event fires on the child'); verified in-repo matrix spec/project/e2e-test-stability/en.md lines 70,161
- Cypress {force:true} bypasses ALL actionability checks — it does not scroll into view, does not verify visible/enabled/attached/readonly, does not check animation or covering, and does not re-fire on a descendant; it forcibly fires the event at the element. So force skips the 'covered'/hit-test check entirely and re-introduces the silent wrong-target hazard by opt-in. _[cypress]_  
  — source: https://docs.cypress.io/app/core-concepts/interacting-with-elements (Forcing / {force:true})

## §9  (settled=True)

Distinguishing a test defect from a product defect is a differential-diagnosis problem: evaluate the same failure evidence against two competing hypotheses (test-is-wrong vs product-is-wrong) and rule each in or out via ordered, evidence-gated branches, exactly as clinical decision trees rule disorders in/out from a feature set. The spec should encode an ORDERED procedure, not a checklist, because two branches are validity gates whose violation silently corrupts every downstream conclusion: (0) artefact provenance MUST be verified before any provenance-dependent evidence is trusted, because a mis-attributed per-profile artefact escalated a test bug into a reported product defect; then the cheap, near-decisive test-bug signal — (1) does the failure correlate with LOCATOR STYLE rather than the page (identical UI/build passing under one locator and failing under another ⇒ test bug). Only after those do you ask (2) could a human perform the action here (an open, rendered dialog whose target is visible/stable/hit-testable ⇒ reachable ⇒ test wrong), guarding against the false shortcut that (3) "viewport-specific" implies "test bug" — a control genuinely unreachable at 393px but reachable wide is a product defect (responsive/WCAG target-size), not test noise — and finally (4) profile-independence via a clean isolated context, changing one variable at a time. Each branch names the evidence that discharges it and the failure mode of skipping it, and every step is machine-checkable (artefact SHA/test-id match, locator-only A/B diff, elementFromPoint hit-target equality + non-empty bounding box, per-viewport reproduction, per-profile pass/fail matrix).

**Findings:**
- When a test fails, the team cannot immediately tell whether it signals a genuine defect or test instability; a fault-revealing failure reproduces consistently across reruns on the same build, whereas a flaky failure is non-deterministic on the identical code — this reproduce-across-reruns distinction is the base validity check before either hypothesis is entertained. _[generic]_  
  — source: https://arxiv.org/pdf/2302.10594
- Differential diagnosis is formally a decision tree that starts from a feature set and follows ordered questions to rule disorders in or out; the competing-hypotheses heuristic evaluates the SAME diagnostic evidence across plausible competing diagnoses under uncertainty. This is the formalism the ordered test-vs-product procedure instantiates: one evidence set, two hypotheses, ordered rule-in/rule-out branches. _[generic]_  
  — source: https://pubmed.ncbi.nlm.nih.gov/3989960/
- Most XPath/locator Selenium failures are not caused by the product but by the locator depending on unstable implementation details; prefer stable ID/role/test-id locators. This grounds Branch 1: if identical UI/build passes under a stable locator and fails under a brittle one, the differentiator is the locator, so the failure is a test bug — an A/B where only the locator varies isolates it. _[selenium]_  
  — source: https://prama.ai/choosing-the-right-locator-strategy-for-robust-selenium-test-scripts/
- Playwright's actionability model defines the machine-checkable proxy for 'could a human perform the action': the target must be Visible (non-empty bounding box, not visibility:hidden), Stable (same box across two frames), Receives Events (it is the hit target — Playwright hit-tests at the click point and fails if an overlay would capture the click), and Enabled. A rendered-state screenshot/trace showing the dialog open with the target passing these checks means reachable ⇒ the test is wrong (wrong wait/frame/locator), not the product. _[playwright]_  
  — source: https://playwright.dev/docs/actionability
- 'Receives events' is verified by hit-testing at the action point (document.elementFromPoint-style): Playwright checks whether some other element (usually an overlay) captures the click at that coordinate. This makes the reachability branch testable — assert the element under the click point equals the intended target — but the check is a point-in-time read, so it must be captured from the same failing render, not re-evaluated later (TOCTOU risk). _[playwright]_  
  — source: https://playwright.dev/docs/actionability
- A screenshot is the fastest way to see what the browser actually rendered at failure and is almost always more diagnostic than the error string; capturing trace/screenshot/video/HAR on failure lets you judge reachability without manual reproduction. This is the evidence artefact the reachability branch consumes. _[playwright]_  
  — source: https://oneuptime.com/blog/post/2026-01-28-playwright-debug-test-failures/view
- Layout changes at breakpoints genuinely introduce defects — elements overlapping, focus order changing, content hiding, controls pushed out of view — and WCAG 2.2 target-size requires interactive targets to be at least 24x24 CSS px (44x44 recommended). Therefore a control unreachable at 393px but reachable wide is a PRODUCT defect (responsive/accessibility), which falsifies the shortcut 'viewport-specific ⇒ test bug'. The branch is testable via per-viewport reproduction plus an in-viewport/target-size assertion at the narrow width. _[generic]_  
  — source: https://testparty.ai/blog/mobile-accessibility-testing
- Parallel workers cause CI-only failures and cross-contamination through shared accounts/data/storage, and capturing per-run artefacts (logs, screenshots, video, HAR) on failure is what enables attribution without reproduction. Because artefacts from one worker/profile can be attributed to the wrong test, provenance (artefact filename/metadata ↔ failing test-id, worker, build SHA) MUST be verified before any profile- or environment-dependent evidence is trusted — a mis-attributed per-profile artefact otherwise escalates a test bug into a reported product defect. _[generic]_  
  — source: https://currents.dev/posts/how-to-debug-playwright-tests-in-ci
- Reproducing in a clean, isolated context (fresh profile/incognito, no cached cookies/extensions/state) and changing only one variable at a time distinguishes environment/config causes from genuine application defects: pass in clean profile + fail in dirty profile ⇒ environment/state; fail in both ⇒ product defect independent of local state. This is Branch 4, and it is only valid once Branch 0 provenance has confirmed the compared artefacts truly belong to the profiles they are labelled with. _[generic]_  
  — source: https://myhelp.northwoodtech.edu/kb/article/258-how-to-use-incognito-inprivate-window/
- Playwright's isVisible can report true for an element the user cannot actually interact with (input hidden off-screen behind a styled label/pseudo-element), showing that a single visibility signal is insufficient evidence for reachability — the reachability branch must require the full actionability set (visible AND stable AND receives-events AND enabled) plus in-viewport, not a lone isVisible/displayed check. _[playwright]_  
  — source: https://github.com/microsoft/playwright/issues/24327

The mandate's claim is confirmed at source level. When a test carries a non-strict xfail mark and its call phase raises, pytest's skipping plugin rewrites the report in pytest_runtest_makereport to rep.outcome = "skipped" and attaches rep.wasxfail = <reason>. Because BaseReport.failed is defined as `self.outcome == "failed"`, an xfailed failure has report.failed == False and report.skipped == True — so a harness that captures failure artefacts (screenshot, page source, traceback) only inside `if report.failed:` (or `if report.when=="call" and report.failed`) keeps nothing for exactly the tests that were already flagged as suspect. The correct capture predicate keys off the xfail signal rather than the boolean failed: trigger artefact capture whenever `report.when == "call"` and (`report.failed` OR `getattr(report, "wasxfail", None) is not None`), i.e. use `hasattr(report, "wasxfail")` to detect that an xfail was recorded regardless of the "skipped"/"passed" outcome. Strictness only changes xpass handling: non-strict xpass → outcome "passed" + wasxfail; strict xpass → outcome "failed" with "[XPASS(strict)]"; xfail_strict in pytest.ini / xfail_strict=true sets the project-wide default strictness. A framework-agnostic rule: the diagnostic harness's artefact-capture gate MUST be driven by "an exception/failure occurred during the test body", not by the framework's final green/red verdict, so xfail-suppressed and other soft-failure outcomes still yield a screenshot and traceback.

**Per-framework:**
- **selenium**: Selenium itself has no xfail concept; the demotion is entirely pytest's. In a Selenium+pytest stack the screenshot fixture (a pytest_runtest_makereport hookwrapper storing rep_call, or a fixture reading item.stash) must capture driver.get_screenshot_as_png() / driver.page_source whenever the call-phase report indicates a body exception — condition on `getattr(rep, 'wasxfail', None) is not None OR rep.failed`, never on rep.failed alone, or every xfail(strict=False) failure loses its screenshot and traceback.

**Findings:**
- A non-strict xfail mark whose test FAILS is rewritten by pytest's skipping plugin to rep.outcome = "skipped" with rep.wasxfail set to the xfail reason, inside the pytest_runtest_makereport hook (the excinfo/istrue branch). _[pytest]_  
  — source: https://github.com/pytest-dev/pytest/blob/main/src/_pytest/skipping.py
- BaseReport.failed is defined as `return self.outcome == "failed"` and BaseReport.skipped as `return self.outcome == "skipped"`; therefore an xfailed failure (outcome "skipped") has report.failed == False and report.skipped == True, so a `if report.failed:` artefact-capture guard skips it entirely. _[pytest]_  
  — source: https://github.com/pytest-dev/pytest/blob/main/src/_pytest/reports.py
- The wasxfail attribute is added to the report only by the skipping plugin ('xfail reason if xfailed, otherwise not defined; use hasattr to distinguish'), making `hasattr(report, "wasxfail")` the concrete, documented signal a harness should test to detect any xfail outcome (xfailed or xpassed) irrespective of outcome/failed/skipped. _[pytest]_  
  — source: https://github.com/pytest-dev/pytest/blob/main/src/_pytest/reports.py
- pytest's own terminal status mapping proves the outcome overloading: pytest_report_teststatus checks `hasattr(report, "wasxfail")` and returns 'xfailed' when report.skipped is true and 'xpassed' when report.passed is true — i.e. an xfail failure is genuinely carried on a 'skipped' report, not a 'failed' one. _[pytest]_  
  — source: https://docs.pytest.org/en/stable/_modules/_pytest/skipping.html
- Strictness governs only xpass: non-strict xpass -> rep.outcome = "passed" + rep.wasxfail; strict xpass -> rep.outcome = "failed" with longrepr '[XPASS(strict)] <reason>'. xfailed (expected failure) stays green/'skipped' in both modes. _[pytest]_  
  — source: https://docs.pytest.org/en/stable/how-to/skipping.html
- The default strictness is configured project-wide via `xfail_strict = true` in pytest.ini (or the strict=True/strict=False argument per @pytest.mark.xfail), which flips whether XPASS fails the suite. _[pytest]_  
  — source: https://docs.pytest.org/en/stable/how-to/skipping.html
- The canonical harness pattern for exposing per-phase results to a screenshot/teardown fixture is a pytest_runtest_makereport hookwrapper that does `rep = outcome.get_result()` (or `rep = yield` in the modern `wrapper=True` form) and stores rep keyed by rep.when; the fix for this mandate is to make that fixture's capture condition include `getattr(rep, "wasxfail", None) is not None`, not just `rep.failed`. _[pytest]_  
  — source: https://docs.pytest.org/en/stable/example/simple.html#making-test-result-information-available-in-fixtures
